The short answer

The vendors are right and most rules exist exactly once: who may use the product (decideEntitlement), what plays (resolvePlayback), what a page is (the block document). A rebuild would keep Cloudflare, D1, Mux, WorkOS and Stripe. The cost sits in how many pieces there are and in the seams between them. One Journey Page lives in two databases behind two Workers. A video's truth is split between Mux, a JSON bag and the browser tab that recorded it. Every boundary is typed by hand, so the compiler believes whatever the code says the database returned. Most of the bugs that keep coming back sit on those seams.

The move that closes the most gap. Fold workspace-tree and auth-email into the router (four PRs), then merge the page and Library databases into AUTH_DB (four PRs, the first gives previews their own data). After that a page, its Library card, its address and its form submissions are written in one transaction, and a whole family of "exists in one place but not the other" bugs cannot happen. You deferred the fold on 21 Sept. What changed since is that the reason workspace-tree was a separate Worker, its render Durable Object, was deleted on 22 Sept, and this pass found three new bugs that live on that seam.

Before that, this week. A dozen small changes carry most of the customer-visible gain. The largest is one attribute on the public video player. Phones currently download 2 to 11 MB of video behind posters before anyone taps play. Another is one config line that may cut the 818 ms prospects wait for a public page, because the Worker runs next to the prospect while every database statement travels to Eastern Europe and back, one after another.

A Journey Page's content, address and submissions live in PUBLIC_PAGE_DB. Its folder, position and Library card live in WORKSPACE_TREE_DB, behind another Worker reached over HTTP with signed identity headers. After every save the router copies the page into the tree in the background, and on every Library load it joins three databases back together by hand. When the copy fails, the page exists and the Library does not show it. That is how a recorder's share page ends up live and unfindable after its video is deleted, how a PR preview writes the page to production and its card to a preview database, and why a script exists whose only job is finding pages and cards that disagree.

workspace-tree was split off to host the clip render pipeline and its Durable Object. That pipeline left with the Mux cutover. The tree already dispatches through a route table with declared access per route, so it can be mounted inside the router nearly as it is.

What it deletes. About 1,500 to 2,000 lines for the fold (the identity codec, the proxy, the tree's HTTP marshalling, the webhook relay, the stack deploy mode, two Wrangler configs) and 600 to 900 for the merge (the card projection, the cross-database joins, three of four outbox table copies, the coverage audit script). More important are the questions it removes. Which Worker am I in? Is this caller a service or a user? Does this route accept service callers? Which deploy mode does this diff need? Did the card write land?

Why AUTH_DB and not a new content database. A lead form writes a submission to the page database and then a contact to AUTH_DB, best effort. Merging into AUTH_DB puts contacts, pages, Library and grants in one transaction; a separate content database would leave that split. All four production databases together are 310 MB, so size is not the constraint. VIDEO_STATS_DB stays separate as the append-only events store, and r2-media stays separate because it owns its own host and edge cache.

Where the panel split. GPT-6 Astra ranked a server-owned recording lifecycle first and the fold fifth. Its point stands. The recorder is the hottest bug area and its fix does not strictly need the fold. I still put the fold first because the lifecycle's last steps (create the share page as a Library item in the same transaction as the video, and make deleting a video delete or flag its page) need page and Library in one database, and because the fold is mechanical. The lifecycle's first two PRs can run in parallel inside the folded code.

Where this differs from the 24 Sept greenfield section, and which assumptions it rests on

The 24 Sept report said to merge databases only if dual writes keep biting. They are biting: orphan recorder pages, cards that disagree with pages, best-effort contact linking. It said never adopt Workflows; the clip reconciler is now a hand-written state machine stored in JSON, driven by a cron sweep and waitUntil, which is what Workflows replaces. It put the typed router seam before the fold; the tree already has the route table, so fold first and let the router adopt it. It put one renderer "later"; on-page editing (WIL-3276 and WIL-3277) makes the React canvas the product, and every inline control widens the gap with the string renderer. It had no prospect read path at all.

Fast-moving assumptions. D1 read replication still needs the Sessions API and its beta status is unclear, so treat replicas as an experiment. Smart Placement's effect with D1 must be measured, which is why row 4 comes with Server-Timing. _headers rules on Static Assets have been reported to apply inconsistently when the Worker runs first, which is why row 3 excludes /assets/* from run_worker_first. Hono's typed client stays fast on a few hundred routes when split into sub-apps. Workflows and the Workers Vitest pool are GA and support the Vitest version this repo uses.

Where the panel did not agree. Opus and Fable would retire Convex for a Worker route; Astra would keep it until a replacement proves the per-workspace cap, expiry and reload recovery. I side with retiring it when streaming generation is built, and not before. Opus and Fable want a per-workspace Durable Object for realtime; Astra would start with polling. The Durable Object is the end state, but it is not in the next quarter's plan except as the push that replaces the processing page's full-page poll.

Decisions only you can make

Reopen the Worker fold (WIL-3165)? You deferred it on 21 Sept. The case for it is that the render Durable Object that justified the split was deleted the next day, three bugs found this pass live on the seam, and the work is mechanical. The case against is that it is eight PRs of plumbing before the recorder lifecycle gets full attention, and the database merge needs a short write freeze. My recommendation is yes.

Stop moving things into Convex? WIL-3306 (email on Convex) and WIL-3309 (Library on Convex) point the other way from this plan. WIL-3309 in particular would split a page and its card across two platforms instead of two databases. My recommendation is to close both and replace Convex when streaming generation is built.

Should shared pages stop changing while the rep edits? Today every autosave is live on a link a prospect may have open. A publish step fixes that and makes public pages cacheable, at the cost of one more button. My recommendation is yes, with publish as the default action after the first save so the fast path stays one click.

The unused stops_billing flag on access grants. It is stored and shown in support tools, set to false everywhere, and read by nothing. Either it should cancel billing when a grant starts, or it should go.
