Summary

Today an action such as "publish a Journey Page" is written up to four times. The browser route hand-parses its input. The editor declares its own copy of the response type. The agent door has a second definition with a zod schema and an effect class. Measured on main, Clarity takes requests through 8 doors and about 175 entry points: 101 HTTP method-and-path pairs, 34 MCP operations, 12 webhook event types, 14 cron tasks, 10 data-writing scripts and 4 r2-media entries. 34 of them validate input with a schema, and all 34 are MCP operations. I count 43 rules restated in two or more places, and 29 of those copies disagree. The agent stack keeps its two definitions in step with a hand-written ledger, parity.json (137 rows), whose test checks coverage and not behavior.

Two things got better since the first measurement. The trial wall no longer decides access by HTTP method and path regex, because #1473 moved lapsed accounts to Free and the wall now refuses only suspended accounts (R/trial-wall.ts, 156 lines). And publication is one D1 batch in R/public-page-delivery/live-pages.ts, fenced by clarity/live-page-writes, instead of three separate writes. That store is the one this design needs, so PR 3 adopts it.

The target has two layers. An action defines policy once: name, input and output schema, who may call it, its effect class, whether an agent needs the owner's approval, and the product event its commit writes. A store defines an invariant once. Each table or rule has one writer, fenced by a lint, as clarity/videos-write-fence does for videos and clarity/live-page-writes does for publication. The editor calls act(name, input) over one route, POST /api/actions/:name. MCP and the CLI list the same registry. Webhooks, cron jobs and scripts never call actions. They call the same stores the actions call. One kernel runs every call from every door through the same checks in the same order. An approved change commits only if the state the owner approved is still the state in the database, checked inside the same D1 batch.

The path is 13 PRs. PR 0, merging the stack, is done. The approvable actions move into the kernel first, each with an in-batch guard. Production /mcp stays closed until all of them are guarded, which happens at PR 6. At the end parity.json, the agent dispatcher, the 5,050 lines under R/agent/, the Library's HTTP route table and about 1,750 lines of hand-written editor API modules are gone.

2. The target

Two layers

An action is one thing a signed-in person or their agent can ask Clarity to do or tell them, with one input and one output. It owns policy. A store is the module that writes a table or keeps a rule. It owns the invariant, including the guard that checks an approved state inside its batch. Clarity has three stores of this kind today: videos (clarity/videos-write-fence, so only W/video-row.ts writes videos), machine edits (boundaries/machine-commit) and publication (clarity/live-page-writes, so only live-pages.ts inserts a publication, activates a route or writes kept_reason). The design extends that pattern and puts one action layer on top.

Doors adapt. The editor, MCP and the CLI call actions. Webhooks, jobs and scripts call stores, never actions, because they carry a provider's signature or a job lease, not a person's intent. A capability that has no person behind it, such as a legacy /watch link publishing on first visit, is defined once in its store function, and the store's fence lists every caller. Policy lives in an action, an invariant lives in a store, and a lint fences each.

What an author writes

An action is two declarations that the compiler ties together. The contract is what crosses the wire, and both the editor and the Worker import it. The action is the server half. There are three builders, one per kind of action, because a single builder with a conditional type does not infer (see the critic round).

// packages/actions/src/pages.ts (no server code; the editor imports this)

  version: 1,

Type sketch

// packages/actions/src/contract.ts
export type Effect = 'read' | 'write' | 'spend' | 'publish' | 'retract' | 'destroy';
// What a write can expose. Anything but 'none' makes the write promotable to publish,
// so its action must be built with action.approvable and carry a card.
export type Exposes = 'none' | 'live-media' | 'password-gate' | 'share-page';

type AnyObject = z.ZodMiniObject<z.core.$ZodShape, z.core.$ZodObjectConfig>;   // strict, strip and loose all fit

export type Contract<N extends string = string, I extends AnyObject = AnyObject, O extends z.ZodMiniType = z.ZodMiniType, E extends Effect = Effect> = {
  readonly name: N;          // ^[a-z][a-z0-9_]{1,63}$: the URL segment, the MCP tool name, the CLI words
  readonly version: number;  // stored with an approval; a bump makes a pending approval stale
  readonly effect: E;        // the effect at rest
  readonly exposes?: E extends 'write' ? Exposes : never;
  readonly input: I;
  readonly output: O;        // one output for every door; a door may encode it, never reshape it
};

export function contract<const N extends string, I extends AnyObject, O extends z.ZodMiniType, const E extends Effect>(c: Contract<N, I, O, E>): Contract<N, I, O, E>;

// Keyed by each contract's own name, so a key cannot differ from its name. A duplicate name throws at load.
export function contracts<const C extends readonly Contract[]>(...list: C): { readonly [K in C[number] as K['name']]: K };

export type ActionName = keyof typeof CONTRACTS;
export type ActionInput<N extends ActionName> = z.input<(typeof CONTRACTS)[N]['input']>;
export type ActionOutput<N extends ActionName> = z.output<(typeof CONTRACTS)[N]['output']>;

The commit guard

An approval means something only if the commit checks the approved state in the same transaction. D1 runs a batch as one transaction and rolls the whole batch back when any statement fails (Cloudflare D1 batch docs). SQLite has no RAISE outside triggers, but a CHECK violation is a statement failure. One shared helper turns any condition into a statement that aborts the batch when the condition is false:

-- migrations-auth: one table, empty between batches
CREATE TABLE commit_guards (ok INTEGER NOT NULL CHECK (ok = 1));

// R/commit-guard.ts
// The first statement of a guarded batch. A false condition violates the CHECK, D1 rolls the batch back,
// and the store maps the constraint error to { kind: 'changed' }. The batch's last statement deletes the row.
export function commitGuard(db: D1Database, condition: string, binds: unknown[]): D1PreparedStatement {
  return db.prepare(`INSERT INTO commit_guards (ok) SELECT CASE WHEN (${condition}) THEN 1 ELSE 0 END`).bind(...binds);
}

Each approvable store function takes the expected state, prepends its guard, and appends the cleanup statement. The store owns both the plan and the guard, so the rule for "what counts as unchanged" lives in one module. live-pages.ts already guards the live-page limit this way, with the limit in each statement's WHERE (live-pages.ts:51-58). The commit guard is the same idea for the state the owner approved.

Approval

The rule is one line in the kernel. A call from an agent principal whose effect, read from the card, is publish or destroy stores an ask and stops. The approvable builder makes a card mandatory wherever that can happen. A write that can expose something must say so in its contract (exposes), and the publication and video stores' fences admit only actions built with approvable. That keeps a future videos_edit from being written as a plain write. This is the "Agent 5" plan from the agent-access design, now owned by the kernel instead of the agent dispatcher.

The browser never asks. A session principal is the owner, or support acting for them, and the click is the decision that approval stands in for. The browser still runs card and passes bound to run, so both doors share one run body and one commit guard. An approval decision requires the owner's own session. An impersonated session cannot approve (R/agent/connections-api.ts:28).

Exposure and the card come from one read, so the effect cannot be decided on one snapshot and committed on another. videos_edit computes the live-page fingerprint once. That read yields both the effect (publish when any live page uses the video) and the bound. If a page goes live after the read, the guard refuses the commit as stale. The agent asks again, now as a publish, and the owner sees the live page on the card.

videos_share and a link the owner turned off (decision 6). The one action turns the link on for both doors. The browser's share already does, since #1473 routed it through goLive (R/video-share-page.ts:177). Open editor tabs across a deploy

Each family PR moves the editor to new URLs, and an open tab still holds the old bundle. An old tab cannot learn a new behavior, and a forced reload can discard edits the document store has not sent yet (E/lib/journey-page-document-store.ts:295,595). So the plan never forces a reload on a write.

Instead, each family PR replaces its old handlers with thin legacy adapters. An old row keeps its URL and wire format, maps the old input onto the action, calls perform, and maps the output back to the old envelope. An adapter holds no rules, so the action is still the one definition. PR 2 adds a deploy-aware notice. Every action response carries X-Clarity-Build, and when it differs from the bundle's own build, the editor shows "A new version is ready" and reloads only after the document store reports nothing pending. The adapters go in the last PR, once Workers logs show no hits on them for two weeks.

Analytics

State-change events stay where they are atomic and door-independent: D1 triggers and store batches. They fire for every writer, including jobs, scripts and the legacy /watch hit, which is correct. Moving them into the kernel would lose events on a crash and miss internal writers. The action declares which event its commit writes, or why it writes none. A kernel test runs each action on the SQLite D1 helper and asserts that the declared outbox row appears exactly once.

Decision 8 renames the publish event. The server event journey_page_published replaces the client event journey_page_publish_changed (E/hooks/use-page-publication.ts:188,229, vocabulary at E/lib/product-analytics-events.ts:6). The store writes it in the same batch as the change, with a via property that records the provenance (session, agent, job, watch-link). That property is a label for analytics, not policy, so it does not bring a principal back into the store. Today goLive writes no event at all, so agent publishes are invisible to PostHog (rule 28). Any PostHog chart on the old name moves to the new one. Clicks (data-analytics-id), RUM and upload progress stay as they are, because they describe interaction, not commits.

Why not a framework, and why not REST

tRPC, oRPC, Hono RPC and ts-rest give a typed client and schema plumbing. None knows effect classes, approval cards, commit guards, replay or two principal kinds. We would write all of that as middleware anyway, then an adapter from their router to MCP, and carry their runtime in both the Worker and the editor. The kernel, the HTTP door, the MCP door change and act total about 500 lines of our own code.

Keeping resource URLs and deriving each route row from the action (the gpt-6-astra runner's design) was the serious alternative. It keeps URLs stable for open tabs, along with GET semantics and today's retry. It costs a path-template language, a mapping from path, query and body into the input, and per-family codecs that keep today's envelope quirks ({data} against {stats}, snake case) as permanent vocabulary. Clarity's /api has no outside consumer. The editor ships with the Worker that serves it, and MCP is the public contract. The one route therefore pays three transitional costs: legacy adapters for a migration window, a retry map, and a build notice. In return it removes a permanent mapping layer. William confirmed the one route (decision 2).

Tradeoffs accepted

  • We accept a URL change for every editor call, legacy adapters until old tabs are gone, and a build notice, in exchange for one HTTP row and no per-action path mapping.
  • We accept one output per action. The editor loses some snake-case fields and the agent some condensed views. A door that needs a different view gets a second read action.
  • We accept zod/mini in the editor bundle for input schemas, so screens can reuse them for validation. The size is unmeasured. PR 2 measures it.
  • We accept that the editor trusts output types at runtime. The kernel test parses every action's output against its schema, and the editor ships with the Worker.
  • We accept that the agent audit row lands after the effect, outside the store batch, as today (R/agent/audit.ts:54-61). That is safe only when the effect deduplicates itself. So every keyed create carries a client-chosen id into its store, derived from the connection and the idempotency key, as page create already does with its client UUID. A retry after a crash then hits the store's own uniqueness, not a second insert. folders_create needs this change, because the Library mints a fresh UUID today (W/index.ts:683).
  • We accept that browser calls stay unrated by the kernel, as today. Autosave would trip a per-user write tier.
  • We accept computing the card on browser publish and delete too. That costs a few reads per click, and it gives both doors one run body and one guard.
  • We accept a coarser live-page fingerprint than today's rule, so a harmless change can refuse an agent's video edit as stale.

6. How this design was made

The how step ran four read-only explorers (gpt-6-sol), one per slice: router HTTP doors, the Library and non-browser doors, the editor client, and the parity stack. Their inventories are in the appendix.

The architect step ran three runners on the same brief, each with a different starting lean, so the result could not quietly converge on one shape. Fable kept "operations are the API", with one route and a generated type file. Opus started from "capability modules, no central dispatcher", dropped that lean, and arrived at a contract package with one kernel. gpt-6-astra kept resource URLs with route rows derived from each action, opaque action handles and commit-bound approval.

A blind cross-judge scored them 15, 17 and 25 of 30 and recommended astra's design. The judge ran on gpt-6-astra, the only cross-family seat in the pool, so it may favor its own runner's style. The synthesis takes opus's shape as the base: the contract package, resolve and run, and one kernel. It keeps one route, against the judge, for the reasons in "Why not a framework, and why not REST". From astra it takes approval bound to state checked inside the store batch, action versions on approval rows, opaque handles, and red fixtures for every guard. From fable it takes state-change analytics staying in store batches, every outside row stating its reason, and the commit guard's constraint-violation mechanism.
