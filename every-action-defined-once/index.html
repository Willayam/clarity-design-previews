Every action defined once

Design for William, 2026-10-14. Research and design only. Nothing in Clarity was changed, and no PR or issue was opened.

Code read at main e839a6bd5 and at the agent-parity stack tip 64d30da0b (PRs #1465 to #1475, unmerged). Paths are repo-relative. R/ is workers/frontend-router/src/, W/ is workers/workspace-tree/src/, E/ is editor/src/, and S/ is the same path on the stack tip.

Summary

Today an action such as "publish a Journey Page" is written up to four times. The browser route hand-parses its input. The trial wall decides access by HTTP method and a list of path regexes. The editor declares its own copy of the response type. The agent door has a second definition with a zod schema and an effect class. Measured on main, Clarity takes requests through 8 doors and about 140 entry points: 96 HTTP method-and-path pairs, 9 MCP operations, 12 webhook event types, 13 cron tasks, 10 data-writing scripts and a few more. 9 of them validate input with a schema, and all 9 are MCP operations. I count 28 rules restated in two or more places on main, and 17 of those copies already disagree. The unmerged parity stack brings agents to 34 operations and adds 9 more restated rules. It keeps the two definitions in step with a hand-written ledger, parity.json.

The target has two layers. An action defines policy once: name, input and output schema, who may call it, its effect class, whether an agent needs the owner's approval, and the product event its commit writes. A store defines an invariant once. Each table or rule has one writer, fenced by a lint, as clarity/videos-write-fence already does for videos. The editor calls act(name, input) over one route, POST /api/actions/:name. MCP and the CLI list the same registry. Webhooks, cron jobs and scripts never call actions. They call the same stores the actions call. One kernel runs every call through the same checks in the same order, so the browser wall and the agent dispatcher can no longer drift apart. An approved change commits only if the state the owner approved is still the state in the database, checked inside the same D1 batch.

The path is 14 PRs, the parity stack first and then 13 more. Approval enforcement (the "PR 5" of the agent-access plan, which is #1470 on the stack) reaches staging with the stack. The approvable actions move into the kernel first, each with an in-batch guard. Production /mcp stays closed until all seven of them are guarded, which happens at PR 6. At the end parity.json, the agent dispatcher, agent/ops-*.ts, the trial wall's /api rules, the Library's HTTP route table and about 1,400 lines of hand-written editor API modules are gone.

What the parity stack does and does not change

The stack is real progress for agents. It adds 25 operations, owner approval for publish and destroy with a claim state and a facts digest (S/R/agent/approvals.ts:267-367), a CLI that discovers tools at runtime (S/packages/clarity-cli/clarity.mjs:381), and evals. Fresh agents passed 383 of 385 tasks on the stack tip, against 115 of 275 on main (issue #1463).

It does not define actions once. Its Library operations call the browser's HTTP handler with a synthesized Request and read the status code for meaning. library_delete treats a 400 as "this is a page card" (S/R/agent/ops-destroy.ts:205-209). The editor still calls the old routes. parity.json (137 rows) records which browser path each operation should match. Its test checks syntax and coverage only, so it cannot show that the two doors validate, authorize or answer alike (S/editor/tests/agent-parity.test.ts:128-179).

It also leaves one class of gap that matters before production. Every approval recomputes the card's facts at the owner's click, compares their digest, then runs a separate write that does not check them again. A folder delete removes whatever the folder holds when its batch runs (S/W/workspace-tree-store.ts:333-410). A video edit checks for live pages in JavaScript, then commits through the Library (S/R/agent/ops-publish.ts:391,435). A change in the milliseconds between the check and the write commits something the owner never saw. The same pattern covers page delete and video share.

2. The target

Two layers

An action is one thing a signed-in person or their agent can ask Clarity to do or tell them, with one input and one output. It owns policy. A store is the module that writes a table or keeps a rule. It owns the invariant, including the guard that checks an approved state inside its batch. Clarity already has stores of this kind for videos (clarity/videos-write-fence, so only W/video-row.ts writes videos) and machine edits (boundaries/machine-commit). Draft #1473 adds one for publication (clarity/live-page-writes). The design extends that pattern and puts one action layer on top.

Doors adapt. The editor, MCP and the CLI call actions. Webhooks, jobs and scripts call stores, never actions, because they carry a provider's signature or a job lease, not a person's intent. A capability that has no person behind it, such as a legacy /watch link publishing on first visit, is defined once in its store function, and the store's fence lists every caller. Policy lives in an action, an invariant lives in a store, and a lint fences each.

editor ── act() ──► POST /api/actions/:name ─┐
agent ── MCP tools/call ─────────────────────┼─► kernel ─► action.resolve, card, run ─► stores ─► D1, Mux, R2
CLI ── MCP tools/call ───────────────────────┘                                         ▲
Mux, Stripe webhooks ── verify signature ──────────────────────────────────────────────┤
cron jobs ── lease ────────────────────────────────────────────────────────────────────┤
legacy /watch first hit, scripts ──────────────────────────────────────────────────────┘

What an author writes

An action is two declarations that the compiler ties together. The contract is what crosses the wire, and both the editor and the Worker import it. The action is the server half. There are three builders, one per kind of action, because a single builder with a conditional type does not infer (see the critic round).

// packages/actions/src/pages.ts (no server code; the editor imports this)

Type sketch

// packages/actions/src/contract.ts
export type Effect = 'read' | 'write' | 'spend' | 'publish' | 'retract' | 'destroy';
// What a write can expose. Anything but 'none' makes the write promotable to publish,
// so its action must be built with action.approvable and carry a card.
export type Exposes = 'none' | 'live-media' | 'password-gate' | 'share-page';

type AnyObject = z.ZodMiniObject<z.core.$ZodShape, z.core.$ZodObjectConfig>;   // strict, strip and loose all fit

export type Contract<N extends string = string, I extends AnyObject = AnyObject, O extends z.ZodMiniType = z.ZodMiniType, E extends Effect = Effect> = {
  readonly name: N;          // ^[a-z][a-z0-9_]{1,63}$: the URL segment, the MCP tool name, the CLI words
  readonly version: number;  // stored with an approval; a bump makes a pending approval stale
  readonly effect: E;        // the effect at rest
  readonly exposes?: E extends 'write' ? Exposes : never;
  readonly input: I;
  readonly output: O;        // one output for every door; a door may encode it, never reshape it
};

export function contract<const N extends string, I extends AnyObject, O extends z.ZodMiniType, const E extends Effect>(c: Contract<N, I, O, E>): Contract<N, I, O, E>;

// Keyed by each contract's own name, so a key cannot differ from its name. A duplicate name throws at load.
export function contracts<const C extends readonly Contract[]>(...list: C): { readonly [K in C[number] as K['name']]: K };
export const CONTRACTS = contracts(pagesPublish, pagesUnpublish, libraryDelete /* ... */);
export type ActionName = keyof typeof CONTRACTS;
export type ActionInput<N extends ActionName> = z.input<(typeof CONTRACTS)[N]['input']>;
export type ActionOutput<N extends ActionName> = z.output<(typeof CONTRACTS)[N]['output']>;

// Generated from CONTRACTS by scripts/check-actions.mjs --write, checked with --check in CI.
// The editor reads it to retry reads, without bundling every schema.
export const EFFECTS: Readonly<Record<ActionName, Effect>>;

// One refusal vocabulary. It starts as the union of today's reason vocabularies
// (JourneyPageRejection in packages/journey-page-domain/src/journey-pages-api.ts:110, the stack's
// S/R/agent/refusal.ts, the wall's codes), so no existing answer is lost.
export type Refusal =
  | { code: 'invalid_input'; message: string; issues: InputIssue[] }
  | { code: 'not_found'; message: string }
  | { code: 'caller_not_allowed'; message: string }
  | { code: 'permission_required'; permission: Permission; settingsUrl: string }
  | { code: 'rate_limited' | 'daily_limit'; retryAfterSeconds: number; message: string }
  | { code: 'access_walled'; wallCause: WallCause }
  | { code: 'account_suspended'; message: string }
  | { code: 'stale_revision' | 'already_created'; message: string; current: JourneyPageDraftWire }   // the autosave merge needs the draft
  | { code: 'stale_base' | 'generation_running' | 'workspace_limit' | 'reload_required'; message: string }
  | { code: 'stale_approval'; message: string }
  | { code: 'empty_page' | 'live_page_limit' | 'not_ready' | 'unavailable'; message: string }
  | { code: 'edit_refused'; at: number; message: string; refusal: EditRefusal; revision: number }
  | { code: 'idempotency_conflict' | 'recently_denied'; message: string };

// Rules that live outside the registry but are shared by both sides.
export const PASSWORD = z.string().check(z.minLength(8));   // auth-session.ts and the three editor password screens

// workers/frontend-router/src/actions/action.ts
export type Principal =
  | { readonly kind: 'session'; readonly identity: AuthIdentity; readonly impersonatorId: string | null }
  | { readonly kind: 'agent'; readonly identity: AuthIdentity; readonly connection: AgentConnection };
// No 'system' kind. Webhooks, jobs, scripts and the legacy /watch hit call stores.

export type SessionAccess = 'account' | 'account-not-impersonated' | 'staff' | 'never';
export type AgentDoor =
  | { readonly title: string; readonly description: string; readonly destructiveHint: boolean; readonly idempotentHint: boolean;
      readonly requires?: Permission;
      // A keyed replay answers the stored output only while still valid (an upload grant unexpired,
      // a created folder not deleted), as S/R/agent/dispatch.ts:111-124 does today.
      readonly idempotency?: { kind: 'natural'; field: string } | { kind: 'input'; replayStillValid?: ReplayCheck } }
  | { readonly hidden: string };   // why agents cannot call it; this replaces parity.json's "excluded"

// What a lapsed account may still do. The default derives from the effect: reads, retracts and destroys
// stay open. Exceptions are declared, as checkout start is today (R/trial-wall.ts:40).
export type WhileLapsed = 'open' | 'refused';

export type ApprovalCard<B> = {
  readonly target: { kind: ApprovalTargetKind; id: string; name: string };
  readonly summary: string;
  readonly details: readonly ApprovalDetail[];
  readonly bound: B;                              // the state the run commits against; hashed with the card
  readonly effect: 'publish' | 'write' | 'destroy';   // derived from the same read as bound, never a second query
};

type Common<C extends Contract> = {
  readonly session: SessionAccess;
  readonly agent: AgentDoor;
  readonly whileLapsed?: WhileLapsed;
};
type In<C extends Contract> = z.output<C['input']>;
type Out<C extends Contract> = z.output<C['output']>;
type Event = { writtenBy: 'store'; name: ProductEventName } | { none: string };

// Properties are written in the order resolve, card, run, so T and B infer left to right.
export const action: {
  read<C extends Contract<string, AnyObject, z.ZodMiniType, 'read'>, T>(c: C, d: Common<C> & {
    resolve(ctx: ActionContext, principal: Principal, input: In<C>): Promise<T>;
    run(ctx: ActionContext, principal: Principal, target: T, input: In<C>): Promise<Out<C>>;
  }): ActionHandle<C>;

  // Writes that expose nothing, spends and retracts.
  plain<C extends Contract<string, AnyObject, z.ZodMiniType, 'write' | 'spend' | 'retract'> & { exposes?: 'none' }, T>(c: C, d: Common<C> & {
    event: Event;
    resolve(ctx: ActionContext, principal: Principal, input: In<C>): Promise<T>;
    run(ctx: ActionContext, principal: Principal, target: T, input: In<C>): Promise<Out<C>>;
  }): ActionHandle<C>;

  // Publishes, destroys, and writes that declare an exposure. The card is mandatory.
  approvable<C extends Contract<string, AnyObject, z.ZodMiniType, 'publish' | 'destroy'> | (Contract<string, AnyObject, z.ZodMiniType, 'write'> & { exposes: Exclude<Exposes, 'none'> }), T, B>(c: C, d: Common<C> & {
    event: Event;
    resolve(ctx: ActionContext, principal: Principal, input: In<C>): Promise<T>;
    card(ctx: ActionContext, target: T, input: In<C>): Promise<ApprovalCard<B>>;
    run(ctx: ActionContext, principal: Principal, target: T, input: In<C>, bound: B): Promise<Out<C>>;
  }): ActionHandle<C>;
};

// workers/frontend-router/src/actions/registry.ts
export const ACTIONS = registry(pages.publish, pages.unpublish, library.remove /* ... */);
// Both directions fail to compile: a contract with no action, and an action whose contract is not in CONTRACTS.
type Registered = RegisteredName<typeof ACTIONS>;
const complete: [Exclude<ActionName, Registered> | Exclude<Registered, ActionName>] extends [never] ? true : never = true;

The sketch is a design, not compiled code. Two critics compiled the previous version with the repo's TypeScript 6.0.3 and zod 4.4.3. A single builder whose parameter held a conditional type inferred every target as unknown. Opus's critic checked that separate builders like these infer with 0 errors. The kernel PR's first commit is a compile test of exactly these examples: a publish, a plain write, a promotable write, a loose-object contract, a missing card, a wrong output, an extra action and a duplicate name.

// workers/frontend-router/src/actions/kernel.ts
export type Performed =
  | { kind: 'done'; output: unknown }
  | { kind: 'refused'; refusal: Refusal }
  | { kind: 'asked'; approvalId: string; approvalUrl: string; expiresAt: string }   // agent principals only
  | { kind: 'retry'; retryAfterSeconds: number };

// Every call from every door, in this order:
//   1. find the action                                           not_found
//   2. admit the principal: session access, agent door,          caller_not_allowed, not_found for a hidden
//      impersonation rule, suspension from the identity row      action, account_suspended
//   3. parse input with the contract                             invalid_input
//   4. agent permission grant                                    permission_required
//   5. agent rate tier, per connection                           rate_limited
//   6. agent keyed replay, if still valid                        stored output, or idempotency_conflict
//   7. resolve the target                                        what resolve refuses
//   8. read: run and return. No standing read, so a lapsed account's reads never call Stripe
//   9. approvable: card, which yields bound and the effect now from one read
//  10. lapsed standing, for write, spend and publish unless      access_walled, or the principal's rule
//      whileLapsed is open                                       when standing cannot be read
//  11. agent, and the effect now is publish or destroy: store    asked, or recently_denied
//      the ask (action name and version, canonical input,
//      card digest) and stop
//  12. run(…, bound). The store prepends its commit guard        stale_approval, stale_revision
//  13. agent audit row
export function perform(ctx: ActionContext, principal: Principal, name: string, raw: unknown): Promise<Performed>;

// The owner's Approve click. Rebuilds the agent principal from the connection row, parses the stored
// input against the current contract (a different version is stale_approval), reruns steps 2 to 4, 7, 9
// and 10 (no rate charge, no replay), compares the card digest with the approved one, claims
// pending to executing, then runs 12 and 13 once.
export function resume(ctx: ActionContext, owner: Principal & { kind: 'session' }, approvalId: string): Promise<ApprovalOutcome>;

The kernel is the deep module. It hides parsing, door admission, permission, rate, replay, target loading, account standing, approval and audit behind perform and resume. A door is transport only. The HTTP door is about 150 lines. The MCP door is today's R/agent/mcp.ts calling perform. The editor's act is about 80 lines over the existing apiFetch. An action author writes resolve and run, plus card when the builder demands it.

The commit guard

An approval means something only if the commit checks the approved state in the same transaction. D1 runs a batch as one transaction and rolls the whole batch back when any statement fails (Cloudflare D1 batch docs). SQLite has no RAISE outside triggers, but a CHECK violation is a statement failure. One shared helper turns any condition into a statement that aborts the batch when the condition is false:

-- migrations-auth: one table, empty between batches
CREATE TABLE commit_guards (ok INTEGER NOT NULL CHECK (ok = 1));

// R/commit-guard.ts
// The first statement of a guarded batch. A false condition violates the CHECK, D1 rolls the batch back,
// and the store maps the constraint error to { kind: 'changed' }. The batch's last statement deletes the row.
export function commitGuard(db: D1Database, condition: string, binds: unknown[]): D1PreparedStatement {
  return db.prepare(`INSERT INTO commit_guards (ok) SELECT CASE WHEN (${condition}) THEN 1 ELSE 0 END`).bind(...binds);
}

Each approvable store function takes the expected state, prepends its guard, and appends the cleanup statement. The store owns both the plan and the guard, so the rule for "what counts as unchanged" lives in one module.

Approval

The rule is one line in the kernel. A call from an agent principal whose effect, read from the card, is publish or destroy stores an ask and stops. The approvable builder makes a card mandatory wherever that can happen. A write that can expose something must say so in its contract (exposes), and the publication and video stores' fences admit only actions built with approvable. That keeps a future videos_edit from being written as a plain write. This is the "Agent 5" plan from the agent-access design (approvals, publish, share page, delete, live-media edits), now owned by the kernel instead of the agent dispatcher.

The browser never asks. A session principal is the owner, or support acting for them, and the click is the decision that approval stands in for. The browser still runs card and passes bound to run, so both doors share one run body and one commit guard. An approval decision requires the owner's own session. An impersonated session cannot approve (S/R/agent/approvals-api.ts:8).

Exposure and the card come from one read, so the effect cannot be decided on one snapshot and committed on another. videos_edit computes the live-page fingerprint once. That read yields both the effect (publish when any live page uses the video) and the bound. If a page goes live after the read, the guard refuses the commit as stale. The agent asks again, now as a publish, and the owner sees the live page on the card.

uploads_finish with sharePage: true births a published share page, as the recorder does today (R/video-share-page.ts:99-130). Its contract declares exposes: 'share-page', so an agent that sends it gets an approval card. Without the flag it stays a private write.

What the stack already built carries over: the agent_approvals table, the claim state, the 24-hour expiry, the 10-minute denial block and the approval screens. Four things change. Approval rows gain an action_version column (migration, nullable for rows the legacy executor wrote). resume parses stored input against the current contract instead of casting it (S/R/agent/approvals.ts:329-345). The commit binds to bound inside the store's batch. And until the last approvable operation moves, the approve and deny API routes each row by name: a name in ACTIONS goes to resume, anything else to the stack's approveApproval.

Account standing and entitlement

Today the browser decides access by method and path, and the agent by effect class. The kernel decides it in two places. Suspension is checked at admission, from the identity row the session already holds, as both doors do today (R/trial-wall.ts:79-81, S/R/agent/caller.ts:206). Lapsed standing is checked only for write, spend and publish, after the card has fixed the effect. Reads never trigger a standing read, so a lapsed rep browsing the editor costs no Stripe calls, exactly as today. Retracts and destroys stay open to a lapsed account, because it may still take down what it published. Checkout start declares whileLapsed: 'open'. The trial wall keeps only app-shell redirects, the suspended answer, and the /api rows that stay outside the registry and write (the upload relay and the speech window) unless each of them requires a grant from an action that already refused a lapsed account.

Draft PR #1473 changes what "lapsed" means. It moves lapsed accounts to Free, keeps writes open, and enforces a three-live-page limit inside the publish batch. If it lands first, step 10 shrinks to "Free or Pro, both continue", whileLapsed disappears, and the live-page limit stays a store invariant that answers live_page_limit.

Two failure modes differ by door today, and the kernel keeps both answers in one function, onStandingUnreadable(principal, cause). When the standing read throws, the browser lets a nonsuspended account through (R/trial-wall.ts:91-98) and the agent answers 503 (R/agent/dispatch.ts:178-186). When D1 says walled and Stripe cannot be asked, the browser keeps D1's walled verdict (R/trial-offer-with-stripe-sync.ts:27) and the agent answers 503 rather than cache a denial Stripe might lift (S/R/agent/policy.ts:38). Changing either is a product call, not part of this migration.

Open editor tabs across a deploy

Each family PR moves the editor to new URLs, and an open tab still holds the old bundle. An old tab cannot learn a new behavior, and a forced reload can discard edits the document store has not sent yet (E/lib/journey-page-document-store.ts:295,595). So the plan never forces a reload on a write.

Instead, each family PR replaces its old handlers with thin legacy adapters. An old row keeps its URL and wire format, maps the old input onto the action, calls perform, and maps the output back to the old envelope. An adapter holds no rules, so the action is still the one definition. PR 2 adds a deploy-aware notice. Every action response carries X-Clarity-Build, and when it differs from the bundle's own build, the editor shows "A new version is ready" and reloads only after the document store reports nothing pending. The adapters go in the last PR, once Workers logs show no hits on them for two weeks.

Analytics

State-change events stay where they are atomic and door-independent: D1 triggers and store batches. They fire for every writer, including jobs, scripts and the legacy /watch hit, which is correct. Moving them into the kernel would lose events on a crash and miss internal writers. The action declares which event its commit writes, or why it writes none. A kernel test runs each action on the SQLite D1 helper and asserts that the declared outbox row appears exactly once. New events such as journey_page_published are written by the store in the same batch as the change, with a via property that records the provenance (session, agent, job, watch-link). That property is a label for analytics, not policy, so it does not bring a principal back into the store. Client events that restate a server fact, such as journey_page_publish_changed, go. Clicks (data-analytics-id), RUM and upload progress stay as they are, because they describe interaction, not commits.

Internal callers

There is no system principal. An action answers "may this caller do this to this account, and must a human say yes". A cron job is the continuation of a call that already passed that question, and it carries a lease (R/jobs-store.ts:6-27). A webhook carries a provider's signature. Running either through the kernel would add a fake principal and skip every step but run.

Guards

Each fails CI and lands in docs/agents/guards.md through scripts/generate-guards-table.mjs, which reads lint messages and script headers.

  1. A new /api row must say why it is not an action. editor/tests/route-table.test.ts already walks every row. It gains a check that every row serving an /api/ path is the actions row or carries an outside reason. A legacy reason must name an issue, and the number of legacy rows has a budget that only shrinks, as css-budget.json does.
  2. Doors reach actions only through the kernel. action() returns an opaque handle. A boundaries/action-kernel lint, built like boundaries/machine-commit, lets only actions/kernel.ts and actions/registry.ts import action modules.
  3. Stores are reached only from their listed callers. A boundaries/store-callers lint gives each fenced store an allowlist: action modules, plus named webhook, job and script modules. A new handler that imports publication.goLive or library.deleteNode fails lint. This closes the real way past the kernel, which is calling a store directly.
  4. MCP lists only the registry. tools/list is computed from ACTIONS where the agent door is open, and tools/call calls only perform. A lint bans tools/call handling anywhere else.
  5. The editor calls the API only through act and named protocol modules. The lint bans importing apiRequest, apiFetch or workspaceTreeRequest, and bans calling fetch at all, outside E/lib/actions.ts and E/lib/protocols/ (uploads, telemetry). Banning the call rather than a URL literal also catches paths built at runtime. Its baseline goes in eslint-suppressions.json and shrinks per family.
  6. Every action is complete. The builders, the conditional event type and the complete constant make a missing card, a missing event declaration, a missing action or an orphan action a compile error. scripts/check-actions.mjs runs tsc over the action compile tests and regenerates EFFECTS. Its header names the rule, so the guards table lists it.
  7. The guards are proven red. scripts/check-action-boundaries.test.mjs holds four fixtures: an /api row with no outside reason, a handler that imports a fenced store, a second MCP tool handler, and an editor fetch. Each must fail its rule. A guard that cannot fail is worse than none.

Why not a framework, and why not REST

tRPC, oRPC, Hono RPC and ts-rest give a typed client and schema plumbing. None knows effect classes, approval cards, commit guards, replay or two principal kinds. We would write all of that as middleware anyway, then an adapter from their router to MCP, and carry their runtime in both the Worker and the editor. The kernel, the HTTP door, the MCP door change and act total about 500 lines of our own code.

Keeping resource URLs and deriving each route row from the action (the gpt-6-astra runner's design) is the serious alternative. It keeps URLs stable for open tabs, along with GET semantics and today's retry. It costs a path-template language, a mapping from path, query and body into the input, and per-family codecs that keep today's envelope quirks ({data} against {stats}, snake case) as permanent vocabulary. Clarity's /api has no outside consumer. The editor ships with the Worker that serves it, and MCP is the public contract. The one route therefore pays three transitional costs: legacy adapters for a migration window, a retry map, and a build notice. In return it removes a permanent mapping layer. I think that trade is right. It is a judgment call, and the decisions section asks William to confirm it.

Tradeoffs accepted

  • We accept a URL change for every editor call, legacy adapters until old tabs are gone, and a build notice, in exchange for one HTTP row and no per-action path mapping.
  • We accept one output per action. The editor loses some snake-case fields and the agent some condensed views. A door that needs a different view gets a second read action.
  • We accept zod/mini in the editor bundle for input schemas, so screens can reuse them for validation. The size is unmeasured. PR 2 measures it.
  • We accept that the editor trusts output types at runtime. The kernel test parses every action's output against its schema, and the editor ships with the Worker.
  • We accept that the agent audit row lands after the effect, outside the store batch, as today (S/R/agent/audit.ts:54). That is safe only when the effect deduplicates itself. So every keyed create carries a client-chosen id into its store, derived from the connection and the idempotency key, as page create already does with its client UUID. A retry after a crash then hits the store's own uniqueness, not a second insert. folders_create needs this change, because the Library mints a fresh UUID today (W/index.ts:688).
  • We accept that browser calls stay unrated by the kernel, as today. Autosave would trip a per-user write tier.
  • We accept computing the card on browser publish and delete too. That costs a few reads per click, and it gives both doors one run body and one guard.
  • We accept a coarser live-page fingerprint than today's rule, so a harmless change can refuse an agent's video edit as stale.

  2. One route for every action, POST /api/actions/:name, instead of today's resource URLs. Recommended: yes. The costs are legacy adapters until old tabs are gone, a read-retry map and a build notice.
  3. Order against draft #1473 (Free plan). Its live-pages.ts is the publication store this plan needs. Recommended: if Free is going ahead, land #1473 first and PR 3 becomes adoption. If not, PR 3 builds the store and #1473 rebases onto it.
  4. When account standing cannot be read. Today a thrown read lets a browser write through and gets an agent a 503. When Stripe cannot be asked, the browser keeps D1's wall and the agent gets 503. Recommended: keep both answers, declared in one kernel function.
  5. An inaccessible page answers 404 for every door. Today the browser can answer 403. Recommended: 404, so an id leaks nothing.
  6. An agent sharing a video whose link the owner turned off. The stack turns it back on after approval, and the browser keeps it off. One action needs one answer. Recommended: keep it off, because the owner turned it off on purpose.
  7. Contact delete for a lapsed account. The agent can, the browser cannot. Recommended: open, like every other takedown. This question goes away if #1473 lands.

6. How this design was made

The how step ran four read-only explorers (gpt-6-sol), one per slice: router HTTP doors, the Library and non-browser doors, the editor client, and the parity stack. Their inventories are in the appendix.

The architect step ran three runners on the same brief, each with a different starting lean, so the result could not quietly converge on one shape. Fable kept "operations are the API", with one route and a generated type file. Opus started from "capability modules, no central dispatcher", dropped that lean, and arrived at a contract package with one kernel. gpt-6-astra kept resource URLs with route rows derived from each action, opaque action handles and commit-bound approval.

A blind cross-judge scored them 15, 17 and 25 of 30 and recommended astra's design. The judge ran on gpt-6-astra, the only cross-family seat in the pool, so it may favor its own runner's style. It checked claims with a compiler. Opus's satisfies registry did not tie keys to names. Fable's name: string widened every name to string. Opus's analytics key would merge repeated publish and unpublish events. And reload_required does not reload today.

The synthesis takes opus's shape as the base: the contract package, resolve and run, and one kernel. It keeps one route, against the judge, for the reasons in "Why not a framework, and why not REST". From astra it takes approval bound to state checked inside the store batch, action versions on approval rows, opaque handles, and red fixtures for every guard. From fable it takes state-change analytics staying in store batches, every outside row stating its reason, and the commit guard's constraint-violation mechanism.

Three adversarial reviewers attacked the first synthesis: fable (15 findings), opus (20) and gpt-6-astra (13). Each read the design end to end and checked claims against both trees. Two of them compiled the type sketch. Findings raised by two or three reviewers independently carry the most weight. The design above already includes every change in the first table.
