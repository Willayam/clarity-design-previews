Inventory

This inventory covers requests initiated by editor/src on main. It counts a distinct method and path once, even when several controls call it. It includes the external media requests that the editor makes after the server grants an upload. It does not count ordinary browser navigation, SDK traffic generated inside PostHog, or the other agents’ webhook, cron, and CLI slices.

Reading the tables: S means a cookie session, O means the handler scopes the resource to the caller’s workspace or checks page access, and A means System Admin. W means the route is below the trial-wall middleware at workers/frontend-router/src/routes.ts:384-390. That middleware lets ordinary reads through for a nonsuspended account; its write exceptions are described below. H means hand parsing or a domain parser, P means a parser or contract imported from packages/, and — means no request body. E means the response type is declared in the editor, P means a package type, and U means an inline cast, unknown, or no typed response. All apiRequest calls share the behavior at editor/src/lib/editor-api.ts:237-334: JSON is cast to T, not checked at runtime; non-2xx becomes ApiRequestError.

  • Zero editor HTTP actions use Zod at their HTTP boundary. The request bodies are hand parsed or use shared domain parsers. Zod appears in the separate MCP operation definitions, for example workers/frontend-router/src/agent/ops-pages.ts:1-102, and dispatch calls safeParse at agent/dispatch.ts:147.
  • 68 of 84 paths sit below the implicit trial-wall middleware. Of those, 41 are writes. Four write paths are deliberate exits for a walled account: checkout session creation, Library deletion, page deletion, and unpublish (workers/frontend-router/src/trial-wall.ts:38-43,210-228). Ordinary reads skip the entitlement decision unless the session is suspended (trial-wall.ts:77-83). The remaining 16 actions are public/auth or external media requests. I found no per-action editor HTTP entitlement schema.
  • For response contracts, the named shared responses I could confirm are 10 package types: five Journey Page request/response types, sharing, page stats, Mux download, video stats, and speech window. The editor declares at least 27 major named response DTOs across Library (12), take (4), admin accounts (8), auth (3); additional local DTOs live in contacts, settings, upload, sharing, and support files. Inline generic envelopes and casts make a single exact “number of types” dependent on whether nested DTOs and anonymous { data: ... } shapes count. The defensible finding is that most Library, take, auth, billing, admin, contact, and upload response contracts are editor-owned, while the Journey Page document and a few media/stats responses are package-owned.

Non-obvious things

  • The trial wall is method sensitive. Reads are usually allowed for a walled, nonsuspended account, while most writes are blocked. A route’s place below the middleware therefore does not mean its read actually performs an entitlement decision. Suspensions are stricter (workers/frontend-router/src/trial-wall.ts:77-83,124-146).
  • apiRequest treats a successful HTTP status as success even if a legacy endpoint returns a 200 error envelope. Its own comment warns callers that data can be missing (editor/src/lib/editor-api.ts:273-293). Notifications also return a bare preferences object rather than a {data} envelope (workers/frontend-router/src/account-profile.ts:408-410).
  • The upload flow is a protocol, not one server action. The router grants an R2 upload, the browser sends bytes to R2 or a PR-preview relay, then the browser verifies public readability and creates a Library node. Video takes instead grant a Mux resumable URL, PUT chunks, then finish the take. The Mux sender interprets 308 ranges and 200/201 completion itself (editor/src/lib/take-sender.ts:9-12,110-136).
  • POST /api/tree/media/videos/:id/download can start Mux rendition work and return a status to poll, even though its name sounds like a read (editor/src/lib/tree-api.ts:339-349; workers/workspace-tree/src/mux-video-download.ts:39).
  • Page creation accepts a client UUID so a retried create can recover the same page; the server refuses an ID belonging to another owner (workers/frontend-router/src/journey-pages-native.ts:328-347). Page updates require a base revision and return a conflict body that the editor uses to merge (:394-421).
  • The Library DELETE /nodes/:id refuses Journey Page cards; the page API owns the page and card together (workers/workspace-tree/src/index.ts:723-735). A generic operation derived from node kind would need that distinction.
  • Server product events may be emitted by SQL triggers, not the handler that conceptually performs the action. New video nodes are a special case: the insert trigger cannot fire at grant because provenance is null, so finish writes video_added manually (workers/workspace-tree/src/video-row.ts:475-500).
  • The editor’s product-analytics-events.ts is a client PostHog vocabulary, not a server action registry. data-analytics-id labels clicked controls. Consent, identity, and route filtering happen in editor/src/lib/product-analytics.ts:50-88,125-135,214-220.
