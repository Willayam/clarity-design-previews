Non-obvious things

Approval is an agent workflow, not a common capability definition. After parsing, permission, rate, exposure, entitlement, and replay checks, the dispatcher calls facts(), hashes the parsed input and card facts, and finds or inserts a pending agent_approvals row. It returns approval_required with a URL; it does not execute the operation (stack/workers/frontend-router/src/agent/dispatch.ts:128). The row stores connection, user, operation, target, canonical input JSON/hash, facts digest/JSON, status, timestamps, and later result/detail (stack/workers/frontend-router/migrations-auth/0042_agent_access.sql:71, stack/workers/frontend-router/migrations-auth/0047_agent_approval_facts.sql:6).

The owner sees the server-built card and clicks in stack/editor/src/components/ApprovalDecision.tsx:48. The cookie API refuses an impersonator’s decision (stack/workers/frontend-router/src/agent/connections-api.ts:24). Approval checks connection and extra permission again, and checks entitlement again for publish. A guarded pending → executing update lets one click claim the row (stack/workers/frontend-router/src/agent/approvals.ts:267). It recomputes facts() and compares the whole card digest, then calls run(context, storedInput, approvedFacts) (stack/workers/frontend-router/src/agent/approvals.ts:329). Page publish binds to approved revision; password update binds to approved timestamp; video edit binds to relevant manifest fields; Library delete uses the approved inventory for its answer (stack/workers/frontend-router/src/agent/ops-publish.ts:139, stack/workers/frontend-router/src/agent/ops-publish.ts:212, stack/workers/frontend-router/src/agent/ops-publish.ts:425, stack/workers/frontend-router/src/agent/ops-destroy.ts:210).

A pending ask expires after 24 hours. A denial blocks another ask for the same connection, operation, and target for 10 minutes. A request still executing after 60 seconds becomes failed and is never run automatically again. These values are constants in stack/workers/frontend-router/src/agent/approvals.ts:30. Agent reads show executing as pending; owner reads show executing (stack/workers/frontend-router/src/agent/ops-account.ts:49, stack/workers/frontend-router/src/agent/approvals.ts:179).

Publish and destroy require approval when the agent asks because an agent call is not the owner’s direct decision (stack/workers/frontend-router/src/agent/operation.ts:7, stack/workers/frontend-router/src/agent/approvals.ts:12). The browser publish, delete, and share handlers run on the owner’s authenticated action, with no separate approval row (stack/workers/frontend-router/src/journey-pages-native.ts:114, stack/workers/frontend-router/src/video-share-page.ts:85). The stack also chooses approval for a live password widening or an edit to a video used by a live page. It does not require approval for unpublish or an agent destroy’s entitlement.

parity.json is a UI call ledger. Its test requires unique row IDs, one agent classification per row, valid effect labels, registered operation references, effect agreement, coverage of every registered operation, and syntactically valid METHOD path strings (stack/editor/tests/agent-parity.test.ts:128). It scans editor TypeScript string/template literals for /api and /auth calls, with manual aliases and three unseen calls, then checks both directions against the ledger (stack/editor/tests/agent-parity.test.ts:22, stack/editor/tests/agent-parity.test.ts:97, stack/editor/tests/agent-parity.test.ts:179). It cannot prove a backend route exists, that a UI action really calls the listed path at runtime, that operation and browser validation/authorization/effects/results match, or that webhook, cron, admin, and script doors are covered. The aliases are asserted as declarations, not derived from runtime calls.

The CLI is dynamic at runtime. The server derives MCP tools/list from the registry’s names, descriptions, and Zod-to-JSON input schemas (stack/workers/frontend-router/src/agent/registry.ts:26, stack/workers/frontend-router/src/agent/mcp.ts:198). The CLI fetches and caches tools/list for an hour, matches words such as pages edit to pages_edit, parses flags against advertised properties, then calls tools/call (stack/packages/clarity-cli/clarity.mjs:381, stack/packages/clarity-cli/clarity.mjs:603). Its five built-in commands and file upload orchestration are hand written (stack/packages/clarity-cli/clarity.mjs:664, stack/packages/clarity-cli/clarity.mjs:709). The Vite plugin ships that source as a static asset (stack/editor/vite-clarity-cli.ts:5). No CLI source file is generated from the registry at build time.

The browser-handler changes are selective extractions. The stack extracts createJourneyPageDraft and duplicateJourneyPageDraft in stack/workers/frontend-router/src/journey-pages-native.ts:340, stack/workers/frontend-router/src/journey-pages-native.ts:585. It exports the existing renameJourneyPage handler for agent reuse (stack/workers/frontend-router/src/journey-pages-native.ts:501). It extracts saveContact and a blank contact input in stack/workers/frontend-router/src/contacts-api.ts:124, stack/workers/frontend-router/src/contacts-api.ts:465. It extracts notification preference writing and exposes reading in stack/workers/frontend-router/src/account-profile.ts:432. The Library index.ts change moves query parsers to tree-query.ts and adds type-only search plus offset; it does not extract a shared action definition (stack/workers/workspace-tree/src/index.ts:416).

Dispatch order matters. Before the dispatcher, POST /mcp verifies a bearer, resolves a WorkOS-linked account and active connection, rejects suspended accounts, and applies a per-user rate limit (stack/workers/frontend-router/src/agent/caller.ts:150). The dispatcher then coerces top-level JSON-string arguments, parses Zod, checks connection permission, applies per-connection rate limit, computes live exposure, checks entitlement, checks keyed replay, asks approval for publish/destroy, runs, and audits non-reads (stack/workers/frontend-router/src/agent/dispatch.ts:15). Reads run before the non-read audit/replay/entitlement branch (stack/workers/frontend-router/src/agent/dispatch.ts:70). Browser entitlement runs as middleware on /api by HTTP method and exit path, before handlers (stack/workers/frontend-router/src/routes.ts:407, stack/workers/frontend-router/src/trial-wall.ts:191).

The agent has two extra consistency systems that browser routes do not derive from an operation: agent_actions replay keys and agent_approvals facts. The audit insert happens after the side effect and outside the store batch (stack/workers/frontend-router/src/agent/audit.ts:54). A crash in that interval can leave an effect without its replay record. Uploads are especially distinct: the uploadId is encoded client-held data, not a server approval or grant, and finish relies on the underlying routes to check it (stack/workers/frontend-router/src/agent/ops-uploads.ts:30). These are material seams for any one-definition design.
