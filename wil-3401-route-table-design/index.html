Route table and Env parse: design for sign-off

WIL-3401  |  2 October 2026  |  code read at origin/main acf3e023  |  evidence: 1 Oct architecture audit, error classes 1 and 2

This is the design pass WIL-3401 requires before any code. Nothing here has shipped. It proposes one route table that owns dispatch order, method checks, audience, trial-wall policy, origin policy and rate tier per route, and one parse of Env into typed capabilities. It ends with a migration order where every step is independently verifiable, and a short list of decisions I need from you.

The problem, measured

Five files decide routing policy today, and none of them can see the others:

This drifts in production, not in theory. Three origin-guard fixes shipped on 1 October alone: b27ecdf3 (the guard refused the public page's own lead and password forms), 17628f38 (Resend webhook missing from the exemption set), c1ab6814 (Mux webhook missing from the same set). Each was found by a failure, not by review, because adding a route does not force choosing a policy anywhere.

The same shape of problem exists for configuration. Env declares 41 optional fields in router-env.ts, more arrive through intersected module types, and 329 source lines read env.UPPER_CASE ad hoc. Each handler re-decides what a missing binding means, and the answers differ: /auth/me answers 503, the trial wall silently lets everyone through (trial-wall.ts:65-67), session resolution reports "not signed in" (auth-session.ts:369-371). The misdiagnosis the ticket names: if (!env.LIBRARY) answers "Workspace tree service is not configured" (index.ts:702-708), but LIBRARY exists whenever PAGE_LIBRARY_DB is bound (workspace-tree-in-process.ts:18-20). When Mux credentials are the missing piece, the 503 blames the wrong subsystem and the operator searches the wrong config.

One more cost the table removes: the wall resolves the session, then the destination handler resolves it again, so every guarded request pays the D1 identity read twice (trial-wall.ts:73, then for example contacts-api.ts:60).

The row type

type Method = 'GET' | 'HEAD' | 'POST' | 'PUT' | 'PATCH' | 'DELETE';

type RouteMatch =
  | { kind: 'exact'; path: string }
  | { kind: 'prefix'; path: string }                  // '/api/tree'
  | { kind: 'pattern'; pattern: RegExp };             // named groups become params

type RateTier = { tier: 'standard' | 'strict'; scope: string } | 'none';
// standard = 60/min per key, strict = 10/min, the two existing Cloudflare
// bindings. scope keys the counter so routes cannot drain each other.

type OriginPolicy =
  | 'same-origin'        // cross-origin mutations answer 403 (the default)
  | 'provider-signature' // webhook authenticates its raw body; origin ignored
  | 'app-cors';          // same-origin plus the one local-dev origin list

type WallPolicy =
  | 'open'       // never walled: public web, auth, infrastructure
  | 'reads-open' // walled account may GET/HEAD; writes answer 402
  | 'exit'       // reachable while walled: claim, checkout, takedowns
  | 'gated';     // every method walled (shell rows redirect, API rows 402)

type RouteRow = {
  name: string;                      // unique; used by logs, tests, telemetry
  match: RouteMatch;
  methods: readonly Method[];        // dispatcher answers 405 + Allow
  audience: 'anyone' | 'account' | 'staff' | 'provider';
  wall: WallPolicy;
  origin: OriginPolicy;
  rate: RateTier;
  surface: 'api' | 'html';           // wall style, 404 shape, frame headers
  handle: (ctx: RouteContext) => Promise<Response>;
};

Two deliberate choices. First, the table stays ordered and dispatch takes the first match, exactly today's rule, so the characterization suite (step 0 below) stays meaningful and no specificity algorithm needs inventing. A table test flags a row that an earlier prefix row shadows. Second, audience and wall stay separate columns: audience is an authentication question (who may call at all), the wall is an entitlement question (what a signed-in but lapsed account may still do). Collapsing them is what today's code does implicitly, and it is why the wall needs its own path lists.

RouteContext carries the request, URL, matched params, the parsed capabilities, and, for account and staff rows, the identity the dispatcher already resolved once. In the real code the row type refines per audience (a discriminated union) so a provider row cannot carry a wall policy and an account handler receives a non-optional identity. The sketch above shows the columns; the union is an implementation detail the first PR fixes in types.

OPTIONS is absent from the methods column on purpose: the dispatcher answers preflights centrally from the origin column, which deletes every per-handler OPTIONS branch. The media-signing and Sentry wrappers stay exactly where they are; the table replaces only the chain inside router.fetch.

The rate column, and the gap it closes

Today a rate tier exists only where a module author remembered one: the auth table, the contact form, and a per-email check inside WorkOS authentication. Four files total. Every anonymous write surface a prospect can reach outside those files carries no tier. The column makes that a decision each row states. The new tiers reuse the two existing Cloudflare bindings with scoped keys, so wave 4 needs no wrangler change, and the per-isolate fallback floor in rate-limit.ts keeps covering environments without bindings. Specific thresholds are a tuning question; the design point is that "none" becomes something a reviewer sees in a diff instead of an absence.

What derives from the table

Dispatch. A ~100-line interpreter: find the first matching row, answer 405 with Allow if the method is absent, answer OPTIONS from the origin column, apply the origin guard, resolve identity once if the audience needs it, evaluate the wall from the wall column, check the rate column, then call the handler with a typed context. No handler re-checks any of this.

The trial wall. maybeEnforceTrialWall keeps its entitlement logic (the D1 read, the Stripe re-check from WIL-3327, suspension) and loses all path knowledge: its input becomes the matched row's wall policy plus the resolved identity. The five path lists in trial-wall.ts and the positional "everything below this line is the app" comment in index.ts:185-187 are deleted. A new route cannot land on the wrong side of the wall because there is no side, only a required column.

The origin guard. rejectCrossOriginMutation stops consulting PROVIDER_CALLBACK_PATHS and reads the matched row's origin policy. Adding a webhook forces writing provider-signature in the row, which is exactly the decision the two 1 Oct fixes added after the fact. A table test asserts every provider-signature row's handler verifies a signature.

CORS and local origins. One constant owns the local-dev origin list; the CORS builder and the guard both read it, with the guard accepting those origins only when the deployment is not production. That closes the ticket's "they disagree about local origins" finding with one deliberate rule instead of three accidental ones.

Security headers. withSecurityHeaders keeps running response-wide and reads the matched row's surface to decide frame denial, instead of re-deriving shell-ness from isAppShellRoute.

Parse Env once

One module parses raw Env into capability groups, once per isolate, pure string checks, no I/O. Each group is a discriminated union, so a handler cannot read a secret without the compiler asking what happens when the group is unconfigured:

type Unconfigured = { configured: false; missing: readonly string[] };

type Capabilities = {
  assets: AssetsFetcher;                        // required; absent fails loudly
  build: { sha?: string; short?: string; branch?: string };
  auth: { db: D1Database; cookieSecret: string } | Unconfigured;
  workos: { apiKey: string; clientId: string; redirectUri: string;
            baseUrl?: string; dashboardEnvironmentId?: string;
            impersonationReturnSecret?: string } | Unconfigured;
  library: { db: D1Database;
             mux: { tokenId: string; tokenSecret: string } | Unconfigured;
             webhookSecret?: string } | Unconfigured;
  email: { db: D1Database; resendKey: string; sender: string;
           webhookSecret?: string; logoUrl?: string } | Unconfigured;
  publicPages: { db: D1Database; unlockSecret?: string } | Unconfigured;
  stripe: { secretKey: string; webhookSecret: string;
            prices: { monthly?: string; annual?: string } } | Unconfigured;
  stats: { db: VideoStatsDatabase } | Unconfigured;
  mediaSigning: { secret: string; ttlSeconds?: number; bucketSeconds?: number } | Unconfigured;
  r2Media: R2MediaBinding | Unconfigured;
  ai: { openaiKey: string; gateway?: { id: string; token: string } } | Unconfigured;
  analytics: PostHogDestination | Unconfigured;   // environment stays per-request
  rate: { lookup?: RateLimiter; strict?: RateLimiter };  // absent = fallback floor
  contactRecipient?: string;
  boardroomOrganizationId?: string;
};

Consequences worth the change on their own:

  • 503s name the real missing thing. The library capability is configured when the database binding exists; whether Mux calls can work is its own sub-capability. The tree route's failure message stops blaming the workspace tree when the missing piece is a Mux token.
  • Fail-open becomes a registry, not an accident. Every place a policy is skipped because a capability is unconfigured goes through one failOpen(name) helper that logs and counts. The ticket's worst case today: the trial wall waves everyone through on a missing binding with no log and no counter. The registry is a short list in code; a test asserts no other fail-open exists.
  • Expectations per environment. The parser takes the deployment environment and a required-capability set for it (production requires auth, workos, library.mux, email, stripe, publicPages, mediaSigning, stats, rate; previews require less, in line with preview email being off). A violation reports to Sentry once per isolate, and /__deploy-info gains a capabilities list of configured group names, values never included, so a bad deploy is visible in the first curl instead of the first customer 503.
  • Test fakes stop being env fields. LIBRARY and MAILER leave Env; tests hand typed fakes to the parse (parseCapabilities(env, { library, mailer })), which also deletes the per-request env shallow-copy at index.ts:121-126. The per-request analytics environment string moves into the route context, where request-scoped values belong.

Migration order, one verifiable unit per step

The mechanism that keeps every wave safe: the table-first dispatcher falls through to the untouched legacy chain for routes not yet in the table. Both exist until wave 7. Reverting a wave is reverting one PR; its routes fall back to the chain.

  1. Wave 0: characterization suite. The inventory above, times four identities (anonymous, entitled, lapsed, suspended), times the interesting methods, snapshotting status, Allow, Location, cache and access headers. Lives with the existing router tests, runs under root pnpm test. Unit: the suite is green against main before anything moves. This is the step the ticket demanded, and every later wave's definition of done is "characterization diff empty except the lines the PR names".
  2. Wave 1: interpreter plus infrastructure rows (4 routes), and the capabilities parser landing alongside. Unit: suite green, preview curl of /__deploy-info shows the capabilities list.
  3. Wave 2: provider webhooks. Deletes PROVIDER_CALLBACK_PATHS. Unit: existing webhook signature tests green, table invariant test added, suite diff empty.
  4. Wave 3: the auth group. Absorbs the 13-row table, centralizes OPTIONS, 405 and CORS, unifies the local-origin rule. Unit: suite diff is exactly the local-origin lines, auth rate-limit tests green.
  5. Wave 4: public prospect surfaces. Adds the new rate tiers. Unit: new 429 tests per scope red-to-green; a preview loop proves a tier fires; suite diff is the tier lines plus the two method tightenings.
  6. Wave 5: app API and staff rows. Wall derivation switches on; wall exits become rows; the dispatcher's single identity resolution replaces each handler's own. Unit: the wall matrix in the suite, plus a fake-D1 call-count test proving one identity read per request where today there are two.
  7. Wave 6: tombstones, shell, wall page, assets. Security headers read the row surface. Unit: suite diff is exactly the 402-to-410 tombstone lines; frame-header tests green.
  8. Wave 7: delete the legacy chain and the ad-hoc env guards; add the lint rule that keeps env. reads inside the parser, the same pattern as the existing CF-Connecting-IP lint. Unit: lint green, grep for env.UPPER_CASE outside the parser returns zero, suite green at the final head.

What this deletes

  • The 206-line ordered chain in index.ts:115-321 and its positional-order comments.
  • About 15 is*Request path predicates spread across modules; the audit counts 47 path-matching condition lines across index, auth and Stripe dispatch.
  • All five path lists and both wall-exit regexes in trial-wall.ts (~60 lines), leaving a pure entitlement module.
  • PROVIDER_CALLBACK_PATHS and the isAppShellRoute re-derivation in security-headers.ts.
  • The auth group's private dispatch plumbing and every per-handler OPTIONS, 405, CORS and not-configured block; handleMeRequest alone carries about 30 lines of it.
  • The duplicate local-origin list in auth-session.ts:1911-1915.
  • One of the two session resolutions per guarded request, a D1 read on every guarded call.
  • The ad-hoc binding guards behind 329 env.UPPER_CASE reads, replaced by typed capability reads; divergent 503 texts collapse into messages the parser derives from the missing field names.
  • The per-request env shallow-copy and the LIBRARY/MAILER test-injection env fields.

Deliberate behavior changes

Everything else is bit-identical under the characterization suite. These five change, each visible as a named diff in its wave's PR:

  1. Anonymous public writes gain rate tiers (page forms, page events, RUM events, video events and portions).
  2. /__deploy-info, /api/analytics/config and the root redirect answer only their listed methods.
  3. Retired API paths answer 410 to walled accounts too; today the wall answers 402 before the tombstone.
  4. One local-origin rule everywhere, with local dev origins accepted only off production.
  5. Wall fail-open on missing configuration still fails open but is logged and counted.

Alternatives I considered and dropped

Guardrails over the existing chain: a lint for chain length, a wall test matrix, no structural change. Cheapest, and it leaves five deciders in five files; the origin-guard incidents happened in code that was reviewed and tested. The failure class is "adding a route does not force a policy decision", and only a required column removes it.

A router framework (Hono or similar): solves path matching, which is not the problem, and brings its own ordering semantics, which is. Audience, wall, origin and rate columns are Clarity's domain; no framework carries them, so the policy work remains while the dependency and the characterization-parity risk are added.

Per-group middleware composition: policy as code again, readable only by executing the composition in your head, and invariant tests like "every provider row authenticates a signature" cannot be written against it. The table is data; tests can query it.

Decisions I need from you

  1. The five deliberate behavior changes above: any you want out of scope?
  2. Public-write tiers: fine to reuse the existing standard binding with scoped keys, or do you want a third binding with its own threshold before wave 4?
  3. First-match-wins ordered table, pinned by tests: agreed, or do you want specificity ranking?
  4. The staff column answers 404 or 403 for non-staff accounts: today's per-handler behavior varies; pick one.
  5. Wave ordering: webhooks early (wave 2) touches the scariest routes with the strongest existing tests. If you would rather see two boring waves land first, 2 and 4 can swap.
