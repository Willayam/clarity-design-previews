Staging has drifted from production

Audit run 2026-09-29, read-only. Prod clarity.video, staging staging.clarity.video. Counts are aggregate queries against each environment's D1 databases and the Cloudflare API. No customer content was copied.

The short version. Staging code matches main today, but only because someone put it back at 11:12 UTC. Staging data stopped tracking production in May. Every one-shot data job since then ran on production only: the Journey Page block backfill in July, the account reconciliation, and the Mux re-ingest last week. So staging still carries shapes production no longer has, and it lacks shapes production is full of.

  • 750 of staging's 1,636 videos (46%) have no Mux asset. Production has 67 of 7,497, and only 10 of those are real videos. Staging's re-ingest never ran: 1 staging video carries mux_reingest_asset_id, against 1,322 on production.
  • 5,330 of staging's 5,807 live Journey Pages (92%) are still schema v1 documents. The v1 renderer was deleted on 2026-07-07, so all 5,283 public routes to them answer 503 v1_document_unsupported. Production has zero v1 pages.
  • The shape the trim fix needed is missing on staging. 807 production Mux videos carry the legacy trim_start/trim_end pair; staging has none. Staging's 760 old-app imports point at production's Mux assets, while staging's own token belongs to the Mux "Spike" environment.
  • Staging is a branch sandbox, not a pre-production copy. In September, 106 of 116 staging router uploads came from 46 different branches. A push to main never deploys staging.
  • Branch migrations have landed on staging and never reached main: 1 on the workspace tree database, 3 on the auth database. Production has 1 stray migration of its own.

4. Deployed code

  • At the time of the audit, both routers' /__deploy-info reported 296ea631, the current main.
  • From 2026-09-28 23:16 to 2026-09-29 11:12 UTC, staging ran verify/wil-3441-staging, a merge of three fix branches.
  • September staging router uploads: 116 in total. 106 came from 46 branches, 5 from main, and 5 carry no annotation.
  • Deploys of the workspace tree, R2 media and auth email Workers carry no commit annotation in either environment, so nothing records which commit they run. Staging's R2 media and auth email were last deployed on 2026-09-25, production's on 2026-09-29.
  • Stray Workers still on the account: clarity-frontend, clarity-frontend-production, clarity-frontend-staging, clarity-workspace-tree, editor-app-staging, workos-cutover-plan, clarity-ai-generate, tony and clarity-cloudfront-proxy, plus 39 PR preview pairs. The media-artifact-producer Workers are gone from both environments.

5. Process

  • A push to main deploys production only. Staging deploys through a manual workflow dispatch from any branch (108 runs so far) or a local just deploy-stack-staging. Nothing puts staging back on main afterwards.
  • deploy-stack-staging applies migrations from whatever branch is being deployed. That's how the 4 branch migrations got onto staging.
  • Nothing seeds or refreshes staging data. There's no seed, snapshot or parity tooling in the repo. Both environments got the same legacy import in May: 1,721 production users and 1,722 staging users were created that month. After that, every data job ran on one side only: the Journey Page v1 to v2 backfill, the account reconciliation and the Mux re-ingest on production, and the branch backfills on staging.
  • The staging critical e2e records real videos on every staging deploy. That explains the 376 source-less September videos.

Not checked

  • Convex function and schema parity. There's no Convex deploy key in this shell.
  • WorkOS environment settings. There's no WorkOS key in this shell.
  • The Stripe mode and the Mux environment of the actual secret values. Secrets are readable by name only. These rows rely on the runbook and the verify-loop doc.

Plan, ranked by value per effort

My opinion is that staging should be production-shaped and follow main. Branch verification can still borrow it, but it has to be handed back. Re-ingesting staging's dead videos into Spike would spend Mux encoding on test data that doesn't look like production anyway. Delete it, then seed the shapes production actually has.

  1. Put staging back on main automatically. Shigh
    Run the staging stack deploy on every push to main, after production. Also run it on a nightly schedule so a branch build can't sit there for more than a day. Stamp the commit sha on the workspace tree, R2 media and auth email uploads the way the router already does, so each Worker's version can be traced to a commit.
  2. Delete the shapes production no longer has. S to Mhigh
    Export a backup first. Then soft-delete staging's 750 R2-only video nodes, and the 5,330 v1 Journey Pages with their 5,283 routes. Keep a handful of R2 videos that mirror production's 10 re-ingest exceptions, because production still has that shape. Staging writes are destructive, so this needs William's approval first.
  3. Parity check recipe on a schedule. Mhigh
    Add just env-parity, run daily in GitHub Actions like Cost Watch, with a red run as the alarm. It diffs applied migrations and DDL for every database, secret names per Worker pair, each Worker's deploy annotation against main, and a shape catalog of the video, page, user and subscription classes in this report. It flags any shape production has at least 10 of that staging lacks, and any staging shape production has none of. Read-only by construction.
  4. Generate a shape fixture workspace from production counts. M to Lhigh
    A script reads the parity catalog and builds one staging test workspace with at least one node per production shape. For videos that means an old-app import with the legacy trim pair, source-trim only, thumbnail_url posters, a manifest with a Mux clip, a transcript, an R2 exception and a pending shell. For pages it means every block kind, theme presets and a page listed in more than one workspace. The Mux assets are created in Spike so edits work. This replaces the hand-copying WIL-3441 needed.
  5. Stop branch migrations landing on staging unseen. Smedium
    deploy-stack-staging should refuse a migration that isn't on origin/main unless it gets an explicit flag, and should log what it applied. Then reconcile today's strays: staging's workspace tree 0019 and 3 auth migrations, and production's 0004_journey_page_preview_url.
  6. Scrub real customer data from staging. Mmedium
    Staging holds 2,401 real legacy accounts, 163 live Stripe subscription ids and copied view history. That's a privacy exposure rather than a fidelity problem, so it ranks last here. Pseudonymise or delete these once the fixture workspace from item 4 exists.
