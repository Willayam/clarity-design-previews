Agents on Clarity

A recommended design for letting an AI agent do everything a Clarity user can do. Written 2026-09-30. Nothing here is built yet. Every decision in the last section is yours to make.

The short answer

Build one set of Clarity operations on the server, and put a remote MCP server in front of it first. Claude Code, Codex, Cursor, ChatGPT and claude.ai all connect to that one MCP server over OAuth. The clarity CLI comes second, as a client of the same operations, because it is cheaper in tokens for the agents that have a shell.

Use WorkOS for the OAuth part. AuthKit already works as the authorization server for MCP clients, and Clarity users already are WorkOS users, so an agent signs in with the same account and the same password or Google login. Clarity keeps one small table of its own that says what each connected agent may do and lets you revoke it instantly.

The surprise from walking the code is that the API mostly exists. Journey pages, the library, uploads, transcripts, publishing, stats, leads, contacts and brand all have first-party routes in the router Worker today. What is missing is narrower.

  1. No way to authenticate anything but a browser cookie.
  2. Four workflows that only the editor knows how to finish: the resumable upload, saving an AI generation to the page, applying a theme or composing blocks, and knowing when a video is ready.
  3. No guard against the editor's autosave overwriting an agent's change.
  4. Pages go live the moment they are created, which is fine for a person and risky for an agent.

The first slice that proves the whole path (local video to published page URL, from all five hosts) is about four to five engineer-weeks after a two to three day WorkOS spike.

Two findings shape everything below. Every one of those routes authenticates through one function, resolveAuthSessionContext in workers/frontend-router/src/auth-session.ts, which reads the clarity_session cookie. And the gap is smaller than feared. It is four workflows and one missing credential type, not a missing API.

control-clarity.mjs is not the seed. It is a good verification harness (Playwright, test-account logins, direct D1 writes for stats seeding, production guards). None of that belongs in a customer tool. Once the real CLI exists, verify-loop can use it for API-level checks.

Recommended design

One set of operations, three thin transports

Each capability is written once as an operation: a name, a zod input and output schema, a required permission, an effect class (read, write, publish, destructive, spend), and a function that does the work. One dispatch function runs every check in one place: permission, input validation, entitlement, spend limits, rate limit, approval, audit. Operations never branch on who is calling beyond that.

The transports hold no logic.

  • Remote MCP at clarity.video/mcp. Stateless, per the 2026-07-28 MCP spec. It exposes a curated set of about 15 workflow tools, not one tool per route. This is the only thing claude.ai, ChatGPT web and the Claude mobile apps can use, and Claude Code, Codex and Cursor speak it too.
  • An uploader. npx @clarity-video/upload <file> <upload-url>, a small Node script that runs the resumable protocol against a one-session, write-only upload URL the MCP server hands out. It has no login of its own. It is the part of the CLI that exists in the first slice.
  • The clarity CLI. Second. It fetches the operation catalog at runtime, so a new operation ships with a Worker deploy and no CLI release. It adds JSON output when stdout is not a terminal, fixed exit codes, --dry-run, and a setup command that installs a skill file for Claude Code, Codex and Cursor.

The operations live in workers/frontend-router/src/agent/. The router already holds all three D1 databases, every service binding, page persistence and the Convex token. Operations call extracted cores (a page-core.ts pulled out of journey-pages-native.ts, for example), never the router's own HTTP routes. One reviewer argued for a separate Worker so agent traffic and extra dependencies cannot affect public page rendering. I would start in the router behind a kill switch and split only if cold starts on public pages measurably regress.

Why MCP first and not the CLI first. The research is real that CLIs are cheaper in tokens and more reliable for coding agents. Scalekit measured MCP using 4 to 32 times more tokens than gh for the same GitHub tasks. But a CLI reaches only three of your five hosts, and it needs its own login path. MCP reaches all five with one OAuth path, and hosts now defer tool loading, which takes most of the token cost away at 15 tools. The one thing MCP cannot do is move a 2 GB file, and the uploader script covers that without a second auth story. Supabase found agents did best with MCP plus a skill file that explains the workflow, 71 percent task success against 58 for MCP alone, so the skill ships in the first slice too.

These ids, tool names and URLs are illustrative. The agent never pulls the transcript into its own context. pages.generate reads it server-side. The uploader runs in the background because a 2 GB upload outlives Claude Code's Bash timeout and Codex's 60 second tool limit, and it resumes from the last acknowledged part if it is rerun.

In claude.ai or ChatGPT there is no shell, so the video comes in through the person. clarity_uploads_start returns a browserUrl. The page requires the same signed-in Clarity user (no pre-authenticated links, as the MCP spec requires for URL handoffs), offers drag-and-drop and the recorder, and runs the same uploader the Library uses. From there the tool calls are identical. Import from a Drive or Dropbox link comes later, once server-side fetching has SSRF, size and timeout limits.

When something is refused, the error says what to do next.

Authentication

WorkOS AuthKit, used as the OAuth server for MCP. This is what WorkOS built for exactly this case. Clarity serves a Protected Resource Metadata document at /.well-known/oauth-protected-resource pointing at the AuthKit domain. The host discovers it on the first 401, registers itself with a Client ID Metadata Document (the MCP spec's preferred method; Dynamic Client Registration stays on for older clients), and sends the user to AuthKit's hosted login. Clarity users are already WorkOS users, and the invite flow already uses AuthKit's hosted login, so they sign in with what they have. The access token is a JWT with sub set to the WorkOS user id.

How the router checks a token. On /mcp and /api/agent/v1/* only, the router verifies the JWT locally against the AuthKit JWKS (cached), checks issuer, audience (the Clarity resource URL) and expiry, requires sub, client_id and sid, and rejects a request that carries both a bearer token and a cookie. It maps sub through the same findIdentityByWorkosUserId read the cookie path uses and refuses accounts that are not active. It then builds an Actor with only an owner id, a workspace id and a WorkOS user id. The type has no role, admin, impersonator or Stripe fields, so no operation can reach an admin path by accident. Agent tokens never go through resolveAuthSessionContext, and the existing cookie routes do not change.

What each connection may do lives in Clarity. WorkOS tokens for MCP clients carry only the OpenID scopes. The WorkOS docs say clients that register themselves "cannot have scopes assigned per client", and a user with no organization has no roles to resolve. So Clarity keeps an agent_connections row per (user, client, consent) with the permissions, status and last use, read on every request. The first call from a new connection returns an approval link to a Clarity page where you pick what it may do.

  • Read. Library, videos, transcripts, pages, stats.
  • Build. Read, plus upload, create and edit private pages, AI generation, themes and brand.
  • Leads and contacts. A separate switch, because they are other people's personal data and the most likely thing a prompt injection would try to leak.
  • Publish and delete are never standing permissions in the first release. Each one returns an approval link bound to the exact page revision and payload. You approve on a Clarity page with a POST from your own non-impersonated session, the page cannot be framed, and it shows the client's real host next to its self-declared name.

Revocation. Settings gets a Connected agents list. Revoking marks the row, which blocks the next request immediately. It also deletes the authorized application at WorkOS so refresh tokens stop working. Queued work (a generation in flight) re-checks the connection before it writes.

Audit. An agent_audit row per write, denial, approval and revocation (connection, operation, target ids, outcome, cost, request id), shown per connection in Settings. WorkOS Audit Logs require an organization.

The CLI, later. It registers like any MCP client: its own Client ID Metadata Document hosted by Clarity, authorization code with PKCE on a loopback port, the same audience, the same verifier. I dropped the WorkOS device-code flow. Its device authorization request takes no resource indicator, so CLI tokens would carry a different audience from MCP tokens, and one-click device links are a known phishing pattern. A paste-the-code page can cover SSH sessions later.

Server-side work that closes the gaps

  • Upload. The resumable protocol driver moves into packages/recording-session-protocol with a pluggable byte source and resume store. The uploader script uses it first; the editor moves onto it afterwards and its copy is deleted. A new uploads.finish step does seal, complete and accept-original in one call, keyed on the session so a retry converges.
  • AI generation is saved by the server. A Convex completion callback calls persistGeneration in the router. The generation row records the connection that started it and the page revision it started from. Persisting checks page ownership, checks the connection is still live, writes a one-time receipt per generation together with the page, and never overwrites a page that changed since the generation started (the output is kept as an unapplied draft instead). The editor's own save-and-acknowledge bridge is deleted once it uses the same path, so a closed tab no longer strands a generation.
  • Revision on every page write. journey_pages gains a revision number. Every writer sends it, including the editor's autosave, and a stale write gets a 409 with the current revision. Without this the editor silently erases an agent's theme change within a second. The editor's conflict behavior is real design work (reload, or rebase by block id) and is sized as such.
  • Jobs are views, not a table. A job id names a row that already holds the state: the upload session, the workspace-tree derivations (playable, poster, transcript), the Convex generation row, or the approval row. jobs.wait polls server-side for at most 45 seconds and returns with a retry hint. Nothing depends on the MCP Tasks extension, which no host confirms supporting yet.
  • Page operations. pages.create builds the default document with Customer Brand, pages.apply_theme runs the existing preset macros from ADR 0007, pages.edit_blocks edits by durable Block id. All read, modify and write under the revision check.
  • Undo. Each agent write keeps the previous document, so a bad theme or block edit can be rolled back.

Safety

Risk What stops it
An agent creates a page and it is instantly live Agent-created pages get a Share ID that starts disabled. Every path that activates a public link (page create, the access route, the route endpoint, the per-video share page) sits behind the publish approval for agents. Whether people's own pages should also start private is your call (roadmap WIL-3226 already asks for it).
Edits to a page that is already public Treated as publishing, so they go through approval too
Prompt injection from a transcript, lead note or contact note Those texts are written by other people. Deletes and publishing need a person. Leads and contacts are off unless you turn them on. Billing, sign-in and admin are absent from the operation list, not guarded.
Deletes Approval link bound to the exact targets, single use, 15 minute expiry. The approval page is the dry run.
Retries and crashes Creating operations take an idempotency_key argument (a tool argument, because MCP has no portable header), stored on the domain row it creates. Upload and generation converge on their natural keys.
AI spend A daily generation cap per workspace inside Convex generate.start. This is new for people too; today there is no cap.
Container and storage cost Daily upload bytes and concurrent processing jobs per workspace for agent connections
Floods A Workers rate-limit binding per connection, the same mechanism as the existing auth lookup limiter
Trial wall and Pro decideEntitlement on every write and spend operation, failing closed. Reads follow today's browser rule. Whether agent access is a paid feature is an open decision.
A bad deploy or abuse An AGENT_GATEWAY switch (off, read-only, on) that works without a deploy. The gateway is off on PR previews.

Ergonomics for the agent

  • JSON everywhere. The CLI prints JSON when stdout is not a terminal and progress as NDJSON on stderr.
  • One error shape: a stable code, a sentence the model can repeat to the user, a hint with the next action, and structured extras (permission, approvalUrl, currentRevision, retryAfterSeconds). One table maps each code to an HTTP status, a CLI exit code and an MCP error result.
  • Readable ids and names in results, bounded lists with pagination, and a concise or detailed output switch, following Anthropic's tool-writing guidance.
  • Discoverable without docs. MCP lists tools with schemas. The CLI's clarity ops and clarity describe <op> read the same catalog. The skill file explains the workflow order (upload, wait, generate, theme, request publish).

Alternatives I rejected

Surfaces

  • CLI first. Cheapest in tokens for coding agents, but it reaches three of five hosts and needs its own login. It comes second.
  • Bearer tokens on every existing route. Teach the cookie resolver to accept tokens and generate tools from the routes. It is the fastest start, and it fails three ways. Every future route becomes agent-reachable by default. Role and admin flags flow into agent calls. And the agent still has to replay the browser's upload and whole-document save protocols, which is exactly where agents fail.
  • Let the agent drive the editor. Grow control-clarity.mjs or use computer use. No remote hosts, no permissions, no reliable 2 GB upload, and every UI change breaks it.
  • Code Mode (one execute tool over a typed SDK). Right for Cloudflare's 2,500 endpoints. At about 30 operations, named tools with host tool search are cheaper to run and easier to audit.
  • A separate agent backend in Convex. Pages, media and identity live in D1 and R2 behind the router, so every Convex action would call back into the router with a second identity hop.
  • Adopt BuilderIO's agent-native framework (the pattern WIL-3245 cites). It assumes Postgres and Nitro. The idea carries over and is the core of this design: one registry of typed actions that the UI and every agent surface call.

Auth

  • Clarity runs its own OAuth server (workers-oauth-provider). Two of three designers picked this. It gives checkbox scopes on the consent page and one grant store. It also makes Clarity own token issuance, refresh rotation, registration abuse and consent security for a very small team, when WorkOS already does this and Clarity already pays for WorkOS. It stays the fallback if the spike fails.
  • WorkOS Standalone Connect (your own login page as the Login URI, with custom consent options). I proposed this in the first draft and two critics took it apart. Its completion API creates or updates users by an external id that Clarity's WorkOS users do not have, and a new id with an existing email fails. Standard AuthKit login already knows your users.
  • WorkOS API Keys. User keys require an organization membership, and validation is a remote call on every request. Useful later for headless jobs if Clarity adopts organizations.
  • WorkOS Agent Auth and Agent Registration (launched 2026-08 and 2026-09). Early access, organization-bound, and Agent Registration must be switched on by the WorkOS account team. Worth revisiting.
  • A personal WorkOS organization per user to unlock RBAC, API keys, audit logs and Agent Auth. Thousands of synthetic organizations to obtain credentials, and it collides with the real Customer Organization concept that is coming.
  • WorkOS device-code flow for the CLI. No resource indicator on the request, so a second audience to accept, plus the device phishing pattern.

The pattern is clear. WorkOS assumes a B2B shape with organizations. Clarity's workspace is one person, so WorkOS answers who the user is and Clarity answers what the agent may do. If Customer Organizations become shared workspaces, several of these open up, and only the token check changes.

Decisions for you

  1. Should agent-created pages start private until you approve publishing? I recommend yes. Should people's own pages follow (WIL-3226)?
  2. Is publishing always approved per page, or can you grant a standing "publish without asking" to an agent you trust? I recommend per-page approval for the first release.
  3. What does "put a video together" mean to you? Trim and a looping preview, the per-video share page, a Journey Page around one video, or stitching several videos into one? The last one is new product work, not an API.
  4. Is agent access a paid feature, or open to live trials under the same entitlement rule?
  5. What daily AI generation cap per workspace? It is new for people too.
  6. Directory listing. Do you want Clarity in the Claude and ChatGPT connector directories, or is adding it as a custom connector enough for now? Directory listing adds review, a privacy page and a support contact.
  7. Where should the operations live if cold starts matter? In the router behind a switch (my pick) or in a separate Worker from day one.

What I could not verify

  • Whether AuthKit MCP OAuth works end to end for a Clarity user with no organization in each of the five hosts. The docs say a token without org_id is valid; nobody has run it. This is the Phase 0 spike.
  • What deleting an authorized application at WorkOS does to access tokens already issued, and whether MCP clients registered by CIMD appear in that list.
  • Whether the consent id (sid) stays the same across refresh.
  • Connect pricing. The WorkOS pricing page lists no separate Connect line and AuthKit is free to one million monthly users, which suggests no extra cost. Not confirmed.
  • Whether any host supports the MCP Tasks extension. The design does not depend on it.
  • Host limits I took from docs, not measurements: claude.ai's 240 second tool call and 10 second OAuth endpoint limits, Codex's 60 second default tool timeout, Claude Code's 25k token result limit.
  • How Mux, the closest precedent (a video API on WorkOS for MCP auth), handles uploads through MCP. Their docs do not say.
  • The explorers traced route dispatch and key handlers, not every handler body. Sizes are estimates.

How this was made

Four gpt-6-sol explorers mapped the codebase. Two Opus researchers read current WorkOS docs and the MCP and host landscape. Three designers on Fable, gpt-6-astra and Opus each produced a full design independently. A gpt-6-astra judge scored them blind. The base came from the astra design (private creation, server-side generation saving, revision checks, Clarity-side grants on WorkOS). The operation registry, the no-role Actor and derived jobs came from the Opus design. Upload package placement and response limits came from the Fable design. Three critics (Fable, gpt-6-astra, Opus) then attacked the combined recommendation. They changed it in five places: standard AuthKit instead of Standalone Connect, no device-code flow, publishing behind approval, leads as a separate permission, and a smaller first slice that leads with MCP.
