D12

Prospect-page tracking: submits counted on the server, return visits in page stats

PR #1511

The tracking script counted a form submit when the browser fired its submit event, before the worker accepted anything, so a refused form still counted: June 2026 holds 30 submit events against 17 stored rows on customer pages. Four event types (section view, section dwell, scroll depth, return visit) were accepted and never sent; production has zero rows of each. Every visit sent viewer_id null, so a rep could not see that a prospect came back. Now the worker records the submit after it stores the row, the dead types are refused, and page stats show return visits from a per-page viewer id.

What changes (6)
  • Page stats: new fact "Return visits" beside Page visits, shown only when above zero. A return is a visit from a browser that opened the page at least 30 minutes before, counted among the latest 1,000 visits like the other figures.
  • Public page: the tracking script keeps one random id per share link in localStorage (key clarity.viewer.<shareId>) and sends it with page events. No cookie.
  • Public page: on a lead form submit the script adds a hidden page_session_id field instead of sending its own page_form_submit beacon.
  • Worker: lead-capture writes one page_form_submit event after the submission row is stored, in the visit that sent the form. A failed event write is logged and the form still succeeds.
  • Worker: POST /api/pages/events refuses page_section_view, page_section_dwell, page_return_visit and page_form_submit with 400 "event_type is not supported".
  • Agent tool pages_stats: description names returnVisits and the 30-minute rule.

Notifications: one switch, on by default, fired when they start

PR #1510

Four toggles decided which watch milestones emailed the rep, and only 'watched 60%' was on by default. So a prospect starting to watch sent nothing, and a button click never sent anything. 93% of customers never touched the toggles and nobody has changed one in the new app (D6 brief). Now one switch, on by default, sends an email when a prospect starts watching, then at most one an hour saying how far they got and which buttons they clicked.

Recorder: automatic trim with one Restore link, edit modal saves as you go

PR #1517

Trimming was a three-way choice (Auto, Custom, None) that 6 users ever made, and a video with no automatic trim had no way back except dragging a handle to the edge. The edit modal saved only on Done and threw the edit away on Esc, while the recorder saved as you went. Now the automatic trim lands on the handles with nothing to choose, one "Restore full video" link undoes any trim, and the modal saves like the recorder.

What changes (5)
  • Recorder finish screen and edit modal: the Auto / Custom / None group is removed; "Restore full video" shows in its place while the video is trimmed
  • Edit modal: Cancel is removed; each edit saves 700 ms after the rep lets go, with "Saving…" then "Saved" next to Done
  • Edit modal: Esc and a click outside now save and close, like Done (before, they dropped the edit)
  • Edit modal: after a failed save, "Couldn't save changes." with Try again stays; Esc or a click outside then closes without the save
  • The four recording layouts are unchanged

Risks

  • While the automatic trim is still pending there is nothing to restore, so a rep can no longer choose None in advance; they wait for the trim to land, then restore. The pending spinner on Auto is gone with the button.
