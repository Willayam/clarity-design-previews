Design review · 2 October 2026 · No production changes

Render the first page once, then show an image

Recommendation

Keep the current card appearance and PDF.js renderer. Generate a small thumbnail during upload, store it privately, and display it through the existing signed image preview path. Backfill existing documents and provide a repair path for missing previews.

This removes PDF parsing from ordinary library browsing without introducing a separate rendering service. Thumbnail generation must never prevent a valid document from being uploaded or opened.

Why revise the current implementation

  1. Partial downloads do not work across the current media origin. PDF.js requires browser-readable range headers, but the media response does not expose them through CORS. The current settings therefore do not prevent full-document downloads. CORS header exposure and PDF.js loading options.
  2. Rendering repeats on later visits. The rendered page lives only in its mounted canvas. Reopening a folder or receiving a newly signed URL can discard it and repeat the work.
  3. Visibility is not a concurrency limit. Every visible card can start its own PDF worker. The existing checks establish correctness on small fixtures, not performance with a folder of large PDFs.
  4. Failures need diagnosis. A broken file and a network or deployment error currently produce the same silent icon fallback. Record the outcome without recording signed URLs or document content.

Constraints to preserve

  • Store previews in a private image namespace, authorize them through the document, and bind them to the immutable source.
  • Keep the existing signed-URL refresh. Do not weaken generic metadata-write protections to attach thumbnails.
  • Backfill existing PDFs with a resumable operation that reports missing, encrypted and unreadable sources.
  • Keep the document usable if preview generation fails. A repair operation must cover future interruptions, not only the initial backfill.

Evidence and limits

The existing browser verification rendered square and portrait PDFs through the real PDF.js worker in both card layouts at desktop and phone viewport sizes. It checked visible page pixels, fonts, proportions, opening and unreadable-file fallback. API records were mocked. Successful isolated rendering had no console errors.

Those checks did not establish large-file performance on a physical phone or validate the proposed thumbnail upload and storage flow. Before shipping, verify those paths on staging, including unauthorized thumbnail requests and an interrupted upload.

Source review found no deployed PDF rendering queue or service to reuse. The current image upload and signed preview paths can be extended, but this still requires backend validation and metadata changes.

Review synthesis

Fable 5.1, Opus 5.5 and GPT-6-Astra independently rejected the current implementation unchanged. Fable and Opus recommended persisted browser-generated thumbnails. Astra initially favored bounded browser rendering, then preferred persisted thumbnails after checking reuse of the existing private-image upload and signing paths.

All three identified the range-header problem and repeated rendering. The lead recommendation is an explicit resumable backfill for existing documents, rather than relying only on someone opening each old file. Total backfill bytes remain unmeasured.
