How to read this

One box is one unit of work. Every box names the evidence that checks it. A nested box is a sub-step of the box above it. Check a box only when its evidence exists, a file, a log line, a screenshot, a test run, or a SHA. The body is a how-to. The appendices explain and record.

The program runs skills/poteto-mode/playbooks/autopilot-full.md under the installed plugin. Sequenced work is merge-then-branch. Every PR targets main and never stacks, because stacked PRs get no CI in this repo. Every merge deploys production, so every merge is an operator gate. Owners stop at merge-ready and William clicks merge, unless William grants landing authority in chat. P0 is the exception. It is a scratch PR that is closed, never merged, after its evidence is captured.

Pre-merge proof works because pull_request events run the workflow file from the PR's own merge ref. Labeling a PR with deploy-preview therefore exercises its own workflow and script edits with secrets, and workflow_dispatch --ref <branch> runs that ref's workflow file. A scratch commit that exercises a path the diff does not trigger is pushed, observed in the run log, then dropped before review.

Two driver skills carry the live lanes. CI and deploy-script lanes use the run skill (gh run view --log, curl .../__deploy-info, read-only wrangler d1 execute, node scripts). Browser lanes against https://pr-<n>.clarity-video.workers.dev use the verify skill and the repo's verify-loop CLI (.agents/skills/verify-loop/cli/control-clarity.mjs). A CLI lane's screenshot is a saved terminal capture or log excerpt as the named .png, with the raw text kept beside it as <slug>.txt.

Tests alone are not sufficient verification. A PR is verified only when its unit, live, and perf boxes are all checked.

Appendix B. Alternatives rejected

These are the synthesis's decisions; this plan does not reopen them.

  • Two preview databases per PR (B's shape). Production keeps email separate (wrangler.jsonc lines 207-212); three per PR match it for little added cost.
  • Checked-in preview database ids. The id-less template makes the resolver the only id source; nothing a reader pastes into the repo can bind.
  • Recreate databases on every deploy (A). Loses reviewer QA state and pays the cold apply per push; drift-driven recreate preserves both.
  • Immutable database generations (D). More machinery than the fingerprint table needs.
  • PR-prefix enforcement inside r2-media (C, D). Preview data is synthetic, keys are unguessable owner and uuid paths, and prefix logic touches production media code paths for no observable isolation gain.
  • A docs-only redeploy skip. The judge's correction stands, a base-to-head diff cannot tell whether the latest push was docs-only on a code-changing PR.
  • A staging lease, as an application D1 table (A) or otherwise. After P8 staging has one claimant; follow-main's busy check stays; a lease arbitrates nothing.
  • Staging before production on main pushes (D). Adds roughly 10 minutes to every release; a separate decision for William; filed as a follow-on at close.
  • Seeding previews from staging exports. Real addresses, out-of-repo child tables, and yesterday's schema; the fixtures script is versioned with the code.
  • Per-PR R2 buckets. One shared clarity-media-preview with a 14-day lifecycle rule; per-PR databases already make foreign object keys unreachable.
  • A shared preview media Worker kept current from main (B). Per-PR Workers built from the branch are one mechanism and preview branch media code.
  • Per-PR Mux webhooks. Ingest settles on read (workers/workspace-tree/src/mux-video-ingest.ts); previews need no webhook delivery.
  • PostHog on previews. Never; the generator deletes the token and the P1 allowlist enforces its absence.
  • Stripe test keys, email capture, and a preview cron endpoint inside this program. Follow-ons, filed at close.
