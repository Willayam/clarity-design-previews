Render once. Store the image.

The upload renders the first page with PDF.js and attaches an owner-validated image to the original document. Browsing uses the existing signed-image path.

The 3,148,083-byte synthetic PDF produced an 11,834-byte WebP. This is one local observation, not a performance benchmark.

What the local run proved.

  • Uploaded previews remained attached after reload. Repeated attachment was idempotent; wrong-owner and mismatched-source requests failed.
  • All six browsing checks fetched images without fetching a PDF, PDF.js, or its worker.
  • Invalid PDFs and refused thumbnail uploads retained their original files. Rename and Open continued to work.
  • The real backfill renderer and attachment code passed dry-run, apply, and repeat checks with SQLite and a local storage substitute.
  • The built renderer passed Chromium, Firefox, and WebKit checks. Japanese font mapping assets loaded successfully.

Verification boundaries.

The browser run used actual upload, render, card, Library API, signing, and SQLite code. Identity, upload storage, and the surrounding application shell were local substitutes. No customer data or production services were used.

Real D1 HTTP and R2 operation, deployed module-worker MIME handling, authenticated full-router behavior, physical phones, and customer PDFs still need a staging check. No deployment or live backfill was performed.
