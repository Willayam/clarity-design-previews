Clarity and agent-native: audit and rebuild question

Date 2026-10-14. Clarity at main e839a6bd5. agent-native clone at 459b1eb. Read-only; nothing was built or run. Version 2, revised after two independent critics reviewed version 1 (section 8).

1. Summary

Do not rebuild Clarity on agent-native. The case is stronger than "it would cost too much". agent-native is a Postgres-only, Node-oriented application kit. Its core alone is 5.4 times the size of all of Clarity (measured, 596,520 against about 110,000 non-test lines). It has no replacement for the parts of Clarity that are the product, which are the block page model, the public edge renderer, Mux playback and the recorder. The parts it would replace, meaning routing, auth, an action registry and an MCP door, are the parts Clarity has already built, and Clarity's versions fit Cloudflare Workers, D1, WorkOS and Stripe, which agent-native does not. A rebuild would hand back 4 to 13% of today's functionality, none of it drop-in, for 4 to 9 engineer-months of all capacity.

What agent-native does get right is one idea, and Clarity can take the idea without taking any of the code. The idea is a single capability registry that both the UI and agents call. Clarity has the registry already, defineOperation in workers/frontend-router/src/agent/operation.ts, but only the MCP door calls it, and the editor still calls 92 separate /api routes. Making defineOperation the one registry the editor also calls is the real simplification William is asking about. It deletes a second copy of the product's capabilities instead of adding a framework on top of both. Everything else worth taking is a repository convention or a product idea.

What to do next.

  1. Let agent/dispatch.ts accept a session caller, then move the editor's read and write app-data routes onto operations one PR at a time, with a parity guard whose baseline exempts admin, billing, webhooks, auth callbacks and connection management.
  2. Finish human approval in the agent door, which agent/operation.ts:8 defers to "PR 5", before any publish or destroy operation becomes reachable by an agent. The editor's own calls need no approval step, because the signed-in person is the human.
  3. Emit $mcp_* usage events to PostHog from agent/mcp.ts. About a day.
  4. Add a no-silent-coercion ESLint rule baselined with eslint-suppressions.json.
  5. Check the hot D1 queries with EXPLAIN QUERY PLAN and an index review, and write the three-outcome exit code convention down for new check scripts.

2. What agent-native is

agent-native is Builder.io's framework for "agent-native" web apps, where an in-app AI agent and the UI call the same action layer. It is a monorepo of a core framework, a UI toolkit, a protocol package and about a dozen product templates (clips, analytics, forms, crm, content, design, slides, mail, plan, calendar, dispatch).

Architecture, read in code.

  • Actions. defineAction in agent-native: packages/core/src/action.ts:597-610 takes a schema, a description and run. Its options cover HTTP exposure, agent and MCP visibility, approval, authorization, change events, caching and audit (action.ts:368-489). Build discovery mounts HTTP routes for actions/ files (packages/core/src/deploy/route-discovery.ts:326-380); React calls them through useActionQuery and useActionMutation (packages/core/src/client/use-action.ts).
  • Agent runtime. A server run loop with tool execution, approvals and resumable runs (packages/core/src/agent/run-loop-with-resume.ts, agent/production-agent.ts, the latter 13,674 lines in one file). Engines for Anthropic direct, Vercel AI SDK adapters, OpenRouter and a Builder.io gateway.
  • Application state. Navigation and selection stored per session in a SQL table so the agent can see what the user is looking at (packages/core/src/application-state/store.ts:20-60).
  • Runtime. Nitro 3 and H3 on the server, React Router 8 on the client, Node 22.22 or newer. Build presets for Netlify, Vercel, Node and cloudflare_module; Cloudflare Pages is rejected (packages/core/src/deploy/build.ts:6587-6595). About 110 files in packages/core/src import fs or child_process (grep, tests excluded), so the Workers preset would have to tree-shake or shim all of them. Their own sites deploy to Netlify via prebuilt artifacts.
  • Database. Postgres or PGlite only. packages/core/src/db/client.ts:1801-1803 throws on any other DATABASE_URL scheme. Zero references to D1Database anywhere in packages/core/src (grep). Drizzle's Postgres builder; AGENTS.md says "keep schemas PostgreSQL-specific".
  • Auth. Better Auth plus optional SSO and SCIM (server/better-auth-instance.ts:983). No WorkOS anywhere in core.
  • Storage and email. S3 and R2 for files, Resend or SendGrid for mail. Stripe appears only as a generic provider-API catalog entry; there is no billing or entitlement module.
  • Packaging. @agent-native/agentkit is the conversation protocol plus a headless client with one runtime dependency (packages/agentkit/package.json). Its README says agent execution stays outside the package, so the run loop is yours to write. The chat UI lives in @agent-native/toolkit, which has 88 dependencies, 27 of them @radix-ui packages, and requires react-router ^8.1 as a peer (measured from packages/toolkit/package.json). Clarity's editor is on @base-ui/react and react-router-dom ^7.18 (editor/package.json:14,37).
  • Conventions. AGENTS.md (383 lines) states the invariants and points to 87 SKILL.md files under .agents/skills. 81 non-test guard scripts under scripts/guard-* (42 .mjs, 39 .ts; measured). Guards are meant to report three outcomes, exit 0 passed, 1 failed, 2 could not run, and the diff-scoped ones refuse to pass when they cannot find the base ref (scripts/lib/changed-lines.mjs:52-70). Only about 25 of the 81 use exit code 2 or requireAddedLines (grep), so the convention is partial even at home. Formatting is oxfmt and oxlint. Releases go through Changesets.

Maturity and licence, measured. 7,169 stars, 653 forks, 85 open issues, created 2026-03-12, pushed 2026-10-14. 7,422 commits since creation, 2,032 of them in the 30 days to 2026-10-14 from 43 authors, 1,414 of those by Steve Sewell (Builder.io's CEO). packages/core/package.json says 0.208.0 while its CHANGELOG opens with an unreconciled 1.0.0 entry, and the 0.x changelog lists breaking splits. There is no LICENSE file at the root; the root package says ISC, the 17 publishable packages say MIT. Builder.io gateway credentials are wired into core as one of several model paths (packages/core/src/server/credential-provider.ts:2275-2304). At that commit rate on a 0.x line, any runtime dependency on agent-native needs an exact version pin and a named upgrade owner (inferred from the changelog's breaking entries).

Templates that touch Clarity's domain, read in code. templates/clips is a Loom-like product (1,345 ts, tsx and rs files) with a browser recorder, a Chrome extension, a Tauri desktop app, resumable chunk uploads with leases, ffmpeg thumbnails, Builder or S3 storage, and an MP4 or WebM <video> player behind a same-origin Range proxy (templates/clips/server/routes/api/video/[recordingId].get.ts, app/components/player/video-player.tsx:603-614). It does not use Mux and has no HLS path. Transcription runs through a Builder-managed service, and cleanup through a Builder model or a bring-your-own Gemini key (templates/clips/actions/request-transcript.ts:944-965, cleanup-transcript.ts:64-70), so those gains are not free either. templates/videos is retired. templates/forms, templates/analytics and templates/crm are standalone apps, covered in section 7.

Where complexity and duplication live, read in code.

  • Two renderers of the same block document. The editor preview (editor/src/components/editor/LivePreview.tsx 980) and the public Worker renderer (public-page-delivery/render-blocks.ts 748) share the registry, theme maths and CSS but not block markup. editor/tests/block-rendering-parity.test.ts limits drift; it does not remove the second copy.
  • Two OpenAI call paths. journey-page-model.ts:74-97 goes through AI Gateway with a direct fallback; packages/ai/src/providers/openai.ts is a separate task route.
  • Legacy fields carried alongside the v2 schema in packages/journey-page-domain/src/blocks.ts:49-73,203-205, retired poster fields in served-file-policy/src/index.ts:102-168, and old metadata reads in video-row.ts:603-612.
  • Two capability registries. routes.ts names 92 distinct /api path strings (measured; includes wildcards and near-duplicates) and the Library adds 16 TREE_ROUTES patterns, while the agent registry exposes 9 operations (agent/registry.ts:12). Of the 92, 20 are /api/admin, 13 are billing or Stripe, 2 are webhooks and 5 manage agent connections (measured), so the agent-relevant set is about 45 routes. The operations already call the same domain functions the routes do (ops-pages.ts:10-16) and read caller fields a cookie session could supply (caller.ts:33-40).
  • Five files over 900 lines in the router and Library (auth-session.ts, index.ts, video-row.ts, stripe-billing.ts, workspace-tree-store.ts), held by the LOC ratchet.

What Clarity already has that agent-native would be credited with. defineOperation (agent/operation.ts) with an Effect class (read, write, spend, publish, retract, destroy), an idempotency declaration, a target for audit keys and an Untrusted<T> wrapper for prospect text. The Effect class is a richer vocabulary than defineAction's needsApproval, authorize and readOnly flags, but it is vocabulary so far. The comment at operation.ts:8 defers human approval to "PR 5", ops-account.ts:50 says approval rows "are written from PR 5", and runOperation in dispatch.ts:145-209 checks permission, rate tier, entitlement and replay but has no approval branch (read in code). The nine live operations declare only read and write effects. So the policy model exists on paper and enforcement is one PR away. Beyond the door, Clarity has generated D1 row types with a lint that rejects hand-written rows, a rule against SQL-text-reading tests backed by a SQLite D1 that runs the real migrations, one lint-enforced writer of the videos table, a generated docs/agents/guards.md with 36 rules and the CI step that reaches each one, a LOC ratchet, a CSS budget, append-only migrations, per-PR preview Workers with seeded D1s, and an eslint-suppressions.json baseline that lint:prune only ever shrinks. Zero process.env reads in workers and packages (grep); the typed Env is the config schema agent-native asks for.

5. The rebuild question

What we would get for free. The application shell (router, auth session plumbing against Better Auth, org model), an action registry with HTTP and MCP exposure, an in-app chat agent with approvals, application state, real-time sync, i18n catalogs, file upload providers for R2, and the guard tooling. None of it drops in; each piece needs wiring to Clarity's data.

How much that is. Two computations, both inferred from the measured subsystem lines in section 3.

Method Per-subsystem fractions Result
Generous (version 1 of this report) auth 25%, pages 10%, video 5%, AI 40%, telemetry 20%, email and admin 20%, agent door 80%, UI kit 60%, deploy 10% 14,762 lines, 13% of 110,000
Strict (section 4 verdicts) 0 for every "nothing" and "pattern" row, agent door 80%, UI kit 30%, deploy 10% for the guards about 4,200 lines, 4% of 110,000

The generous row credited auth, pages and video with fractions the mapping table marks "nothing", and gave the UI kit 60% on the false premise of a shared stack. The honest range is 4 to 13%, and the number is a planning score, not demonstrated coverage.

What we would rebuild. The block page model and six theme presets, the editor document store with revisions and undo, both renderers, the Library tree, every Mux path (ingest, webhooks, settle-on-read, clips, speech, auto-trim, stills), the recorder and its upload, generation jobs and rebase, the Stripe inbox and entitlement rule, trials, admin, GoHighLevel sync, view stats and notifications, and the tables as Postgres schema plus a data migration. The migrations define 52 tables, 7 of them temporary or later dropped, so 46 to 52 depending on what the live database still carries (measured from workers/*/migrations*). About 70,000 product lines, plus the tests that matter among 96,000 test lines, because the SQLite-backed D1 test harness does not carry over. Measured lines, inferred scope.

What we would lose. D1 with generated row types and the migrations-run-in-SQLite test base. Mux adaptive playback, trims and stills, unless Mux is re-integrated into a template built around file playback. WorkOS, unless an adapter is written, and with it every existing Agent Connection, because the door's bearer is an AuthKit token. Per-PR preview Workers with isolated D1s. The LOC ratchet, CSS budget and guards table as they stand. The edge cache and the Worker cache API in front of public pages, if and only if public delivery moves off the Worker. Every runtime cost and latency figure Clarity has today; no explorer could determine cold start, bundle size or correctness of the Workers preset at this size. Workers now allow 64 MiB uncompressed per script (Cloudflare changelog, 2026-09-04), so size is a measurement to take, not a wall.

What we would gain. An in-app chat agent with a run loop, tool approvals and resumable runs. MCP OAuth connectors. Multi-provider model engines. Application state the agent can read. Comments, reactions, transcript search, agent-readable share links, Loom import, a Chrome extension and a desktop recorder from clips, with transcription tied to Builder-managed services or a Gemini key. i18n. Read in code.

On the in-app chat. GenerateComposer.tsx already turns pasted prospect context and attachments into a page inside the editor, and the MCP door already serves Claude, ChatGPT, Codex and Cursor. A chat panel would be a third way to reach the same operations. Building it on agent-native means writing the run loop yourself (agentkit does not ship one), upgrading React Router a major, and carrying Radix beside Base UI. Widening the MCP door is worth more today. Revisit a chat panel if the agent audit log shows reps leaving the editor for external hosts to finish edits, or if a customer segment cannot connect an external agent at all. Then agentkit's protocol is the first candidate for its transport.

Effort. A parity rebuild is a guess at 4 to 9 engineer-months of all capacity with no feature work, followed by a cutover. The basis is 70,000 lines at Clarity's measured pace of about 18,000 net product lines a month (git numstat over workers, packages, editor/src and scripts since 2026-04-01, tests excluded; 1,041 pull requests, 921 merged, measured from GitHub), so about 4 months for the lines alone. Then tests, the table cutover, moving WorkOS users to Better Auth, re-authorising Agent Connections, and a stack none of the team has run (Nitro, Postgres, Better Auth, a 0.x framework with breaking changes between releases). The high end is what the unknowns could cost, not a calendar estimate.

Why the premise fails. The claim is that adopting agent-native would vastly simplify Clarity. Measured, packages/core is 596,520 non-test lines against Clarity's 110,000, and the single file production-agent.ts is 13,674 lines. Size alone does not prove a framework is bad; it proves that adopting it swaps 110,000 lines you wrote and test for a dependency five times larger that you do not control, on a database you do not run, with about 110 Node-only imports to get past on Workers. The parts of Clarity that are complicated (two renderers, two AI paths, legacy fields, two capability registries, 900-line files) are Clarity's own duplication, and the framework has no replacement for any of them. Simplification comes from deleting those copies. Subtract before you add.

Recommendation. Do not rebuild, and do not take agent-native runtime code now. Take its one architectural idea and apply it to code Clarity already owns. Make defineOperation the single capability registry that both the editor and agents call, so the 92-route and 9-operation registries become one. That is the real simplification William is after, and it costs operations, not a framework. Alongside it, adopt the repository conventions in section 6 and keep the product ideas in section 7 on the list. Watch agentkit only as a future transport for a chat panel, under the condition stated above. Do not scaffold a template.

What would have to be true to flip this. All of the following. Clarity decides an in-app chat agent is the primary interface and is willing to leave D1 for Postgres. agent-native ships a D1 or SQLite dialect, or a spike proves the cloudflare_module preset at Clarity's size against Neon over HTTP. agent-native reaches a stable 1.0 with a LICENSE file. Mux lands in clips, or Clarity drops Mux. Even then the right move is a new Clarity app on agent-native that calls Clarity's existing Workers for media, not a rebuild.

6. Standards to adopt without a rebuild

Ranked by payoff over cost. Each names the agent-native file, the change in Clarity, the files touched and a rough cost.

  1. One capability registry. agent-native's guard-no-action-twin-routes.mjs fails a PR that adds a /api route re-exporting an action or an app-data CRUD route with no action behind it, and exempts streaming, webhooks and auth callbacks (agent-native: scripts/guard-no-action-twin-routes.mjs:1-50). Its feature checklist requires every feature that adds data or a capability to add its action (.agents/skills/adding-a-feature/SKILL.md:15-17). In Clarity the end state is within reach. Operations call the same domain functions as routes (ops-pages.ts:10-16) and read AgentCaller fields a cookie session can supply (caller.ts:33-40). The change, in order. First, let agent/dispatch.ts accept a session caller so the editor can call operations through the same policy path. Second, migrate the roughly 45 agent-relevant app-data routes to operations one PR at a time, read and write effects first. Third, finish the human-approval enforcement that agent/operation.ts:8 defers to "PR 5" before any publish or destroy operation is reachable by an agent, because runOperation runs every operation without an approval check today. A session caller is the human, so the editor path needs no approval step. Fourth, add a parity guard in the style of scripts/check-loc-ratchet.sh that lists /api routes with no backing operation, baselines today's list, exempts admin, Stripe billing, webhooks, auth callbacks and agent-connection management, and fails when the list grows. This is Clarity's own ARCHITECTURE line "Agent hosts reach the same Worker" taken to its end. Cost about two days for approval, a day for the session caller, a day for the guard, then an operation per PR as a habit.

  2. MCP usage events in PostHog. agent-native emits $mcp_tool_call with $mcp_tool_name, $mcp_duration_ms, $mcp_is_error and $mcp_client_name so PostHog's MCP dashboards work unchanged (agent-native: packages/core/src/mcp/analytics.ts:152-179); tool results are never sent and arguments are off by default. Clarity has PostHog and an agent_actions audit table but no MCP events (grep of agent/). The right boundary is callTool in agent/mcp.ts:132-156, which sees the tool name, the outcome kind, the error path and the handshake's client name, not one call in dispatch. product-analytics.ts drains outboxes and exposes no generic track, so the change is an event insert into the existing outbox, a timer around runOperation, and the client name carried from initialize. Cost about a day.

  3. No-silent-coercion as an ESLint rule. agent-native: scripts/guard-no-silent-coercion.mjs:18-32,50-65 rejects empty catch blocks, .catch(() => null) and ?? [] on an awaited call, with a coercion-ok: <reason> opt-out. Clarity has no equivalent (search of scripts/, eslint.config.mjs and docs/agents/guards.md). A coarse regex finds about 105 candidate sites in product source; those are candidates, not bugs. Write the rule inline in eslint.config.mjs beside the six existing clarity/* rules and baseline the current count with eslint-suppressions.json and lint:prune, the mechanism that already holds the raw form element and shadcn appearance counts. No diff-scoping script and no dependency on item 5. Cost one day.

  4. D1 read cost. agent-native: scripts/guard-no-unbounded-table-reads.mjs:1-30 flags an added SELECT with no WHERE and no LIMIT; its header records a 170 TB Neon transfer bill from one such read. The lesson transfers, the heuristic does not. D1 bills rows read, and a WHERE clause on an unindexed column still scans the table. Clarity's existing D1 lint selects calls by method name and checks row types (eslint.config.mjs:309); it does not read SQL text, so a bounded-read rule is a new visitor, and the rules live inline in eslint.config.mjs, not in a plugin directory. workspace-tree-store.ts has 34 lines matching SELECT and 3 matching LIMIT (grep). The better first step is to run EXPLAIN QUERY PLAN on the hot queries (the minute cron's sweeps, the Library list, the public page read), check each against the indexes the migrations create, and add indexes where the plan says SCAN. A lint rule for new raw SELECTs is a secondary aid. Cost one day for the plan review, half a day for the rule if wanted.

  5. Three-outcome exit codes as a written convention. agent-native's requireAddedLines (agent-native: scripts/lib/changed-lines.mjs:52-70) exits 2 when the base ref is missing or a source file diffs as binary, so "could not inspect" never reads as "passed". Clarity's check scripts already fail closed where it matters; check-loc-ratchet.sh and check-migrations-append-only.sh run under set -euo pipefail, and scripts/check-ci-invariants.sh guards two such cases. The gap is about new scripts. Write the convention (0 pass, 1 fail, 2 could not run) into docs/agents/guards.md and apply it to each new scripts/check-* as it lands. Only about 25 of agent-native's 81 non-test guards follow their own rule (grep). Cost half a day.

  6. Default MCP exposure follows in-app exposure. agent-native: packages/core/src/action.ts:389-418 makes mcpTool default to agentTool, so one flag stays one decision. When item 1 produces many operations, add a single exposure field on Operation rather than a second list. Cost zero now; a design note on the issue that starts item 1.

  7. Doc budgets. agent-native: scripts/guard-doc-budgets.mjs holds AGENTS.md and named skills under a word ceiling. Clarity's AGENTS.md is already small; apply a ceiling only to .agents/skills/*/SKILL.md, where length creeps. Cost half a day.

  8. A friction report. agent-native: scripts/agent-friction-report.mjs counts repeated corrections and names the skill that should have prevented them. Revisit when docs/agents/loops.md next changes. Cost two days, value unproven.

Already in Clarity, so not recommended. A small AGENTS.md that points to skills. Guards listed in one place with CI reachability. Append-only migrations. No source-reading tests. Shared UI primitives over raw elements. snake_case analytics ids. A single typed config. An action-style registry with audit and idempotency. A verify feature map. A suppressions baseline that only shrinks.

7. Product ideas worth stealing

  • Agent-readable share links. Clips lets an agent read a shared clip's transcript and timestamped frames without the video, and keeps agent hits in a separate recording_agent_views table so human view counts stay clean (agent-native: templates/clips/server/db/schema.ts:410-432). Prospects' assistants will open Journey Pages; Clarity's public page could serve a transcript and summary to a declared agent and keep those hits out of VIDEO_STATS_DB.
  • One named view rule. shouldCountView counts a view after 5 seconds, 75% completion or a scrub to the end (templates/clips/server/lib/recordings.ts:417-422).
