Removing the editor panel, and the edits underneath it

Gap assessment and design, 2026-10-06. Read-only investigation at commit 41bfc02ed. Nothing in the repo changed.

Four GPT-6 Sol explorers traced the code. Three Opus investigators read git history, Linear and the design site. An Opus explainer and an Opus synthesizer combined them. Both synthesis lanes were meant to run on Fable and dropped out on a Fable usage limit, so Opus took over. The coordinator spot-checked the claims this summary leans on against the code. The history is on a second page, why it looks like this.

The short version

The panel on the right is a second copy of the page. The canvas already edits every visible string except the lead form and the pricing plans. What only the panel can do today is short. It deletes a block, moves a block from the keyboard, edits the form and pricing plans, adds or removes logos once a row has some, and swaps an attached PDF.

The prior plan from 2026-09-08 had five steps. None of them started. Code work on panel removal stopped on 2026-08-13, and no record says why. Since then the panel was restyled (#724) and gained panel-only settings (#782). The map ticket WIL-3276, the prototype ticket WIL-3277 and the undo question WIL-3278 have been in the Linear trash since the 2026-10-01 cleanup.

The bigger gap sits under both surfaces. There is no shared, typed edit. Each control builds its own field patch, often by array position. The hero rule lives in three functions plus guards in five UI files. Only FAQ renumbers seq_no, and the public page orders lists by seq_no. Every save sends the whole document, and the merge treats each list as one value. If two writers edit different FAQ rows, one loses its row. The editor has no undo. An agent has nothing typed to call. Deleting the panel without fixing this moves the duplication onto the canvas.

Text editing has two plain-text engines with different rules. EditableText does headings. Escape commits, empty text saves, rich paste goes straight in, and nothing guards IME composition. InlineText does CTA labels, FAQ rows and table cells. It pastes plain text, guards IME and snaps empty text back. Moving blocks has one shared drag helper, beginPointerDrag, which four of the seven drags in the editor use. The canvas grip is invisible to keyboards and screen readers. The only live region for move announcements sits inside the panel, and it goes silent when the panel is collapsed.

The recommendation in one paragraph

Give every list item a durable id. Make every change a typed PageEdit that names its target by id. Have one pure applyEdits in packages/journey-page-domain enforce every rule, and have it return the inverse edits, which gives undo. Add an edit spec to each BLOCK_REGISTRY entry with field names, limits and caps. The text field, the MCP input schema and the edit-by-asking prompt all read that spec. The editor, the built-in AI and an MCP pages_edit tool all call applyEdits. On top of that sit one plain-text field, one drag lifecycle, one handle-and-menu keyboard idiom, one row-controls grammar and one settings card. Each slice deletes its panel copy in the same PR. Part 3 below has the types, the alternatives table, the sequence with a check for each slice, and the calls only William can make.

Where the coordinator differs from Part 3

Slice 2 should stay small. Build applyEdits with only the edits the canvas uses today: block insert, move and remove, set_field, and FAQ items. Add each list's edits in the slice that builds its UI (pricing in 7, form in 8, summary and gallery in 9). Do not move the panel's pricing and form editors onto the new core. Those copies get deleted, so migrating them first is wasted work. They keep calling the updateBlock wrapper until their slice removes them.

Part 1. How the editor works

Overview

The editor shows one Journey Page document in two places. The right-hand panel is the data-slot="editor-panel" element at EditorWorkspace.tsx:240-355, and it lists every block as an accordion of form controls. The canvas is LivePreview, which renders the page with the published markup and swaps in inline editors when it receives update callbacks (LivePreview.tsx:139-233). Both places call the same useEditorPage commands and write to the same document store, so they never disagree about content.

The canvas already edits every visible string except those in the lead form and the pricing plans. It alone reorders FAQ rows and edits summary tables and galleries. The panel alone deletes a block, moves a block from the keyboard, edits the lead form and pricing plans, adds or removes logos once a row has some, and changes an attached PDF.

The gap that matters most sits under both places. There is no shared, typed edit. Each control builds its own field patch, often addressing list rows by array position, and useEditorPage.updateBlock shallow-merges that patch into the block (use-editor-page.ts:207-216). Storage only ever receives whole documents. So each rule lives wherever a component needed it. The hero rule sits in three functions and in guards across five UI files, seq_no renumbering exists only for FAQ, and clearing media is four copied literals. Undo has nothing to record, and an agent has nothing typed to call. Deleting the panel without fixing this would move the duplication onto the canvas.

Key concepts

JourneyPageDocument is one ordered blocks array plus name, brand, meta, extras and an optional theme (blocks.ts:184-206). A Block is { id, kind, fields } with one of nine kinds (blocks.ts:32, 157-182). Block ids are durable because engagement analytics use them as section_id, and a Block keeps its id across rename and reorder (CONTEXT.md:175; WIL-3276 notes).

Several kinds hold lists. FAQ questions have carried a row id since PR #530 (questions.ts:16-39). Pricing plans, plan features and form fields carry seq_no and at most an optional id. Summary rows are bare { cells }. Gallery and logos images are { image_id }, and the same image can appear twice (index.ts:209-256; blocks.ts:137-139; GalleryEditor.tsx:102-103). The public renderer orders questions, plans, features and form fields by seq_no, never by array position (render-blocks.ts:594, 620; render-values.ts:74-76; lead-form-fields.ts:62-66). An editor reorder that only permutes the array therefore changes nothing on the live page. The FAQ slice's review loop caught exactly that bug before it shipped (WIL-3277, 2026-07-28).

BLOCK_REGISTRY maps each kind to default fields, a normalizer, the published root skeleton, a label and a one-line generation prompt (blocks.ts:240-249, 632-642). It records nothing about which fields a person or an agent may edit, their length limits or list caps.

useEditorPage connects the document store to React and exposes the edit commands (use-editor-page.ts:53-308). addBlockOfKind mints a UUID and calls domain addBlock. removeBlockById calls removeBlock. moveBlockTo reads the live document, clamps the target around the hero and calls moveBlock. updateBlock shallow-merges a field patch, so callers rebuild nested arrays and objects themselves. updateDocument takes a whole document, and the Share dialog's link fixes use it (EditorWorkspace.tsx:194; JourneyPageShareDialog.tsx:198-202).

The document store keeps the live document outside React, one store per editor mount (journey-page-document-store.ts:157-561). edit records a change by the rep, resets the save status and arms autosave, which fires 900 ms after the last change. replace applies a merge or a server echo without touching the save status (journey-page-document-store.ts:65, 240-257). One writer serializes saves. When a save's echo matches what was sent, the store keeps its own objects, because a contentEditable draft lives in the DOM and a remount would erase it (journey-page-document-store.ts:82-132; commit e2288ec38).

The save protocol sends the whole document with the revision it was made from (journey-page-drafts.ts:53-81). The router normalizes it, refuses missing or duplicate block ids and bad Library references, and updates the D1 row only if the stored revision still matches (journey-pages-native.ts:369-399; journey-page-content-store.ts:71-86, 142-188). A stale save gets 409 stale_revision with the current draft. The client then merges and tries again, three attempts in all (journey-page-drafts.ts:16, 64-79).

mergeDrafts is that merge (merge-drafts.ts:8-74). The local side wins whatever it changed since the base. Blocks merge by id and then field by field into nested objects, but every array is one unit (merge-drafts.ts:76-88). Two writers that change different rows of one FAQ therefore conflict on the whole list, and the writer that merges second keeps its whole list. A block that one writer deleted and the other edited survives only when the editing writer merges second (merge-drafts.ts:23-26).

LivePreview renders each block with the published page's root tag and data attributes, and a table-driven test holds it to the SSR renderer (blocks.ts:208-221; block-rendering-parity.test.ts). It edits only when it receives onUpdateBlock and the media callbacks, and renders read-only markup otherwise (LivePreview.tsx:139-276). The panel renders BlockEditor, a switch from block kind to a per-kind form (block-editors.tsx:60-82). It sits inside the editor-form element, which also holds the editor's only live region for move announcements (EditorWorkspace.tsx:253-258).

Canvas plain text uses two contentEditable components. EditableText edits headings and owns the alignment bar and the character count (EditableText.tsx:23-247). InlineText edits CTA labels, FAQ rows and summary cells (InlineText.tsx:12-78). Rich text uses one Tiptap configuration that the panel's RichTextField and the canvas's InlineRichText share (RichTextField.tsx:322-379, 490-512). A contract test keeps Tiptap's output inside what sanitizeRichText allows (rich-text-contract.test.ts). The panel's own inputs are native controlled inputs that write on every keystroke (FormFields.tsx:103-225).

beginPointerDrag owns one pointer gesture from press to settle (reorder.ts:131-229). It waits for 4 px of travel, captures the pointer, ignores other pointers, autoscrolls, allows one drag at a time, and settles exactly once on pointerup, pointercancel, lost capture, a competing drag or cancel(). It blurs the focused editor first. A contentEditable that React relocates loses focus without a blur event, and its typed text would never commit (reorder.ts:141-145; WIL-3277, 2026-07-28). The panel block drag, the canvas section drag and the FAQ and summary row drags use it. No other drag does.

Typing a FAQ question on the canvas

The question is an InlineText, a plaintext-only contentEditable, so typed characters stay in the DOM and React state does not change (InlineText.tsx:35-46). On blur, InlineText trims the text, clamps it to 255 characters, puts the old value back if the result is empty, and otherwise calls onCommit (InlineText.tsx:47-52). FaqListEditor turns that into update(index, { question }), which rebuilds the whole questions array and calls onUpdateBlock(faq.id, { questions }) (FaqListEditor.tsx:94-97, 189). updateBlock shallow-merges the new array into the block's fields and calls store.edit (use-editor-page.ts:207-216). The store recomputes the document's JSON signature, sets the save state to idle, notifies React and arms autosave (journey-page-document-store.ts:203-257). After 900 ms without another change, save('auto') snapshots the document, and saveDraftMerging PUTs it whole with base_revision (journey-page-document-store.ts:330-383; editor-api.ts:417-429). The router saves under the revision check and answers with the next revision. The store keeps its own objects and takes only the server ids and the revision (journey-page-document-store.ts:384-415).

Typing the same question in the panel

The panel shows it in an AutoTextarea whose onChange calls updateQuestion(index, ...) on every keystroke (block-editors.tsx:491-516). That reaches the same updateBlock and the same store. Only the rules differ. The panel writes each keystroke and accepts an empty question. The canvas writes on blur and puts an empty question back.

Dragging a block on the canvas

Hovering a rendered section shows the CanvasReorder grip, except on the first section, which the code assumes is the hero (CanvasReorder.tsx:43-50). Pointerdown starts beginPointerDrag, which blurs and so commits any text being typed. Sections then travel on inline transforms while React leaves the list alone (CanvasReorder.tsx:89-127). On drop the grip reports the dragged block id and the id of the block it should land before. handleMoveSection turns that into document moves with canvasDropMoves, which also carries an untitled logos block that renders inside the story above it (EditorWorkspace.tsx:86-91; reorder.ts:66-81; page-sections.ts:15-28). Each move goes through moveBlockTo, which clamps around the hero, and each becomes its own store.edit (use-editor-page.ts:177-205). The landing is announced in the live region inside the panel (EditorWorkspace.tsx:75-83, 258).

Moving a block in the panel

useBlockReorder folds every accordion to its header so all rows share one height, then turns pointer travel into a slot (use-block-reorder.ts:7-18, 49-102). The grip also takes ArrowUp and ArrowDown. Two buttons that appear on focus offer Move up and Move down, because a screen reader in browse mode consumes arrow keys (EditorWorkspace.tsx:93-101, 284-304; PR #572). All three paths call moveBlockTo.

A generation landing

Generate first flushes the rep's document, so the router generates against what the rep sees (use-ai-generate.ts:257-272). A router job asks the model for blocks, builds a complete document with applyGeneratedBlocks, places attached media, and lands the result with mergeDrafts({ base, local: current, remote: generated }) under the revision check, three tries in all (journey-page-generation.ts:73, 169-259). The stored human draft is local, so any block the rep changed during the run keeps the rep's version. The editor's watcher then calls store.adopt, which waits for any save in flight, accepts the landed revision, and merges the rep's unsaved edits over it (use-ai-generate.ts:149-188; journey-page-document-store.ts:302-314). Media dropped without a prompt skips the model and enters the document through store.replace (use-ai-generate.ts:237-243).

Gotchas

  1. CanvasReorder never stores its drag session. startDrag assigns the result of beginPointerDrag to a local started at CanvasReorder.tsx:82 and never to session.current, so the unmount cleanup at line 35 cancels nothing. If the canvas unmounts mid-drag, the window listeners stay until pointerup, and onSettle can then still call onMove and commit a move. That last part is inference from reorder.ts:183-196, not reproduced.
  2. A rep can delete the hero and cannot add it back by hand. The panel draws its delete button on every accordion, the hero's included (EditorWorkspace.tsx:307-316). Domain removeBlock has no guard (blocks.ts:721-726), and the router validates block ids only (blocks.ts:820-844). The add picker never offers a hero (AddSection.tsx:12-14). The canvas grip, the canvas add seam and the panel drag all treat the first block as the immovable hero (CanvasReorder.tsx:46-49; AddSection.tsx:135-137; use-block-reorder.ts:51-52; EditorWorkspace.tsx:271). After the deletion the first story cannot be dragged, and nothing can be added above it on the canvas. Only a generation puts a hero back (generate-blocks.ts:287-298). This is inference from the code paths, not reproduced.
  3. Emptying a CTA label in its card deletes the link. When focus leaves a CTA slot whose label is empty, the blur handler calls removeCta (CtaRowEditor.tsx:252-259). For the primary CTA that writes { label: '', link: '', style: '' } (CtaRowEditor.tsx:129-131). WIL-3295 placed the fix in that blur path on 2026-08-13, and the code still routes there.
  4. An emptied heading disagrees with the published page. EditableText commits an empty string (EditableText.tsx:137-141). FAQ, pricing, summary and gallery normalizers turn an empty title back into the default on the next load (blocks.ts:468, 504, 546, 626), and the public renderer prints that default (render-blocks.ts:602, 621, 652, 679). Until a reload, the canvas shows the placeholder "FAQ title..." where the live page shows "Frequently Asked Questions". Hero and story titles stay empty. Logos titles are optional by design (blocks.ts:390-391).
  5. Long text from outside loses its tail on the rep's next keystroke. Normalization caps FAQ questions and pricing text at 255 characters (index.ts:546-553, 565-575) but not hero or story titles (blocks.ts:343, 378). EditableText clamps on every input event and moves the caret to the end (EditableText.tsx:124-135, 148-150). A 400-character title written by any other writer would render in full and then be cut on the rep's first keystroke. This is inference.
  6. Form field names can repeat. The panel's "+ Add field" names a new field custom_field${formFields.length + 1} (block-editors.tsx:435). Remove one field and add two, and two inputs post under the same name. I did not check how submissions handle the duplicate.
  7. Two drags commit when they should not. The gallery drag writes the document every time the pointer crosses a cell, so a cancelled drag cannot roll back (GalleryEditor.tsx:38-48). The media resize commits on pointercancel as well as pointerup (JourneyMediaResizer.tsx:61-74).
  8. Committing one summary cell remounts its whole row. updateSummaryCell builds a new row object (SummaryTableEditor.tsx:29-37), and row keys come from a WeakMap of row objects (SummaryTableEditor.tsx:83-96). By inference, tabbing from one cell to the next in the same row can land focus on a node React just replaced. The unit test checks only that other rows keep their identity (summary-table-editor.test.ts:18-23).
  9. A write from outside can erase a draft the rep is typing. InlineText keys its element on value (InlineText.tsx:36-38), and useRichText calls setContent whenever the outside value differs (RichTextField.tsx:366-379). The rep may keep typing while a generation runs (use-ai-generate.ts:257-259). If the landed draft changes the field being typed in, the node remounts or its content is replaced, and the uncommitted text is gone. This is inference, not reproduced.
  10. Canvas move announcements go silent when the panel is collapsed. The only live region sits inside the panel (EditorWorkspace.tsx:258), and the collapsed panel is inert (EditorWorkspace.tsx:249). Inert content leaves the accessibility tree, so a screen reader should hear nothing. This is inference from the inert rule, not tested with a screen reader.
  11. The canvas and the public page order pricing plans differently. The canvas renders plans in array order (LivePreview.tsx:832), and the public renderer sorts them by seq_no (render-blocks.ts:618-620). They agree today only because every add appends a newer timestamp. The QUALITY.md row that warned about this went out in #818, and no code comment replaced it.
  12. Domain rules live in UI files. The CTA add order nextCtaToAdd is exported from a component (CtaRowEditor.tsx:57-64) and imported by the panel. The rule that a preset clears the hero's ctaColor lives in the hook (use-editor-page.ts:245-253), and the agent build design copies it by line reference. MAX_PLANS (block-editors.tsx:543) and SUMMARY_MAX_COLUMNS (SummaryTableEditor.tsx:23) are UI constants. The Share dialog addresses pricing rows by position because "the share dialog is modal" (page-link-destinations.ts:16-19), and an agent writing at the same time would break that assumption.

Part 3. Design recommendation

The data shape

Every addressable thing on a page gets a durable id, and every change is a PageEdit. A PageEdit is a small typed value that names its target by id and states the end state it wants. One pure function in packages/journey-page-domain applies a batch of edits to a document, enforces every rule, and returns the new document with the inverse edits. The browser, the built-in AI and the MCP server all call that function. These are the primitives William asked for. The name avoids "Operation", which the agent glossary already uses for an MCP tool (CONTEXT.md:87-88 on branch agent/connections-dispatcher).

Blocks already have durable ids. List items get them as follows.

  • FAQ questions keep the id they have had since PR #530 (questions.ts:20-35).
  • Pricing plans, plan features and form fields get a stored id beside seq_no. seq_no keeps one job, published order, as the FAQ code already decided (questions.ts:20-23).
  • Summary rows get an id, and the summary block gets columnIds, one per cell position, so a column has an id while cells stay stored as they are.
  • Gallery and logos images become { id, image_id }, because one image can appear twice.
  • The four hero CTA slots keep their keys, primaryCta, paymentCta, customCta and signCta, as ids.

normalizeJourneyPageDocument fills a missing item id from the block id, the list name and the item's stored position. Two tabs that load the same stored draft derive the same ids, and the next save persists them, so no D1 backfill is needed. Two normalizers rebuild items from scratch and must keep id, normalizeSummaryRows (blocks.ts:510-528) and normalizeClientImages (index.ts:613-618). The router has to ship that change before any editor writes ids, the deploy order the store already states for schema changes (journey-page-document-store.ts:324-329).

With ids in place, mergeValue merges an array whose items all carry id the way mergeDrafts already merges blocks. It goes item by item, and whichever side reordered decides the order (merge-drafts.ts:39-52). Arrays without ids stay one unit. That one change gives every whole-document writer per-row merges, the browser and generation included.

The edit set

The edits live in a new module, packages/journey-page-domain/src/page-edits.ts, exported from the package barrel.

import type { BlockKind, JourneyPageDocument } from './blocks';
import type { JourneyPresetId } from './theme-presets';

/** A Block's durable id. Analytics use it as section_id. */
export type BlockId = string;
/** A list item's durable id. Normalize fills it and nothing reuses it. */
export type ItemId = string;
/** Where a moved or inserted thing lands. Before this id, or last when null. Never an index. */
export type Before<Id> = Id | null;

/** The lists inside blocks. The spec says whether seq_no, array order or fixed slots decide order. */
export type ListRef =
  | { list: 'questions' }                  // faq
  | { list: 'plans' }                      // pricing, at most 3
  | { list: 'features'; planId: ItemId }   // one pricing plan
  | { list: 'formFields' }                 // form
  | { list: 'rows' }                       // summary
  | { list: 'columns' }                    // summary, 2 to 4
  | { list: 'images' }                     // gallery up to 24, logos up to 6
  | { list: 'ctas' };                      // hero, four fixed slots in fixed order

export type FieldValue = string | number | boolean;

export type PageEdit =
  // Text and settings on a block. `field` is a name the kind's edit spec declares.
  | { op: 'set_field'; blockId: BlockId; field: string; value: FieldValue; expect?: FieldValue }
  // Block structure. The hero is never inserted, moved or removed.
  | { op: 'insert_block'; blockId: BlockId; kind: Exclude<BlockKind, 'hero'>; before: Before<BlockId>; fields?: unknown }
  | { op: 'move_block'; blockId: BlockId; before: Before<BlockId> }
  | { op: 'remove_block'; blockId: BlockId }
  // List items, addressed by block id plus item id.
  | ({ op: 'insert_item'; blockId: BlockId; itemId: ItemId; before: Before<ItemId>; value?: Record<string, FieldValue> } & ListRef)
  | ({ op: 'move_item'; blockId: BlockId; itemId: ItemId; before: Before<ItemId> } & ListRef)
  | ({ op: 'remove_item'; blockId: BlockId; itemId: ItemId } & ListRef)
  | ({ op: 'set_item_field'; blockId: BlockId; itemId: ItemId; field: string; value: FieldValue; expect?: FieldValue } & ListRef)
  | { op: 'set_cell'; blockId: BlockId; rowId: ItemId; columnId: ItemId; value: string; expect?: string }
  // Media through one rule per kind, assignBlockMedia plus a new clearBlockMedia.
  | { op: 'assign_media'; blockId: BlockId; assetId: string; media: 'image' | 'video' }
  | { op: 'clear_media'; blockId: BlockId }
  // Page-wide settings that belong to no block.
  | { op: 'set_page'; field: 'name' | 'calendlyLink' | 'logoId' | 'logoPosition'; value: string; expect?: string }
  | { op: 'set_theme'; preset: JourneyPresetId | null };

export type EditRefusal =
  | { code: 'not_found'; id: string }
  | { code: 'not_editable'; field: string }
  | { code: 'invalid'; field: string; reason: 'too_long' | 'empty' | 'not_allowed' | 'out_of_range'; limit?: number }
  | { code: 'fixed'; id: string }        // the hero, or a move in a fixed-order list
  | { code: 'full'; limit: number }
  | { code: 'id_taken'; id: string }     // an insert whose id names a different thing
  | { code: 'changed'; current: FieldValue };

export type EditOutcome =
  | { ok: true; document: JourneyPageDocument; changed: boolean; inverse: PageEdit[] }
  | { ok: false; at: number; refusal: EditRefusal };

How the editor, the built-in AI and MCP call it

The editor hook gains one command, apply(edits, { coalesce }). It reads the live document from the store, calls applyEdits, and on success calls store.edit with the result and pushes the inverse onto the undo stack. On a refusal it changes nothing and returns the refusal. A canvas drop of a story with fused logos becomes one batch and one undo step.

  { op: 'move_block', blockId: fusedLogos.id, before: target?.id ?? null },

editor.apply([{ op: 'set_item_field', blockId: faq.id, list: 'questions', itemId: q.id, field: 'question', value: text }]);

addBlockOfKind, removeBlockById, moveBlockTo and updateBlock become wrappers over apply while callers migrate, and each goes when its last caller does. The browser keeps the whole-document save and its revision check. The save protocol from #916 already handles revisions, retries and draft identity, and with item ids the merge no longer loses another writer's row, so the transport does not need to change.

The built-in AI keeps whole-document generation in v1. It already lands under a revision check and keeps the rep's changes. Edit by asking, which the 2026-10-06 AI call architecture plans without a design yet (https://willayam.github.io/clarity-design-previews/ai-call-architecture/), uses edits. The router asks the model for a PageEdit[] whose JSON schema comes from the spec, runs parseEdits, and lands the batch through the same server function as MCP. The editor adopts the result the way it adopts a generation now. A later step can express generation's own landing as edits, which would give it per-row merges and one-step undo.

Revisions, retries and idempotency

A new router function, applyEditsToDraft in workers/frontend-router/src/journey-page-edits.ts, serves MCP and edit by asking. It reads the stored draft, applies the batch, and writes with prepareDraftSave under the revision it read. On a conflict it re-reads and re-applies, three tries, the loop landGeneratedDraft already uses (journey-page-generation.ts:228-259). It writes nothing when the batch changes nothing. It applies edits to the current draft, not to the agent's base, because edits name targets by id and carry intent. The multitrack design chose the same replay-on-head shape for video edits (https://willayam.github.io/clarity-design-previews/multitrack-design-2026-10/). baseRevision tells the agent whether to re-read, and expect lets it guard a field it read. A target that no longer exists comes back as not_found with the current revision. The open editor meets the agent's write at its next save, merges it per item, and keeps its own changes.

applyEdits checks expect only when the field does not already hold value, so a replay of a guarded edit succeeds instead of failing its own guard. Callers mint ids, so applyEdits never calls crypto.randomUUID and stays pure, unlike addQuestion and resequence today (questions.ts:31, 71). Renumbering happens only when order changed. The server skips the write when nothing changed, so a replay does not bump the revision. That matters because every write reads as an unpublished change (journey-page-document-store.ts:439-441). For an answer lost on the network, the #1024 replay record keyed on editId returns the first result.

Undo

applyEdits returns the inverse of each batch, computed from the document it changed. A set_field inverts to the prior value, with expect set to the new value. insert_block inverts to remove_block. remove_block inverts to insert_block with the removed block's full fields and its old successor as before, so the restored block keeps its id and its analytics history (CONTEXT.md:175). A move inverts to a move before the old successor. The store keeps a session stack of entries that each hold the edits and their inverse. Undo applies an entry's inverse through apply, so it autosaves and merges like any edit, and pushes the entry onto redo.

The grain is one gesture. That means one committed text field, one drop including both blocks of a fused story, one add, one remove, one toggle or one preset change. Rich text records once per focus session, because consecutive body edits coalesce on a blockId.body key, and Tiptap's own history handles Cmd+Z while the body has focus. If a merged change from another writer altered a field since, the inverse's expect fails, and that undo step says so instead of overwriting the newer text. Generation landings and other writers' changes stay off the stack. Agent writes keep their inverse in the MCP write record, which gives a later "revert this agent change" the rollback the 2026-09-30 design promised with whole previous documents.

One keyboard idiom for moving things

The closest pieces are FAQ's Alt+Up and Alt+Down in the question (FaqListEditor.tsx:174-185) and the panel's live region (EditorWorkspace.tsx:72-83). The record contradicts itself here. WIL-3277 rule 4 made "arrow keys on the grip" the precise equivalent of drag. The FAQ slice then deleted the grip keyboard path in favor of Alt+arrows and took the grip out of the tab order (WIL-3277, 2026-07-28; PR #530). PR #572 added fallback buttons because browse-mode screen readers consume arrow keys. The same rule 4 rejected per-row up and down buttons, because the item slides away from a stationary pointer.

The resolution is one handle per movable thing. The handle is a button in the tab order, and drag starts from it. Enter or a click opens a menu with Move up, Move down and Remove, plus Add above and Add below for blocks and Duplicate for plans. Alt+Up and Alt+Down move the innermost movable item that holds focus, and Alt+Left and Alt+Right move summary columns. Every move announces its landing in one live region on the canvas. A screen reader can operate a menu without per-row buttons, and the menu closes after each choice, so nothing slides under a stationary pointer. The 2026-09-08 doc already chose "A click menu on the existing gutter grip" for block delete, move and add. The cost is one extra Tab stop per row, which #530 avoided, so the tab order goes to William below.
