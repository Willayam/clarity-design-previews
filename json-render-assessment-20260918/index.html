json-render for Journey Pages

Keep the current page renderer. Build progressive previews with the installed AI SDK first. Revisit json-render if we need nested AI-composed layouts or generated interfaces inside chat.

json-render lets AI compose a UI from an approved component catalog. The application owns the components and their behavior. Clarity already uses this approach with an ordered list of typed page blocks.

Where it could help

UseAssessment

More varied page designsRequires better block designs and controlled layout variants. Installing a renderer does not supply those product decisions.

What the code establishes

The page domain defines nine block kinds. Its generation prompt draws descriptions from the registry, while a structured-output schema constrains the model. The inspected generation action consumes the stream before applying the result to a completed page document.

The apply step preserves existing media, form configuration, block identities, and presentation. Public rendering maps those blocks to HTML. The architecture decision for block documents explicitly retains separate public and interactive editing renderers.

A small experiment that would settle adoption

First compare the existing generation path with progressive previews using the installed AI SDK and synthetic pages. Its local type declarations expose partialOutputStream; the current generation action consumes the stream before applying the final document. The editor already subscribes to generation rows. Publishing validated progress through that subscription is the smaller integration to investigate. If that proves insufficient, compare a custom-schema json-render stream using identical prompts. Keep JourneyPageDocument as the saved format and keep both current renderers. Preview completed, validated blocks in temporary state; commit only a validated final result through the existing preservation rules.

Include new-page generation, a single headline edit, block reorder, a page with attached media, and an interrupted stream. Measure time to first useful preview, time to completion, output validity, token usage, and preservation of media and block IDs. Adoption earns its place only if the user experience improves and total integration code is simpler.

This is an experiment proposal. No package integration, speedup, quality gain, or bundle-size change has been measured.

Principles behind the recommendation

Laziness Protocol: retain the working renderer and try existing streaming primitives before adding a dependency. Type System Discipline: keep the typed page document authoritative and validate generated changes before accepting them.
