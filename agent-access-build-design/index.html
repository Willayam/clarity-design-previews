1. Summary

One bearer door at POST /mcp, verified against AuthKit's JWKS with jose. One policy dispatcher that reads an operation registry, where each operation carries one effect class (read, write, spend, publish, retract, destroy) that decides entitlement, rate tier and whether a human must approve. A video edit on a video that a live page uses is promoted to publish, because public pages resolve the current media, not a frozen copy. Twenty-two operations wrap server functions that already exist; video operations reach the Library only through env.LIBRARY.handleBrowserRequest. Bytes never pass through Clarity; a local agent PUTs the file to the Mux direct-upload URL itself.

Publish, share-page creation, deletion and live-media edits stop at a human. The agent gets an approval link; the owner opens /approve/:id signed in (reachable while walled), sees server-held facts, clicks Approve, and the server claims the row (pending to executing), runs the stored input, then stores the result. Two concurrent clicks execute once; a crash leaves a re-claimable row. The agent never holds a capability.

Replay keys are scoped ${operation}:${targetId}:${value} and match only successful rows. Generation awaits inline for 45 s (measured runs finish in 27 s at most) and hands its lease to the cron if it loses the race, because waitUntil ends 30 s after the response. Three new tables in migration 0034, one index on jobs, one var (AGENT_AUTH_ISSUER, in wrangler.jsonc), two dependencies at +7% gzip. A revoked (workos_user_id, client_id) pair stays refused; after any revoke an unseen client lands pending until the owner approves it, because ChatGPT and Cursor mint new client ids. Uploads and trims get daily workspace budgets beside the generation cap.

Build order: door (staging opens on merge, production stays closed), rows and reads, videos, pages, approvals and Settings, docs, handoff page, production. Eight PRs, 24 to 26 pipeline days. The WorkOS auth discovery runs on staging after PR 1 merges and needs William's dashboard steps and approval first.

4. Architecture

Data shapes

// R/agent/registry.ts
import * as z from 'zod/mini';

export type Effect = 'read' | 'write' | 'spend' | 'publish' | 'retract' | 'destroy';
//  read     open while walled (as browser GETs are); not audited
//  write    entitlement; audited
//  spend    write + the daily generation cap (inside createJob)
//  publish  write + human approval; mints, re-exposes or changes what a public URL serves
//  retract  reduces exposure (unpublish); no approval; open while walled (R/trial-wall.ts:223); audited
//  destroy  human approval; irreversible; open while walled, as the browser's DELETE exit is (R/trial-wall.ts:220)

export type Permission = 'leads_contacts';
export type Budget = 'upload' | 'clip';      // daily workspace spend on Mux, separate from exposure

export type Operation<I, O> = {
  name: string;               // ^[a-z][a-z0-9_]{1,63}$. Underscores: Claude's pattern ^[a-zA-Z0-9_-]{1,64}$ forbids dots.
  title: string;
  description: string;        // first 512 characters self-contained (Codex reads them)
  effect: Effect;
  /** write ops whose target can be on a live page: dispatch promotes them to publish when it is. */
  liveExposure?: (ctx: OperationContext, input: I) => Promise<LivePage[]>;
  budget?: Budget;
  requires?: Permission;
  destructiveHint: boolean;   // chosen per op (§4 Transport), pinned by the table test
  target: (input: I) => string | null;        // pageId, videoId or clientKey, for audit and replay keys
  idempotency: { kind: 'natural'; field: keyof I & string } | { kind: 'input' } | { kind: 'none' };
  input: z.ZodMiniType<I>;
  /** publish and destroy: the server-held facts the approve page shows, plus a digest of them. */
  facts?: (ctx: OperationContext, input: I) => Promise<ApprovalFacts>;
  run: (ctx: OperationContext, input: I) => Promise<O>;
};

export type ApprovalFacts = {
  operation: string;
  targetId: string;
  targetKind: 'page' | 'video';
  revision?: number;                  // publish binds it
  currentShareState: 'off' | 'live';  // read from D1 at render time
  livePages?: LivePage[];             // for promoted video edits: which public pages change
  editorUrl?: string;
  agentAuthored: { label: string; text: string }[];
  digest: string;                     // sha256 of the shown fields plus the target's updated_at
};

export type OperationContext = {
  caller: AgentCaller;
  env: AgentEnv;
  origin: string;
  now: Date;
  waitUntil: (p: Promise<unknown>) => void;
};

Dispatcher, checks in order

  1. Refuse any request carrying a clarity_session cookie (401). /mcp is bearer-only; this is what makes the origin-guard exemption safe.
  2. Verify the signature. Read iss from the unverified payload, map it to exactly one key set (the WorkOS JWKS, or on a pr-N host the preview JWK), and jwtVerify with that single issuer, aud = ${origin}/mcp, RS256, 30 s tolerance. A JWKS fetch error answers 503 auth_unavailable with Retry-After, never 401, because 401 makes every host re-run consent. Refuse an act claim (WorkOS stamps it on impersonation tokens) or a scope without openid. sub must start with user_. client_id, else azp, is required; a token with neither is invalid_token, and seeing one in S3 fails the spike. An unknown bucket would merge every unidentified client's permissions and revocation, so there is none.
  3. First rate limiter, standard keyed agent-sub:<sub>, before any D1 read.
  4. Identity by sub through createAuthAccountMappingStore(env.AUTH_DB).findIdentityByWorkosUserId (packages/auth-identity/src/account-mapping-store.ts:184, the cookie path's read at R/request-identity.ts:24-25). No row is 403 no_account with a sign-up URL. AUTH_DB unbound is 503, so neither fail-open (R/trial-wall.ts:62-64, R/trial-offer-with-stripe-sync.ts:26-29) is inherited.
  5. Connection row by (workos_user_id, client_id). revoked answers 403 connection_revoked, whatever the token. pending answers 403 connection_pending with the Settings URL. An absent row is refused connection_limit when the user already holds ten, inserted pending when the user has any revoked row, and inserted active otherwise. A set caller.suspendedAt answers 403 for every effect, as the wall does (R/trial-wall.ts:84). Stamp last_used_at at most once a minute.
  6. Resolve the operation, parse input with op.input. An ungranted requires answers permission_required.
  7. Second rate limiter keyed agent:<connectionId>, standard (60/min) for read, write and retract; strict (10/min) for spend, publish and destroy. Both use the existing bindings (R/rate-limit.ts:38, wrangler.jsonc:36-47); neither reads the IP header.
  8. Compute the effect. op.effect, except that a write whose liveExposure returns pages becomes publish for this call.
  9. Entitlement, when entitlementRequired(effect) holds (write, spend, publish). Call readWindowTrialOfferWithStripeSync(env, ownerId, now) (R/trial-offer-with-stripe-sync.ts:21-57). A walled verdict is cached per connection for five minutes in the isolate, so a retrying walled agent costs one Stripe call, not sixty a minute. A thrown Stripe error answers 503; the browser wall lets that request through (R/trial-wall.ts:93-100) and a bearer path must not.
  10. Budget, when op.budget is set. Count today's ok rows for this workspace and operation in agent_actions; at the limit answer budget_exhausted.
  11. Replay, when effect !== 'read' and the operation has a key. The key is ${operation}:${target}:${value} and the lookup matches outcome = 'ok' rows only. The same input_hash returns result_json; a different one refuses idempotency_conflict. Refused and failed rows are audit only and never block a retry.
  12. For publish or destroy, re-check the exposure the op guards; videos_share_page on an already-live page answers the existing URL here with no approval, because nothing new is exposed. Otherwise find or insert the pending agent_approvals row for (connection_id, operation, input_hash). In the same batch a pending row past expires_at is retired to lapsed first, so an expired ask never blocks a new one. A row denied within the last ten minutes answers recently_denied. Answer approval_required; op.run does not run.
  13. op.run(ctx, input). The generation cap lives inside createJob (§7).
  14. For effect !== 'read', insert agent_actions with a server-minted uuid id (never the JSON-RPC id, which every connection's first call sets to 1). Return.

The audit row lands after the effect, not in its batch, because saveDraft (R/public-page-delivery/journey-page-content-store.ts:216) and publishJourneyPage (R/journey-page-access.ts:73-85) own their batches. A crash between them leaves the effect without its row; every keyed write converges on re-run.

Transport

Hand-rolled JSON-RPC over POST /mcp, stateless, tools only. Every host speaks the 2025-xx lane today (Claude follows 2025-03-26 to 2025-11-25, research §6), so v1 answers initialize (negotiating 2025-11-25 down to 2025-03-26), notifications/initialized (202), ping, tools/list and tools/call, refuses JSON-RPC batch arrays with -32600, and answers 405 on GET and DELETE. The 2026-07-28 server/discover lane is built when a host sends it; the prototype proved it only against the Inspector CLI. tools/list is derived from OPERATIONS. inputSchema comes from z.toJSONSchema; readOnlyHint is effect === 'read'; destructiveHint is true for destroy, retract, publish and overwriting writes (pages_update, videos_edit, videos_update) and false for creates, so hosts that honour the hint do not confirm every draft edit; idempotentHint is idempotency.kind !== 'none'; openWorldHint false. AuthKit setup

AuthKit is the OAuth authorization server; Clarity is a protected resource that verifies tokens locally. Dashboard, Connect → Configuration: CIMD on (off by default, research §1), DCR on for Cursor, Resource Indicators for staging, later production, and a test of the preview wildcard https://*.clarity-video.workers.dev/mcp (§8). JWT checks

// R/agent/caller.ts
const keySets = new Map<string, ReturnType<typeof createRemoteJWKSet> | ReturnType<typeof createLocalJWKSet>>();

export async function authenticateBearer(request: Request, env: AgentEnv): Promise<VerifiedToken | Refusal> {
  if (request.headers.get('Cookie')?.includes('clarity_session=')) return { code: 'unauthorized' };
  const token = bearerFrom(request);
  if (!token) return { code: 'unauthorized' };
  const origin = new URL(request.url).origin;
  const issuer = decodeJwt(token).iss;                       // unverified; used only to pick one key set
  const keys = keySetFor(env, origin, issuer);               // WorkOS JWKS when issuer === AGENT_AUTH_ISSUER;
                                                             // the preview JWK when issuer === origin on a pr-N host
                                                             // with AGENT_PREVIEW_JWKS set; otherwise invalid_token
  let payload;
  try {
    ({ payload } = await jwtVerify(token, keys, { algorithms: ['RS256'], issuer, audience: `${origin}/mcp`, clockTolerance: 30 }));
  } catch (error) {
    return isJwksFetchError(error) ? { code: 'auth_unavailable', retryAfterSeconds: 30 } : { code: 'invalid_token' };
  }
  if ('act' in payload) return { code: 'invalid_token' };
  if (!scopeIncludes(payload.scope, 'openid')) return { code: 'invalid_token' };
  if (typeof payload.sub !== 'string' || !payload.sub.startsWith('user_')) return { code: 'invalid_token' };
  const clientId = stringClaim(payload.client_id) ?? stringClaim(payload.azp);
  if (!clientId) return { code: 'invalid_token' };
  return { sub: payload.sub, clientId };
}

Connection lifecycle and the revocation rule

One row per (workos_user_id, client_id) for the life of the account, unique on that pair. status is active, pending or revoked. Revoke in Settings flips a row to revoked; every later call from that pair is refused at step 5, including a call with a token refreshed an hour later. Re-enable flips it back and stamps enabled_at, so the history stays. Two hosts have no stable client id. ChatGPT uses a per-connection CIMD URL (https://chatgpt.com/oauth/{callback_id}/client.json, because AuthKit does not advertise authorization_response_iss_parameter_supported, research §1) and Cursor's DCR mints a new id per registration, so removing and re-adding the connector would mint a fresh active pair with no Settings click. Once a user has any revoked row, every unseen pair is therefore inserted pending and refused until the owner approves it in Settings, and a user holds at most ten connections. The WorkOS authorized-application DELETE is not called in v1. Its effect on refresh is undocumented, the id form it accepts is unconfirmed, and the row is the mechanism; it is listed as a flip (§12).

client_name comes from the CIMD document, fetched once at insert with a 3 s timeout and no redirects (the URL is caller-chosen), capped at 64 characters and shown as "named by the client", never as a headline.

Bearer identity resolves by workos_user_id only. The cookie callback also links by external_id (R/workos-account-link.ts), so an account whose row carries a different WorkOS id gets no_account from the agent while the browser works. A documented gap; the fix is to reuse the callback's read-only linking if a user hits it.

-- Agents reach Clarity through /mcp with an AuthKit bearer token. WorkOS holds
-- the consent; these tables hold what WorkOS cannot for an org-less user: which
-- client a person connected, whether they revoked, re-enabled or approved it
-- here, which extra permissions they granted it, every write an agent made, and
-- the human decisions behind the writes that publish or destroy.
--
-- agent_connections is one row per (workos_user_id, client_id) for the life of
-- the account. A revoked row refuses every token, refreshed or not, until the
-- owner re-enables it. Once a user has revoked anything, an unseen client lands
-- pending and waits for the owner. WorkOS's own revocation is not relied on.
--
-- agent_actions is the audit log and the replay store. A replayed request finds
-- its ok row by (connection_id, idempotency_key) and answers result_json
-- unchanged; refused and failed rows are audit only. Reads are not recorded.
-- router.scheduled sweeps rows older than 90 days (previews run no cron).
--
-- agent_approvals: pending -> executing (the owner's click claims the row) ->
-- approved with result_json, or failed with detail. An executing row older
-- than 60 s may be re-claimed; every guarded operation converges on re-run.
-- Expiry is read from expires_at and expired pending rows lapse lazily when the
-- same request is asked again. A publish is stale when journey_pages.revision
-- moved; other facts are stale when facts_digest no longer matches.
--
-- IF NOT EXISTS throughout: a stack deploy applies this about a minute before

The handler:

  1. Row by id; user_id matches; expires_at > now, else 409 expired. Connection still active, else 409 connection_revoked. Rebuild the AgentCaller from a fresh identity read.
  2. Re-parse input_json with op.input (a 24 h window spans deploys). Recompute op.facts; if digest differs from facts_digest, or for publish journey_pages.revision !== input.revision, answer 409 stale and leave the row pending.

Approvals. Publish and destroy never run from the agent's call. Prompt injection, the residual risk. pages_leads and contacts_list return prospect-typed text, off until the owner turns leads_contacts on, wrapped as untrusted. pages_get returns a document that generation filled from pasted contexts and that an earlier agent session may have written, also wrapped.
