WIL-3494 design: the server owns every recording

Linear: WIL-3494. Status: waiting for your sign-off. No migration or code PR starts until you approve it.

The decision

Today the browser tab runs the recording's transaction. The server only learns a take exists when the tab claims it after Stop, so every closed tab, dropped request or race leaves a stranded take or an error on screen.

This design flips that around:

  • The server creates the video when you press Record. The video, its Library entry and its share page are created in one database transaction. A take therefore always has its link, or nothing exists at all.
  • Facts get their own table. What Mux and the server know (upload, asset, readiness, duration, poster, clip, timestamps) moves from a 169-key JSON blob into a typed videos table that no browser request can write. The JSON keeps only what the rep edits.
  • One module owns the lifecycle. A module with five methods (grant, finish, observe, settle, discard) decides every state change through one tested state table. The webhook, read-time settling and a nightly Mux inventory all feed that same table.
  • The recorder becomes thin. It keeps a take's bytes on disk until the server says the video is ready. The only message it can still show is "Couldn't upload your recording", and only when Mux rejected the content, with no dead-end Try again. Everything else retries quietly, and the browser's own "Leave site?" prompt is the only warning, shown only while closing would lose work.

What reps notice

Nothing new on screen. The share-link, save and size errors are already gone (shipped today: #900, #901, #903, #902; see the states page). After this program, a closed tab, a lost connection or Mux being slow no longer strands a take. The upload error appears only for content Mux cannot use.

What you are approving

  • A schema change to the videos data.
  • A new videos table and a rebuilt jobs table, so clips and Mux deletions become retried jobs.
  • A backfill of 7,515 production videos, gated on zero differences.
  • A final shrink of the old JSON. Every row's original JSON is archived first, and the shrink is blocked if any of the 169 keys is unmapped.
  • Nine stacked PRs, expand then flip, each proven on staging. Effort is about 33 to 51 engineer-days. Old tabs keep working for their 7 days, and old recovery journals keep working indefinitely.
  • A nightly Mux inventory that reports only, until you have seen a week of its reports. After that it deletes orphaned Mux objects tagged with its own environment.

Questions only you can answer

  1. Should a take still being recorded show in the Library? The default is yes, as "processing".
  2. When Mux rejects a take, should the recorder drop the stale detail line ("It's still safe in this tab. Check your connection...") and the Try again button? That removes copy, it doesn't add any.
  3. How long should an upload stay open? This needs a probe of Mux's timeout before PR 5. A 12-hour take needs about 13 hours.
  4. When should never-finished takes be swept? The default is 14 days.
  5. When should the inventory delete, and what happens to preview environments? The default is after two completed scans plus 48 hours, and never for untagged objects.
  6. Should the poster be the browser's frame grab or Mux's still? The black-poster history argues for Mux.
  7. Where should a failed trim clip show outside the recorder, using existing copy?
  8. Analytics: count a video as added when it is finished (this design), or at Record?
  9. Should a 403 count as a terminal rejection or a pause?

WIL-3494 design: server-owned recording lifecycle and a typed videos table

Synthesized from the architect arena (base Opus, grafts per arena/SYNTHESIS.md), revised against interrogate/VERDICT.md. Path prefixes follow investigation.md: E/ is editor/src/, W/ is workers/workspace-tree/src/, R/ is workers/frontend-router/src/, M/ is workers/frontend-router/migrations-auth/.

Problem

The browser runs the take's transaction today. It mints the take, asks Mux for an upload, claims a node after Stop, polls for about 88 s, writes metadata twice and then deletes its journal (investigation.md, section 1). The server learns a take exists only at the claim (W/mux-video-ingest.ts:297-331), and the share page commits in a second batch that can fail after the first committed (R/video-share-page.ts:180-204). Every stranded state in rows A to L follows from one of three facts. The server has no row yet (C, D, L). The row and the page commit apart (F). The browser decides a take is done (J, WIL-3451).

Constraints the shape honors: one database with db.batch and no branching on reads; the node id asset:<ws>:video:<firstUploadId> and asset_id = firstUploadId baked into pages and documents; six endpoints old tabs call for 7 days; v1 journals that outlive deploys; a 255-character passthrough; one Mux environment (Spike) shared by staging and previews; no new recorder UI or copy; the Library running in-process in the router with router-only functions (docs/SECURITY.md:13); and a second grant client, the Library file uploader (E/lib/workspace-asset-upload.ts:141-158), which shares the grant and claim endpoints.

Usage (caller's view)

One module, W/video-lifecycle.ts, inside the Library. Every actor that learns something about a take calls it. None of them write or read video SQL.

const videos = library.videos;   // createLibrary({ ..., sharePages }) builds it per request and per cron tick

// Router, POST /api/tree/media/mux/uploads (recorder Start, Library upload, journal recovery, retry grant)
const granted = await videos.grant(scope, { kind: 'recording', clientKey, parentId, retryOf: body.retryOfUploadId ?? null });
//  -> granted {take, upload} | received {take} | rejected {take} | discarded {take}
//  Never 409, never retry_unavailable. The same clientKey replays the same take and the same uploadUrl.

// Router, POST /api/tree/media/videos/mux-original (recorder Stop, uploader finish, old tabs' claim and settle poll)
const take = await videos.finish(scope, videoId, { title, parentId, posterUrl, filename, captureStartedAt, captureStoppedAt });

// Mux webhook (after the HMAC check), settle-on-read and the nightly inventory share one entry
for (const o of videos.observationsFrom(verifiedRef, facts)) await videos.observe(o);
//  contended -> 503 so Mux redelivers (WIL-3426); missing or foreign namespace -> 200, counted

// Library delete, recorder Re-record, uploader cancel, the sweep; folder delete uses the set-based form
await videos.discard(scope, videoId, 'rep');
await videos.discardMany(scope, subtreeVideoIds, 'library_delete');   // statements for the subtree batch

The recorder sees only TakeView, derived from the row and never stored.

type TakeView = {
  videoId: VideoId; shareUrl: string | null;    // null for Library uploads, which have no page
  muxHasBytes: boolean;        // an asset exists; closing the tab loses nothing, so atRisk clears
  journalReleasable: boolean;  // true at ready; the only thing that deletes a journal besides discard
  playable: boolean;
  rejection: null | 'unplayable';   // terminal content rejection; the only cause of "Couldn't upload"
  discarded: boolean;               // reset the recorder, delete the journal; not a problem row
};

The thin recorder in the editor:

const take = createRecorderTake({ api, journal, editSaver });   // module scope; survives SPA navigation
take.start(parentId);    // grant in background, keyed by the journal session id; capture never waits on it
take.stop();             // finish (pending until acknowledged) + final chunk; the link came from the grant
take.atRisk();           // the only input to beforeunload
take.view();             // TakeView | null, polled while !journalReleasable
take.discard();          // Re-record

The router hands the Library one narrow port so the page can join the take's batch without an upward import:

const sharePages: SharePagePort = { newTakePage: (input) => ({ pageId, shareUrl, statements }) };

Shape

Load-bearing decisions

  1. The server creates the take at grant for every request that carries a clientKey (the thin recorder's journal session id, the uploader's existing clientId). Requests without a key (old tabs) keep creation at the claim, through adoption. The creation batch is one plain INSERT into videos plus the node and, for recordings, the page draft, publication and route from the port. A conflict on client_key or node_id aborts the whole batch, port statements included; the caller re-reads by key and replays. No ON CONFLICT DO NOTHING on creation, so a losing grant leaves no companion rows. Its Mux upload is enqueued for mux_discard.
  2. Delivery is what Mux has (uploading, processing, ready, failed, stalled). The rep's two acts are stamps on the row, finished_at and discarded_at, independent of delivery. No asset event touches them. failed is a content rejection, which is terminal. stalled means no usable asset and bytes can still revive the take.
  3. Every upload-sourced observation is fenced on current_upload_id; a regrant is fenced on the upload it replaces (retryOf). current_upload_id and upload_generation stay on the row through processing. Legacy imports have no upload provenance, and upload-sourced transitions refuse them.
  4. One pure reducer, transition(video | null, event, now), returns applied {next, effects}, noop or refused {reason}. The shell writes UPDATE videos ... WHERE node_id = ? AND rev = ?old and every effect in the batch is INSERT ... SELECT ... WHERE (SELECT rev FROM videos WHERE node_id = ?) = ?new. Job effects are ON CONFLICT DO NOTHING. Three lost CAS tries return contended. refused reaches the caller so the saver can retry instead of losing intent.
  5. Effects are rows, never calls. Mux mutations happen only in job runners. Mux reads happen only in grant, settle and the inventory, and come back in through observationsFrom and observe.
  6. Typed facts, intent JSON. videos holds every fact the server owns. workspace_nodes.metadata keeps an allowlist of intent keys. One projection at the store's read boundary, a json_set fenced on rev, merges typed columns back into the legacy keys until old tabs are gone.

Jobs and inventory

mux_clip is one job per video, subject = node. The runner reads videos.clip_revision at every step, never its payload span, waits (no failure counted) while delivery is not ready, and fences promotion on the revision it cut. On a stale promotion it discards its asset and loops. When it would go dead and clip_revision advanced since its last cut, it re-arms instead. The runner writes the returned asset id into the payload under the lease fence as soon as Mux answers; a crash before that leaves a namespace-tagged stray the inventory removes after two scans. After 8 failures the job is dead and projectVideoMetadata exposes mux_clip_failed: true with the job's error from the dead row (WIL-3453).

mux_discard takes asset:<id> or upload:<id> as subject and dedupe_key, unique across all states, so a double discard is one row. 404 is done. A 400 counts only after a re-read proves absence (packages/mux/src/client.ts:353 tolerates only 404 today). After 12 failures the job is dead. Ids come only from videos rows.

Policy shared by all kinds. expiredJobs filters by kind and not_before <= now. A failure releases the lease and sets not_before to 5 s x 2^failures, capped at 10 min for clips and 6 h for discards. The 7-day purge deletes done rows; dead rows are purged after 90 days once resolved. rearmJob(id) moves dead back to running after the caller revalidates ownership; its callers are the clip runner's own re-arm, the inventory and the editor's clip retry. Dispatch by kind with budgets of 3 generation, 5 clip and 10 discard per tick (R/journey-page-generation.ts:280-296 ignores kind today). The per-workspace cap is optional per kind; discards have none.

Settle-on-read and the webhook both stay. settle(scope, ids) loads the videos rows in uploading or processing, at most 3 per read newest first, asks Mux and feeds each answer through observationsFrom and observe. The webhook does the same after the HMAC check. observe takes a VerifiedMuxRef ({namespace, workspaceId, by: 'upload' | 'asset' | 'opToken', id}) that only the verified webhook parser and the scoped settle loader can build, and resolves the row itself. missing and foreign-namespace events answer 200 and are counted; contended answers 503.

The inventory runs from the router cron in production and staging. The passthrough becomes v2, {v:2, n:<namespace>, w:<workspaceId>, id:<firstUploadId>, k:<clientKey or opToken>}, length-checked under 255 (namespace 12, workspace 41, upload id 32, key 36, labels 30). The namespace is the MUX_NAMESPACE var the deploy workflow sets from the D1 database id for previews and fixes to prod and stg otherwise (.github/workflows/cloudflare-deploy.yml:200). The parser keeps reading v1. The nightly tick opens a scan of uploads and assets; the minute cron advances bounded pages and stores cursors. Classes: live (a live row owns it), stray (a discarded row owns it, or a second asset of a take), orphan (tagged with this namespace, no row), foreign (another namespace), unknown (untagged). Only stray and orphan are eligible. Deletion needs two completed scans that saw the object plus a fresh reference check against videos and running jobs, and always runs as a mux_discard job. foreign and unknown are quarantined and counted, never deleted, which is how staging leaves preview assets alone. The scan also feeds assetGone for rows whose asset Mux lacks, sweeps unfinished rows past the horizon, and settles anything unsettled for 24 h. Counts land in video-telemetry. The first release reports only.

The recorder and the uploader as thin clients

The browser owns capture, the bytes until the server says they are releasable, the chunked PUT, unacknowledged finish and edit intent, and the leave prompt.

The journal is the bytes of a take. A v2 journal records {clientKey, videoId, uploadId, generation, status}. It is deleted when journalReleasable is true, on discard, or on Re-record. On rejection it is marked rejected with a TTL equal to the sweep horizon, kept, and never offered for automatic recovery. A take that stalls after processing (operational error, asset gone) keeps its journal, so the existing recovery card on the next /record visit revives it. A v1 journal has an uploadId and no videoId; recovery sends grant({clientKey: sessionId, retryOf: uploadId}).

Grant precedence, stated once, key first. (a) A live row for clientKey. (b) No keyed row, and a row whose source or current upload is retryOf. (c) A key-less or v1 request whose retryOf no row owns: adopt when the passthrough names this workspace, deriving the node id from the passthrough's first upload, else a fresh take. A request that carries a key never adopts. (d) Otherwise create. On a row found by (a) or (b): delivery is processing or ready (Mux holds a usable asset), answer received; retryOf is the current upload, or the current upload has ended (upload_url NULL), regrant against it; otherwise replay the current upload and upload_url. A replay therefore never hands back a null URL, and a retry naming a long-superseded upload returns the current one instead of adopting a second take. The losing Mux upload of any race is enqueued for mux_discard.

Local state is {phase: idle | capturing | paused | stopped, take, bytesHeldLocally, finishUnacked, editsUnacked, discardUnacked}. The predicate is

atRisk = !take?.discarded && (capturing || paused || (!take?.muxHasBytes && bytesHeldLocally)
         || finishUnacked || editsUnacked || discardUnacked)

where bytesHeldLocally covers a journal with bytes and memory-only capture (row H). The module-scoped take manager arms beforeunload on it and nothing else. The "upload" problem row shows iff take.rejection !== null, with the existing title and no Try again. A discarded take resets the recorder. Memory-only capture is the one case where closing after muxHasBytes can still lose bytes to a later operational error; that is accepted so the prompt does not stay up through processing.

Edits ride #901's saver (E/lib/recorder-edit-saver.ts) with its give-up removed. finish intent and edit intent are both pending until the server acknowledges a revision. An API refusal keeps the pending intent, keeps the prompt armed and emits recorder_edit_refused telemetry. A refused conflict re-reads the row and reapplies only the rep's changed fields. flush() resolves when the captured revision is acknowledged.

The Library uploader (E/lib/workspace-asset-upload.ts) sends kind: 'upload' with its clientId as clientKey, gets a row and node with no page and no card, calls finish instead of the claim and discard on cancel.

Every transient failure (network, 5xx, 408, 409, 429, 401 while the session refreshes) retries quietly with the backoff from the quiet-upload-retry branch. A Mux 4xx on a chunk regrants with retryOf rather than giving up.

Sequences

Normal take. Start opens the journal and calls grant in the background with the session id as clientKey; the server reads by key, calls Mux createDirectUpload (passthrough v2, the probed timeout), then commits one batch and returns {take, upload}. Chunks stream from the journal. Stop sends finish (pending until acknowledged) and the final PUT, in either order; the link has been in hand since the grant. Mux's upload.asset_created makes the take processing and clears the prompt; asset.ready makes it ready and releases the journal. Edits go to the saver; a trim bumps clip_revision and enqueues the one clip job.

The strands. The table above covers each; this list names only the delta.

  • A, closed while recording. The prompt arms during capture. The row is uploading, unfinished, listed as processing. In the same browser, recovery regrants (a) and resends. If the rep never returns, the sweep discards it.
  • B, closed after Stop, prompt ignored. finished_at is set, the link may be shared. The upload times out, stalled, card reads "This upload did not finish." Recovery regrants into the same video.
  • C, recovered take whose upload died. (a) finds the row. A v1 journal with no row is adopted with its page in one batch, then regranted. If Mux forgot the upload, a fresh take. No branch answers retry_unavailable.
  • D, retry grant beats the claim. Gone. A regrant needs only the row.
  • E, Mux rejects the content. failed, rejection = unplayable, the existing title once, no Try again. The journal is marked rejected with a TTL. An operational error instead goes stalled and the surviving journal revives it.
  • F, share page fails. It cannot fail apart from the video; a failed batch is retried quietly. A cross-owner collision on adoption gives the take its own page and reports the collision.
  • G, Back to Library mid-upload. The take manager survives navigation.
  • H, no journal. Memory bytes keep the prompt until muxHasBytes.
  • I, journal cannot be reassembled. The loss is real; the row stalls and is swept or shows the stalled card.
  • J, settle times out, then Mux errors. The client never declares success; it keeps the journal until ready. A late content rejection is unplayable; a late operational error stalls and the journal revives it.
  • K, finalize throws at Stop. stop() seals the journal regardless; the pump sends the sealed bytes.
  • L, Stop before the grant returned. The pump queues behind the grant, which retries the same clientKey. A lost response replays; a racing create aborts on the key and replays.
  • Uploader. Grant with kind: 'upload', bytes, finish. Cancel is discard. The webhook beating finish is harmless because finished is a stamp, not a state.

Acceptance criteria

  • No share-link-failed state. The page commits with the video at grant or at adoption, or neither commits; a losing batch leaves no page.
  • No save-failed state. Server facts are not browser writes. Finish and edit intent stay pending until acknowledged; a refused answer is retried, never dropped.
  • "Couldn't upload your recording" only on a terminal rejection, never a dead-end Try again. It shows iff rejection is non-null, which needs the classifier's content rejection. Discard is not a rejection. C loses its dead end because the grant always answers; E loses it because no Try again is offered.
  • Transient failures retried quietly under the leave prompt. Every non-rejection outcome is a wait, and atRisk covers capture, pause, unreceived bytes, unacked finish, unacked edits and unacked discards.
  • No new UI or copy. TakeView replaces state and adds none. The recovery card and the processing card exist today. The only candidate copy change is removing a line (open question 2).

Security note

Every browser-reachable lifecycle method takes a WorkspaceScope the router built from the session, never from the body (docs/SECURITY.md:11-12). observe is router-only and takes a VerifiedMuxRef only the HMAC-verified parser or the scoped settle loader can construct (:13, :17). Mux ids, readiness and posters are columns no browser route maps to; browser JSON writes pass an allowlist. A discard deletes only ids read from videos. upload_url is a credential, stored until Mux has an asset, cleared after, never logged. Playback ids leave the server only through the projection on reads already scoped by workspace or by a live publication (:23); TakeView carries none. parentId is checked against a folder in this workspace at grant, finish and adoption, else root. The inventory deletes only objects tagged with its own namespace and referenced by no row. A finish posterUrl must resolve to this workspace's R2 upload prefix or it is dropped.

The five acceptance criteria were re-checked against the revised table and predicate and still hold; the acceptance section above states each.

Tradeoffs accepted

  • We accept an empty Mux upload when a grant's batch fails after the Mux create, in exchange for no request or attempt tables. The loser is enqueued for discard once a runner exists, else it expires and the inventory reports it.
  • We accept a row and a cardless page for every abandoned keyed take plus a sweep, in exchange for the grant being the single creation point that removes C, D, F and L.
  • We accept one port, sharePages.newTakePage, handed from the router into the Library, in exchange for one batch per take without moving the page builder across the boundary.
  • We accept a stray clip asset when the runner dies between the Mux create and its payload write, in exchange for no clip operation table.
  • We accept keeping bytes on disk until ready, including a rejected journal under a TTL, in exchange for operational errors after processing being recoverable without new UI.
  • We accept that memory-only capture can lose bytes to an operational error after processing, in exchange for the prompt clearing once Mux has an asset.
  • We accept a reducer plus rev CAS over pure-SQL guarded updates, in exchange for one readable, testable source of truth for every transition, creation included.
  • We accept videos rows outliving their nodes with no foreign key, in exchange for retiring video_lifecycles.

Alternatives considered

  • A request table written before the Mux call (Astra's shape). It attributes every Mux object. It lost because the same replay comes from a key column plus abort semantics, and the residual case is an expiring upload.
  • Two axes, delivery and disposition (the original Opus shape). It lost in review because any rule that lets an asset event move disposition forges Stop, and a rule that forbids it leaves kept with no purpose a stamp does not serve.
  • Create at Stop with the page in that batch. Simpler and fixes F, but leaves C, D and L, and has no record-start timestamp.
  • A server-minted take id in the passthrough. Cleaner identity, but it breaks the one-id scheme in pages and documents.
  • A Cloudflare Workflow per take. A second durable store beside a row the webhook and settle already converge on.

export function recorderAtRisk(state: {
  phase: RecorderPhase; take: TakeView | null; bytesHeldLocally: boolean;
  finishUnacked: boolean; editsUnacked: boolean; discardUnacked: boolean;
}): boolean {
  if (state.take?.discarded) return false;
  return state.phase === 'capturing'
    || state.phase === 'paused'
    || (!state.take?.muxHasBytes && state.bytesHeldLocally)
    || state.finishUnacked
    || state.editsUnacked
    || state.discardUnacked;
}
