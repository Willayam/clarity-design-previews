Password trade-off and limits

A successful set or approval card triggers the scrub. A refused set leaves the thread unchanged. Same-step password sets run before generation. Stored human text, source text, tool arguments, detail, modelResult and combined text chunks are scrubbed without rewriting operation names, IDs or state. Existing markers are protected, and a password containing the marker is refused.

Distinctive mixed-character passwords are scrubbed on whole-token matches. Short values, all-letter words and numeric-only values are scrubbed in explicit password assignments and password fields, plus an isolated current password reply. This keeps a password of Acme from replacing the company name and a password of 1000 from deleting the price. The trade-off is that incidental common-word occurrences can remain in stored prose or other text fields. I do not claim complete plaintext removal.

The first provider request and live deltas can already contain the typed value. Earlier forwarded requests cannot be recalled. There is a narrow crash window between the successful action and scrub. Existing page extras and saved generation job bases may retain plaintext; writer prompts exclude extras. These remain, and the final model/runtime password proof is incomplete.
