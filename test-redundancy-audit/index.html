The suite is mostly lean. Whole-file deletion is 6 files and about 1,200 lines. The larger payoff is structural: dead code, source-text greps, and hand-rolled SQL fakes.

Patterns

Dead production code with a test attached. Four of the six KILLs, and two TRIMs, test functions nothing in production calls: hasProtectedEditorAuthSession, buildJourneyPagePresentationSurface, scripts/lib/r2-cors-origin.mjs, journeyPageSummaryFromMetadata, verifyActiveRoutesResolveToContent. The test is what keeps the dead code alive. Delete the code and its test in the same change.

Tests that grep source text. Seven files read .ts, .sql, wrangler.jsonc, justfile, or index.html and assert substrings (S = 0), and auth-door.test.ts and deploy-config.test.sh carry a few more such cases. They break on harmless rewording and miss real breakage. Where the guarded thing can execute (migrations through the SQLite helpers, the theme boot script, deploy-convex.sh dry runs), test it by running it. Keep text greps only for pure config wiring with no runtime to drive.

Hand-rolled SQL fakes next to a real SQLite harness. workspace-tree-store, workspace-brand-store, editor generated-output-jobs, and frontend-router-billing each ship a fake D1 that pattern-matches SQL text and re-implements it in JavaScript. workspace-tree-store spends 270 of its 688 lines on one. workers/workspace-tree/tests/helpers/sqlite-workspace-tree-db.ts and editor/tests/helpers/sqlite-auth-db.ts already run the real migrations. Moving onto them cuts lines and catches real SQL bugs.

Worker behavior tested twice, once from editor/tests. editor/tests holds tests for workspace-tree internals that duplicate workers/workspace-tree/tests at lower fidelity (faststart attempts, posters, generated-output jobs). The worker package is the right home. The MERGE verdicts fold the unique cases there.

A test that passes for the wrong reason. poster-digest.test.ts "skips poster generation when the existing digest matches including trim" sets poster_digest, which no production code reads. It passes only because the fixture also sets poster_url, which trips an unrelated guard.

Rubric

# Test redundancy rubric

Goal: find test files, or cases inside them, that can be deleted or merged without losing protection. A test earns its place by catching a bug no other test catches, through the interface callers actually use.

Score every test file on six dimensions, 0 to 3 each. Higher is better (more reason to keep).

## U. Unique protection (weight 3)

If this file were deleted, which regressions would ship silently?

- 3. Behavior no other test exercises. Deleting it opens a real hole.
- 2. Mostly unique; a few cases duplicated elsewhere.
- 1. Most cases re-assert behavior another file already asserts (same module, same inputs, same outcome).
- 0. Fully subsumed by another file (name it, with file:line).

You must open the files listed in `shared_targets` for overlap before scoring U below 3 or at 3. A U of 0 or 1 without a named covering test is invalid.

## S. Seam (weight 2)

Does it test through the module's interface (codebase-design: "the interface is the test surface")?

- 3. Drives the public interface (HTTP route, exported function, rendered component via user events). Would survive an internal refactor.
- 2. Public interface, but with a few mocks of internal collaborators.
- 1. Reaches past the interface: private helpers, internal state, heavy vi.mock of own modules.
- 0. Asserts implementation text: reads source files and greps them, snapshots internal structure, asserts call counts on internals.

## V. Stakes (weight 2)

What does the guarded behavior cost if it breaks?

- 3. Security, auth, money, data loss, a named past incident.
- 2. Core user flow (edit, record, upload, publish, view).
- 1. Secondary behavior, cosmetic, copy, config value.
- 0. Nothing a user or operator would notice; or the compiler, a type, a lint rule, or a runtime guard already enforces it.

## L. Liveness (weight 2)

- 3. Target code is live and on a hot path.
- 2. Live but rarely changed.
- 1. Target is a one-shot tool: a completed migration, backfill, spike, benchmark, or one-time verification.
- 0. Target is dead, retired, or no longer imported by production code; or the test is skipped/opt-in and nothing runs it.

Check with `git grep` whether production code imports the target, and whether the file is skipped or gated by an env flag.

## F. Fidelity (weight 1)

- 3. Deterministic, asserts outcomes, fails only when behavior breaks.
- 2. Mostly outcome-based; some brittle details.
- 1. Brittle: timing sleeps, exact copy strings, ordering incidentals, large fixtures that mirror implementation.
- 0. Tautological: asserts a mock returns what it was told, or re-implements the code under test to compute the expected value.

## C. Cost (weight 1)

Lines and runtime per unique behavior guarded.

- 3. Small and fast for what it protects.
- 2. Reasonable.
- 1. Large setup or slow (over 500 ms) for modest protection.
- 0. Huge harness or very slow for little.

## Total and verdict

`total = 3U + 2S + 2V + 2L + F + C` (max 33).

Verdict rules, applied in order:

1. **KILL** if L = 0, or U = 0, or total <= 12.
2. **MERGE** into a named file if U <= 1 and the unique remainder is small enough to fold into the covering file.
3. **TRIM** if U >= 2 but specific cases (name them) are duplicated, tautological, or assert implementation text.
4. **KEEP** otherwise.

Downgrade only on evidence. When unsure, say KEEP with confidence `low`, not KILL.
