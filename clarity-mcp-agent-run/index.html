Clarity MCP: fresh-agent run and landing page

Five agents with no Clarity context, eight ordinary requests each, against isolated staging accounts. The full per-task record with every answer, tool call and agent feedback is in the run report. Account emails are redacted.

Findings

Five fresh agents (Claude fable, opus and sonnet through claude -p; gpt-6-sol and gpt-6-astra through codex exec) each ran eight tasks against the staging MCP connector on their own accounts. Measured: 39 of 40 cells passed. The count is high because every task was winnable with the nine tools, or was a gap task where saying "I cannot" counts as a pass. The signal is what each model family paid in calls, errors and seconds, and what the agents said afterwards. Every number is measured from report.json and the raw call logs unless marked as inference.

Friction, ranked by cost

1. Codex hosts cannot see the pages_edit schema, so they guess op names

The served edits schema is an anyOf of 38 variants, 15,601 bytes. Codex renders it as Array<unknown | ...>. The first pages_edit call in all 6 Codex write cells failed with invalid_input on an invented op such as set, set_block_fields or set_media, and the refusal lists the mismatch against every variant. 8 of 16 Codex cells named the unknown type and 6 named the error dump. Claude seats, which see the schema, made 10 pages_edit calls with 0 errors.

Evidence: "pages_edit.edits exposed only unknown types, hiding the supported operations and required fields." (gpt-6-astra, edit-headline)

Smallest fix: discriminate the union on op so invalid_input reports one variant, and add a one-line example for set_field, insert_item and assign_media.

2. insert_item cannot append to an empty FAQ the way agents try

before: null appends, and the description never says so. Codex seats sent strings instead ("", "end", "$end", "append", "null", "-1" and six more). 16 refusals came back as "Edit 1 was refused (not_found)" with {"id": ""} and no field name (sol 13, astra 3). position: 0 refused twice with stale_position because the seats sent an empty expect where the schema wants null. sol never tried null in 15 attempts and failed the cell; astra found it after 5 errors. Inference from the schema source: sol also put question and answer outside value, which the non-strict object would have dropped.

Evidence: "pages_edit requires before to name an existing FAQ row, which an empty FAQ has none of." (gpt-6-sol, add-faq)

Smallest fix: say "null appends" in the description, and make the not_found refusal name the field and value.

3. insert_block silently drops a fields payload

Measured once. gpt-6-sol sent insert_block with fields: {title, questions: [2 rows]}, got {"revision":4,"changed":true}, and the next pages_get showed questions: []. It then deleted its blocks and reported failure.

Evidence: "Clarity's editor refused every attempt to add the first row to an empty FAQ." (gpt-6-sol, add-faq answer)

Smallest fix: z.strictObject on the insert variants, as insert_plan already uses.

4. pages_edit answers {revision, changed} and nothing else

11 of 15 successful write cells re-read the page afterwards. 9 of 9 Claude write cells asked for the touched blocks or the publication state in the reply. All 5 edit-headline cells had to compare revision with publishedRevision to learn the live page was now behind the draft.

Evidence: "I had to call pages_get again and compare revision with publication.publishedRevision." (opus, edit-headline)

Smallest fix: return publishedRevision and stage with every edit, plus the touched blocks.

5. Every permission refusal points at a page that answers 404

4 of 5 form-leads cells called pages_leads and got settingsUrl: https://staging.clarity.video/settings/agents; 4 of 5 answers passed that URL to the user. The lead verified the page answers 404 and the editor has no agent-connections settings, so no user can grant the permission today. Cheap for agents, total for the user. Two seats noted the name is leadsContacts in whoami and leads_contacts in refusals.

Evidence: "The permission_required refusal gave a settingsUrl but no wording I could pass on." (opus, form-leads)

Smallest fix: ship the settings page the URL names, and use one permission name.

6. library_list cannot answer "ready to share", and nothing returns a video share URL

All 5 list-videos cells fanned out to videos_get once per video (15 calls for 3 videos) because list items carry only state. videos_get then reports shareLinkLive: true with only Mux playback and poster URLs; 5 of 5 seats said they could not hand the user a link.

Evidence: "playbackUrl is a raw HLS stream, not something to send a prospect." (sonnet, list-videos)

Smallest fix: add shareLinkLive, durationSeconds and shareUrl to list items and shareUrl to videos_get.

7. pages_stats cannot count form submissions, and its zeros are unexplained

5 of 5 form-leads cells asked for a submission count that needs no leads permission. 5 of 5 page-views cells said visits and totalVisits differ without explanation and that there is no "as of" timestamp.

Evidence: "If they had disagreed, I wouldn't have known which one to report." (opus, page-views)

Smallest fix: a per-form submission count, a lastVisitAt, and one sentence defining the two visit fields.

Lower cost: 4 Claude cells guessed the set_field name title from the document dump with 0 errors, and 7 cells said pages_get documents are mostly empty media fields.

What worked

All 15 gap cells passed the blind judge; every answer said plainly that upload, publishing or page creation was unavailable and pointed to the editor. The one failed cell was honest: sol said the FAQ still needed adding and removed the empty blocks it had created. Claude seats finished every write in 3 to 6 calls with no pages_edit errors. Median latency per tool was 41 to 194 ms; the one outlier was a 20.4 second whoami (gpt-6-sol, form-leads).

Harness artifact: 12 of 24 Claude cells said the whoami email did not match the user's email. Claude seats saw the operator's account email in their system prompt, so this is excluded above.
