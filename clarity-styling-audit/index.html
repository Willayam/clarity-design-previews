Part 1: How styling works

Overview

Clarity's styling is not one system. It is six, plus inline styles as a cross-cutting mechanism, and only one of the six is the "Tailwind v4 + shadcn" system the docs describe. The editor SPA carries a genuinely idiomatic Tailwind v4 theme and a Base UI + cva primitives layer (editor/src/index.css, editor/src/components/ui/), but it sits on top of 10,966 lines of hand-written, unlayered CSS (24 numbered legacy partials, 16 colocated component/route stylesheets, and two bespoke "glass" surface languages) that, because it is unlayered, beats every Tailwind utility in the cascade. Outside the SPA, published journey pages are styled by a completely separate attribute-driven token system (--jp-*) held in a TypeScript string and rendered by two independent renderers (worker SSR and the editor's LivePreview), and a handful of worker pages carry their own private <style> template strings with hand-copied tokens.

The repo declared a migration from the legacy CSS to Tailwind + shadcn in June 2026, split the old monolith into partials, and then deleted its own roadmap the same day. Since then roughly 10x more styling commits have landed in the legacy layer than in the design system, the partials have grown 13%, and the newest large features (the editor canvas, the auth flow) were written in the legacy idiom. Enforcement is inverted: the strongest CSS discipline in the repo protects the published page (ADR 0007, machine-checked), while the editor's design-system lint is uncommitted, warn-level, and invisible to every automated path. This document maps the systems, the cascade inversion, the token copies, the dual renderers, and what actually gates a merge.

Key Concepts

  • The theme entry (editor/src/index.css, 179 lines): the only Tailwind v4 file. @import "tailwindcss", @theme inline mapping utility names onto --* tokens, :root/.dark oklch values (slate neutrals, brand blue #2563eb), @custom-variant dark. Loaded eagerly on every SPA route from main.tsx:13.
  • Cascade layers: Tailwind v4 emits everything inside @layer theme/base/components/utilities. Unlayered CSS outranks all layered CSS regardless of specificity. Everything in this repo except index.css is unlayered, on purpose. This single fact explains most surprising behavior.
  • Primitives (editor/src/components/ui/, 22 tsx files): shadcn-style components on @base-ui/react (not Radix), styled with Tailwind + cva, merged via cn() = twMerge(clsx(...)) (editor/src/lib/utils.ts). State is expressed through data-* attributes (the base-nova variant vocabulary from shadcn/tailwind.css).
  • Surface languages: two hand-written unlayered CSS dialects in the primitives folder. button-surface.css ("Halo Glass", 285 lines) paints every Button via data-button-variant attributes; chrome.css (.cg-*, 161 lines) is the glass toolbar/panel family. Both derive from --glass-* theme tokens.
  • Legacy partials (editor/src/styles/00-*.css ... 25-*.css, 24 files, 7,398 lines): the pre-migration stylesheet, split from a 6.6k-line monolith in June 2026, aggregated by editor/src/styles.css and loaded only inside the authenticated app.
  • The journey-page system (packages/journey-page-domain/src/journey-page-styles.ts, 883 lines of TS holding 31.5 KB of CSS): the published-page stylesheet. Its own --jp-* token ladder, scoped to .jp-theme, styled almost entirely via data-journey-* / data-module-kind attributes. Shared verbatim by the worker SSR and the editor preview.
  • The migration: styles.css's header comment ("Migration target: replace these with Tailwind utilities + shadcn primitives. Delete a partial as it empties out.") is the entire written policy. No ADR, owner, or exit criterion exists.
  • The ratchet: eslint.config.mjs errors on raw <button>/<input>/... outside components/ui/ with a shrink-only per-file baseline (eslint-suppressions.json). It is the repo's proof that ratcheting works; nothing equivalent exists for CSS.

How It Works

The systems, enumerated

Explorer counts of "five" vs "six" systems differ only on grouping; here is the reconciled inventory. Everything below editor/src totals 11,145 CSS lines across 44 files.

  1. Tailwind v4 + shadcn design system. index.css (theme, tokens, @layer base) plus the 22 primitives. 18 of the primitives are pure Tailwind + cva with no hand-written CSS (card.tsx, input.tsx, dialog.tsx are close to unforked upstream). Only 5 cva() call sites exist (button, badge, sidebar, tabs, button-group). Global on every route.
  2. Unlayered chrome CSS inside the design system. button-surface.css (imported by index.css, so global: "auth and public pages have buttons too") and chrome.css (imported by styles.css and directly by VideoPlayer.tsx:15 so the player's glass works on public routes; it therefore ships twice). These are the design system's own appearance layer, written as unlayered CSS keyed off data attributes so they beat the cva color classes without !important.
  3. The 24 numbered legacy partials, 7,398 lines, reachable only through styles.css, which is imported exactly once, from routes/ProtectedEditorLayout.tsx:21, a lazily loaded route. Flat kebab class names with at least four competing prefix idioms (app-sidebar-*, mp-/cpk-/ste- abbreviations, real BEM in places, is-* state classes). The numbering gaps (03-buttons, 15-preview-modal) are the migration's only two completed deletions.
  4. Colocated per-component and per-route CSS, 16 files, 3,088 lines: 11 component files (MediaPicker.css 366, SummaryTableEditor.css 300, ...) each imported from its own tsx, and 5 route files (LoginRoute.css 640, PublicHomeRoute.css 328, TermsRoute.css 205, PrivacyRoute.css 198, TeamsRoute.css 28). Same idiom as the partials but outside the aggregator's declared cascade order.
  5. The journey-page system. journey-page-styles.ts + theme.ts (document-to-custom-property resolver) + theme-presets.ts (6 presets, each a CSS string). Delivered two ways: the worker inlines it into one <style> in <head> (render-shell.ts:86), and LivePreview.tsx:54-107 appends it to document.head at runtime as <style id="jp-theme-css"> plus two mutable singletons for preset CSS and Google Fonts. Note packages/journey-page-domain is not a pnpm workspace package (no package.json, not in pnpm-workspace.yaml); both consumers import it by deep relative path, and it gets bundled twice.
  6. Worker private template-string CSS. The trial wall (workers/frontend-router/src/trial-wall-page.ts, hand-copies 8 theme tokens and re-implements Button as .app-btn), the internal updates page (internal-updates.ts, zero tokens, literal slate hexes), the password gate (a second <style> injected into <body>, render-blocks.ts:195-262), and transactional email (workers/auth-email/src/templates/base.ts, table layout + style="" attributes).

Cross-cutting: ~84 inline style={} sites in tsx. Explorer 2 hand-classified them: 53 are measured/computed geometry (legitimate), 19 content-derived typography/alignment, 11 user-chosen colors, 4 are the house-blessed custom-property handoff pattern ({'--media-card-accent-hue': ...} consumed by CSS), and only ~16 are static styling that belongs in a class.

Which system a file uses is decided by feature, not by date. The editor canvas and property panels are a closed semantic-CSS world (block-editors.tsx: 81 semantic / 16 Tailwind tokens); settings, admin, dialogs, and marketing are Tailwind-first (PublicHomeRoute.tsx: 251/14). Files created in July 2026 were 44% Tailwind by token share and August files 26%: new code joins the legacy system when it lives in legacy territory. AuthRoute.tsx (created 2026-08-27) is 31 semantic / 0 Tailwind, styled by a 640-line BEM sheet named after a component (LoginRoute.tsx) that no longer exists.

The cascade inversion

index.css:4-6 explains why button-surface.css is unlayered: "Tailwind utilities sit in @layer utilities, so these rules win over the CVA's colour classes without !important." Commit cc7394df (2026-09-10) states it as policy. But the comment frames a targeted trick; in the built output, the entire hand-written layer (10,966 lines) is unlayered and therefore outranks every Tailwind utility, verified: the ProtectedEditorLayout chunk contains zero @layer at-rules.

This inverts the mental model a Tailwind developer brings. A utility can never override a semantic class on the same element. Verified casualty: sidebar.tsx:135 sets bg-[#f6f4ef] (layered utility) while styles/01-app-shell.css:11-14 sets an unlayered gradient on the same element via .editor-shell-frame; the cream never renders. The codebase survives mixing only by a hand convention, held in comments ("geometry always stays with the consumer", chrome.css:8): semantic classes own paint, utilities own box metrics. 45 className strings mix the two, almost all on marketing routes. cn() cannot help; twMerge only understands Tailwind names, so a semantic-vs-utility conflict passes through silently. Only 11 !important occurrences exist, so the convention mostly holds, but nothing enforces it.

Between two unlayered systems, ordinary specificity and source order decide. button-surface.css selectors are (0,2,0) attribute pairs, so they beat single-class partial rules despite loading earlier. 63 class names are defined in more than one editor stylesheet, and 20 of those straddle an ordered partial and an unordered colocated file, so their winner depends on Vite's module evaluation order (media-card-preview is defined in three files; MediaPickerDialog.css deliberately re-skins nine class names owned by 13-journey-index.css and 14-library.css).

The token model and its copies

index.css declares the shadcn core set (--background, --primary, --border, ...) in oklch, hand-swapped to slate/blue from the baseColor: "neutral" (zinc) that components.json still declares. Extensions: --success/--warning/--info (fully wired with dark values, but used only 6 times against 43 raw-palette-color usages that should be them), --sidebar-* (used only inside sidebar.tsx), --glass-* (feeds both surface languages), a 7-step radius ladder, and --chart-1..5 (ten dead declarations still holding stock zinc greys; the lint recommends them as "nearest theme tokens", which would be wrong). Secondary namespaces are derived per context: --btn-* (button-surface.css), --cg-* (chrome.css), --jp-* (journey pages).

There is no shared token package. Every crossing of a bundle boundary is a copy:

  • The trial wall hand-copies 8 of ~45 tokens into a template string (trial-wall-page.ts:51-62, with a candid comment: "Three reviewers across two review rounds called that copy a blocker"). editor/tests/trial-wall-drift.test.ts pins those 8 by regex against index.css, :root only; .dark can drift freely, and the copied button's appearance is unguarded.
  • The --btn-ink/--btn-halo derivation exists byte-identically in three places (button-surface.css:52-53, LoginRoute.css:12-13, 19-record-video.css:410-415).
  • The brand blue exists in at least five forms: oklch in index.css:74, #2563eb in customer-brand.ts, PublicHomeRoute.css, internal-updates.ts, and the auth email, re-copied oklch in the trial wall, and a hard-coded after:bg-[#2563eb] in tabs.tsx:64 that will not desaturate in dark mode the way --primary does.
  • Most subtle: .jp-theme redefines the same token names (--background, --primary, --foreground, ...) in hex on the published-page surface (theme.ts:71-89). Any editor chrome rendered inside the preview silently switches palettes. This is managed entirely by convention and comments (editor/src/lib/theme.ts:1-10; AddSection.tsx mounts "as a sibling of .lp-page, NOT inside it" precisely to escape it).

The partials are mixed, not token-free: ~865 var(--...) reads against 330 raw color literals (77 hex, 130 rgb/rgba, plus oklch), with hotspots in 19-record-video.css, 22-video-edit-modal.css, and PublicHomeRoute.css (74 raw colors). #2563eb appears 7 times raw in the partials, which is exactly what --primary is for. Only 5 of 24 partials contain any .dark selector; the other 19 adapt to dark mode only where they happen to pass through a token.

The two journey-page renderers

ADR 0006 designed per-kind co-located renderers with parity tests and rejected a single shared renderer. The co-location half never happened: BlockDefinition (packages/journey-page-domain/src/blocks.ts:208-216) has no renderer field of either kind. The published page is rendered by a switch in workers/frontend-router/src/public-page-delivery/render-blocks.ts:390-401; the editor preview by a second, independent switch in LivePreview.tsx:211-248, four directories away. They truly share only the stylesheet, the theme resolver, and a few value helpers. Video share pages reuse the SSR renderer (a synthesized document), so they are not a separate surface.

Because the shared stylesheet targets data-journey-* attributes, markup drift is invisible until it changes an attribute. Three confirmed divergences:

  • A standalone logos block is a <div> in SSR (deliberate, tested) but a <section> in the editor (LogosSection.tsx:52-58), which shifts the :nth-of-type(even) section striping for everything after it, in the editor only.
  • The rolling-logos marquee never previews: the editor never emits .client-logo-track and puts data-logos-variant on the wrong element, so both marquee rules can never match. The author sees static rows; the prospect sees a marquee.
  • The video play button differs: the editor omits data-journey-video-preview-trigger, so the journey sheet's brand-tinted 56px button loses to 14-library.css's white-tint 3.5rem one.

The four "parity tests" (FAQ, gallery, summary, CTA row) only assert that both HTML strings contain a handful of data-* substrings; they cannot catch a different element type or a missing wrapper, which is exactly the class of the three bugs above. There is no visual regression testing anywhere in the repo (zero toHaveScreenshot/toMatchSnapshot; the e2e public-page spec asserts intent, not appearance). The one drift-proof value is --media-size: both renderers compute it through the same assetSizeCssVar() and emit it as an inline custom property. That is the model the rest should follow.

Also note the preview's fragility: .lp-page (from 14-library.css, sets background: white; color: #374151; system-ui) and .jp-theme (journey tokens) tie on specificity on the same element; the journey look wins only because LivePreview appends its <style> after the bundle's stylesheet at mount. Published pages have no dark mode at all; darkness is a content choice (theme.base.tone), with readableTextOn() auto-contrast, so the SPA's .dark class mechanism simply does not apply there.

The enforcement map

What actually gates a merge, in full:

  1. editor/vite-backdrop-filter-pair.ts: fails the build when backdrop-filter/-webkit-backdrop-filter counts mismatch in emitted CSS. Born from a real incident (Lightning CSS collapsed the pair; glass shipped flat to Chrome/Firefox, 2026-07-29). The only true CSS gate.
  2. editor/tests/journey-page-theme.test.ts: parses the published-page CSS with postcss and enforces ADR 0007's lever/macro boundary (presets may not touch fonts, heading sizes, section padding; one-sided button rules may set border color only; --foreground remaps must also remap --muted/--card), with tripwires so a regex that harvests nothing fails loudly. The most rigorous styling enforcement in the repo, and it protects the published page, not the app.
  3. editor/tests/trial-wall-drift.test.ts: the 8-token copy guard (:root only).
  4. The component-reuse ratchet: raw form elements are an ESLint error with a shrink-only baseline, 97 suppressions on 2026-09-10 down to 75 across 29 files now. It demonstrably drives behavior (commit 00e9622c: "the raw-element ratchet forbids carrying a suppression to a new file").
  5. A LOC ratchet (scripts/check-loc-ratchet.sh) covers .css over 1000 lines, but only runs inside the local review-loop skill, not CI. 13-journey-index.css (1,906 lines, with an unactioned FIXME to split it) is the only file over it.

Everything design-system-shaped is advisory and, in practice, silent. The @shadcn/lint block in eslint.config.mjs:111-126 is uncommitted working-tree state as of this audit (verified: HEAD's config has zero shadcn references; eslint.config.mjs, package.json, pnpm-lock.yaml are dirty). All six rules are 'warn'; pnpm lint runs eslint . --quiet, which drops warnings; the edit-time hook (scripts/hooks/lint-on-edit.mjs) returns early on exit code 0, which ESLint uses for warnings-only; and the hook filters to .ts/.tsx. No hook, lint, or CI check ever reads a .css file. Editing 1,900 lines of CSS triggers nothing.

The lint's findings (1,563 messages; 1,556 shadcn, 7 stale-disable) are dominated by a structural blindness rather than by bugs: components.json points the design system at src/index.css, whose import graph never reaches styles.css or any colocated sheet. So 955 of the 1,027 no-unknown-classes findings are real classes with real CSS the tool cannot see, and its prescribed fix ("declare it with @utility in index.css") matches nothing in the codebase. The genuinely actionable residue is ~194 findings (raw colors, arbitrary values, inline styles), and even there ~28 are false positives (the accent-dots/ring-track class names squatting in Tailwind's utility namespaces, and third-party brand SVG hexes). Meanwhile the primitives folder is exempt, so the raw brand hex inside the design system itself (tabs.tsx:64) is invisible.

How it got here

Both systems were born together: the React editor arrived in the monorepo on 2026-04-07 already carrying Tailwind v4, components.json, Base UI primitives, and a ~6.6k-line styles.css monolith. On 2026-06-20 the monolith was split into 23 numbered partials byte-identically and a migration was declared; docs/CSS_AUDIT.md, containing the only per-partial roadmap and a "guardrail to prevent backsliding" (lint against new bespoke classes), was added and deleted the same day ("Findings captured in the PR description instead"). The guardrail was never built. The one real wave was buttons (2026-07-27): ~20 bespoke button families collapsed into Button + button-surface.css, ~1,000 lines deleted, two partials removed. Since the split: 107 commits to the partials, +2,962/−2,177 lines, net 6,542 → 7,398 (+13%), three new partials added, and a monthly commit ratio of roughly 10:1 legacy-to-primitives. The reuse ratchet (2026-09-10) and the uncommitted shadcn lint (2026-09-15) are the first enforcement moves aimed at the app side.

What Is Confusing or Inconsistent

Ranked by ongoing cost:

  1. The cascade inversion is global but documented as local. index.css:4-6 presents unlayering as a trick for one file; in the built output all 10,966 hand-written lines are unlayered and beat every utility. A developer writing className="bg-card" on an element carrying any legacy class gets silently overridden (sidebar.tsx:135 vs 01-app-shell.css:11-14), and cn() cannot warn them.
  2. The migration runs backwards and has no plan. The "shrinking legacy surface" grew 13% over 107 commits; new features join it (AuthRoute.tsx, 2026-08-27, zero Tailwind); the only roadmap was deleted the day it was written (16b847c6); no ADR, owner, or exit criterion exists. The only policy is a four-line comment in styles.css.
  3. Two renderers for the same published page, with proven divergences. render-blocks.ts vs LivePreview.tsx; the marquee that never previews, the striping shift, the different play button. The parity tests check substrings, and there is no visual regression anywhere, so what the author sees is not reliably what the prospect gets.
  4. The design system's tooling cannot see two-thirds of the CSS, and gates nothing. components.json → index.css dead-ends before styles.css; 955+ lint findings are the tool describing that graph gap; all rules are warn behind --quiet and a hook that drops warnings; the primitives folder is exempt, hiding its own raw hexes; and no automated path reads .css files at all.
  5. Tokens cross boundaries by hand-copy. 8 of ~45 trial-wall tokens are drift-tested (:root only); --btn-halo is derived in three files; brand blue exists in five forms; .jp-theme shadows the app's token names with different values in the same document, held together by comments.
  6. The docs actively instruct wrong behavior. DESIGN.md specifies DM Sans (the app ships Geist), a radius scale wrong in 3 of 4 steps, glass opacities that contradict index.css, a 680px page width (actual 760), and "always include -webkit-backdrop-filter", which the build fails on (vite-backdrop-filter-pair.ts:50). evals/ui-change-eval.md repeats two of these and is graded before every headless handback, so agents are scored against instructions the codebase forbids.
  7. Same-name collisions and order-dependence. 63 class names defined in multiple stylesheets, 20 straddling the ordered partials and unordered colocated files; MediaPickerDialog.css re-skins nine foreign classes; the preview's entire look depends on <style> insertion order (.lp-page vs .jp-theme); .section/.card/.price squat unscoped in the global namespace, and .ring-track/.accent-dot collide with Tailwind utility grammar.
  8. The font is named everywhere and loaded in one place. Geist @font-face lives only in the auth-gated chunk; /login and friends silently render in fallback sans-serif; only PublicHomeRoute.css opted out knowingly.
  9. The class-name contract is broken in both directions. ~78 dead CSS classes (e.g. the .record-trim-* family, .cg-btn still documented as live in button-surface.css:131) and ~35 class names on JSX with no rule anywhere. Of those 35, ~20 are deliberate-looking worker-parity mirrors (the editor emits the same classes SSR emits, e.g. section-story, while the styling actually rides the data-journey-* attribute next to them), 12 are genuinely dead hooks, 2 are test selectors, 1 renders unstyled (topbar-page-eyebrow). Nothing distinguishes these cases at the call site, and nothing closes the loop. (Explorer counts of 31 vs 35 are the same population; the extra four, section, cta-row, price, lp-summary-table, are all mirrors, verified ruleless.)
  10. Semantic tokens lose to palette memory. --success/--warning/--info exist with dark values and 6 total usages, while text-emerald-600, text-green-600 (two different greens for the same "Saved" state), bg-red-50, bg-amber-500/5 recur; shadow/elevation tokens are genuinely missing, and the dead --chart-* tokens degrade the lint's suggestions.

Compared to Best Practice

Idiomatic (genuinely good):

  • Correct Tailwind v4 entry shape: @import "tailwindcss", @theme inline, @custom-variant dark, :root/.dark oklch tokens, @tailwindcss/vite, no legacy config, no PostCSS build.
  • Textbook primitives: Base UI + cva + cn(), data-slot on every part, cssVariables: true; forks are documented with rationale (button.tsx's size comment).
  • The token set extends shadcn's thoughtfully (--success/--warning/--info, --glass-*, radius ladder) rather than replacing it.
  • Data-attribute state styling as the house idiom (297 attribute selectors; VideoStatsModal shows the legacy idiom done well), matching the base-nova variant vocabulary.
  • The custom-property handoff for dynamic values (--media-size, --media-card-accent-hue), including the shared assetSizeCssVar() that makes one value structurally drift-proof across SSR and preview.
  • ADR 0007's lever boundary enforced by executable postcss tests with harvest tripwires; the backdrop-filter build gate encoding a real incident; the trial-wall drift test; the shrink-only reuse ratchet that measurably moved 97 → 75 in five days.
  • button-base.tsx as an explicit escape valve, and the data-button-surface="none" hatch being documented with intent.

Departures:

  • The cascade contract is inverted: all app CSS is unlayered and outranks utilities, where best practice puts app CSS in @layer components/@utility so utilities stay the final word.
  • 10:1 of new styling work flows into a legacy layer that is nominally being deleted; the newest features are written in it.
  • Six systems where the reference architecture has one; only the Tailwind system is discoverable from a component or visible to components.json-based tooling.
  • Two hand-rolled surface languages and duplicate journey renderers, held to parity by comments and substring tests instead of structure.
  • Tokens are copied across boundaries by hand instead of shared (no token package; packages/journey-page-domain is not even a real package).
  • Docs are a second source of truth that has drifted for months, including live instructions the build rejects; components.json's baseColor: "neutral" would scaffold the wrong ramp on the next shadcn add.
  • The styling lint gates nothing (warn + --quiet + hook exit-0 + .css unread), while a proven ratchet mechanism sits unused next to it; dark mode is per-rule opt-in in the legacy layer; there is no visual regression or CSS budget.

Verdict. Measured against a reference Tailwind v4 + shadcn design system, Clarity has an excellent core and an inverted environment. The theme, primitives, state idiom, and dynamic-value handoff are close to model implementations, and pockets of enforcement (ADR 0007's tests, the backdrop-filter gate, the reuse ratchet) are better than what most Tailwind shops ship. But structurally the design system is the weakest layer in its own cascade, invisible to its own tooling for two-thirds of the CSS, outgrown 10:1 by the layer it was meant to replace, and duplicated by hand at every bundle boundary. This is less "a Tailwind design system with some legacy CSS" than "a legacy CSS codebase containing a high-quality shadcn system that has not been allowed to win." The repo already owns every mechanism needed to change that (the ratchet pattern, codemods, postcss invariant tests, the build-gate slot); none of them currently points at the legacy layer.

Gotchas

  • Editing a .css file triggers no check of any kind. The edit hook filters to .ts/.tsx; ESLint never parses CSS; there is no stylelint. The only things that ever read your CSS are the bundle plugin (prefix pairs) and two vitest suites (published-page CSS and 8 trial-wall tokens).
  • Do not hand-write -webkit-backdrop-filter, even though DESIGN.md:67 tells you to. Lightning CSS emits the alias itself; a hand-written one collapses the pair and the build fails (vite-backdrop-filter-pair.ts:50).
  • A Tailwind utility on an element with a legacy class may silently do nothing (unlayered beats layered), and cn() will not flag it. Conversely, data-button-variant rules in button-surface.css beat single-class partial rules on specificity, so "later file wins" intuition also fails.
  • @import "shadcn/tailwind.css" makes a devDependency load-bearing for shipped CSS. It resolves only through the "style" export condition @tailwindcss/vite sets; any PostCSS-based pipeline would fail to resolve it and lose the base-nova data-* variants.
  • Tailwind's content scan covers editor/ only (no @source anywhere; the scan root is the Vite cwd). A utility class in a worker template or shared package produces no CSS and no warning. The legal HTML's baked-in utilities compile purely by accident of that scan.
  • chrome.css ships twice by design (via styles.css and via VideoPlayer.tsx), so authenticated users download those 161 lines in both chunks.
  • The preview's journey look depends on <style> insertion order. LivePreview appends #jp-theme-css at mount; hoisting that sheet into the build, or changing effect timing, would repaint the preview in 14-library.css's white/system-ui.
  • SSR emits inline text-align on every heading (render-blocks.ts), which outranks the attribute rules and means no theme preset can ever restyle heading alignment.
  • The published page's unsafe-inline style CSP (security-headers.ts:21) exists because the whole stylesheet is one inline <style>; the 31.5 KB re-ships with every HTML response and cannot cache separately.
  • A published-page rule exists because of an editor bug: .rich-text ul/ol { list-style: ... } in journey-page-styles.ts:123-128 restates UA defaults because Tailwind preflight zeroes list markers in the preview only.
  • The 03/15 gaps in the partial numbering are the migration's two victories (buttons and preview-modal, deleted 2026-07-27). Everything else the migration promised is still here.
  • The @shadcn/lint setup is uncommitted working-tree state (verified against HEAD during this audit). As written it changes nothing in CI or the edit hook; if it lands at warn it will stay invisible. The obvious landing shape, given eslint-suppressions.json, is a second shrink-only ratchet scoped to the ~194 actionable findings, with no-unknown-classes disabled until the partials shrink.
  • Open questions the explorers could not settle from the repo: whether route-scoping the other 7,398 partial lines (beyond the documented Geist decision) was deliberate; whether the worker-parity mirror classes are policy or drift (no ADR says); whether anything external depends on the dead SSR classes (section-story et al.); and who owns the lint rollout. These need Linear/PR history.

Part 2: Critique verdict

Three independent critics reviewed the explanation and the code: Claude Fable 5 at max effort, Claude Opus 5 at xhigh, and Codex GPT-5.6 Sol at max. All three agreed on the four structural findings and disagreed only on ordering and on one remedy. The judgment below is mine, as lead.

Reframing the question

Is it one system or several? The honest answer is three legitimate domains, and inside one of them five competing idioms.

Domain Technology Verdict
App chrome (editor SPA) Tailwind v4 + shadcn/Base UI primitives, plus 10,966 lines of unlayered hand-written CSS in five idioms One domain, too many idioms, no governance
Customer journey pages Attribute-driven --jp-* stylesheet in a TS string, rendered by worker SSR and by the editor preview Correct to be separate; the two renderers lack a contract
Worker-only documents and email Private <style> template strings, table-layout email Correct to be separate; tokens are hand-copied in

Having separate systems for the SPA and for no-build SSR HTML is right, not debt. The problems are inside the app domain and at the seams.

Act on

  1. Make the journey renderer contract executable. Both renderers share a stylesheet but nothing enforces that they emit the same skeleton. Three confirmed divergences exist today, and one is a product defect: the rolling-logos marquee never renders in the editor, so the author sees static rows and the prospect sees a marquee. Add a per-kind skeleton (tag plus required data attributes) to BlockDefinition and one table-driven test over BLOCK_REGISTRY that renders both outputs and compares them. The seam already exists in editor/tests/faq-rendering-parity.test.ts. This closes the half of ADR 0006 that was never built. Roughly a day.

  2. Declare the cascade instead of inheriting it from bundler order. Keep button-surface.css unlayered on purpose. Move all other hand-written CSS into a named app layer ordered after utilities. That is a visual no-op today, but it turns "which rule wins" from an accident of chunk order into a fact declared in one file, and it fixes the cross-chunk link-order dependency. Only after that, move individual files below utilities one at a time as small reviewable changes. Opus's version of this remedy, not Fable's immediate flip, because there is no visual regression coverage to make a flip safe.

  3. Retire the migration slogan and write the real ADR. The only policy is four lines in styles.css saying the partials are being deleted. They grew 13% over 107 commits, new features are written in them, and the roadmap was deleted the day it was written. The label is what blocks investment: nobody ratchets or splits condemned code. Opus verified that the editor canvas is a deliberately held quarantine (zero theme-token utilities, zero styled Button inside .jp-theme), which is legitimate architecture. Name the two authoring modes and the boundary, then govern both.

  4. Point the ratchet at CSS. No automated path reads a .css file. Land the shadcn lint as error-level with a shrink-only baseline like eslint-suppressions.json, scoped to the ~194 actionable findings. Turn no-unknown-classes off; it measures the components.json import-graph gap, not defects. Stop exempting components/ui/** from no-raw-colors so the brand hex in tabs.tsx:64 becomes visible. Add .css to the edit hook's file filter. Move the LOC ratchet into CI.

  5. Fix the docs that contradict the build. DESIGN.md tells agents to hand-write -webkit-backdrop-filter, which the build fails on, and specifies DM Sans, a wrong radius scale, and a 680px page width. The eval grades headless handbacks against those rules. Point the doc at code for anything code already expresses. Cheap and high leverage.

Consider

  • Give journey colors their own namespace. .jp-theme redefines --background, --primary, and friends with different values inside the SPA. Opus found the mechanism that makes this fragile: a token read directly in a rule resolves at the element and gets captured; one baked into a :root custom property does not. The reuse ratchet currently steers people toward Button, the primitive that would break this boundary. The fix is --jp-background and so on, matching the existing --jp-page-max-width pattern. Touches presets, so verify against published pages.
  • Make packages/journey-page-domain a real workspace package. It has no package.json, is imported by deep relative path, and is bundled twice. It is the prerequisite for any shared token module.
  • Ratchet duplicate class definitions. 63 class names are defined in more than one stylesheet and 20 straddle ordered and unordered files. .lp-play-button has three owners across two bundles. A shrink-only duplicate-definition check makes source order stop mattering while layering lands.
  • Serve the journey stylesheet as a hashed asset instead of inlining 31.5 KB per response. Also unblocks a stricter CSP later.

Noted

  • Geist is named on every route but only downloaded after login, so /login, /terms, and /teams render in fallback sans-serif. chrome.css ships twice. Worth an owner, not an emergency.
  • components.json says baseColor: neutral while the theme is slate and blue, so the next shadcn add scaffolds the wrong ramp. The five --chart-* tokens are dead and poison the lint's suggestions. Trivial fixes.
  • Button interactive states must be written twice, once in cva and once in button-surface.css. That is the accepted price of the surface-language design and the comments carry it well.
  • SiteHeader's CTA class only resolves on 3 of the 7 pages that render it. A symptom of route-scoped CSS on a shared component; fix when the layering work touches marketing routes.
  • SSR screenshot tests for the six presets would be low-flake and useful, but not first. Every known failure is structural and a markup test catches it for a fraction of the cost.

Dismissed

  • A PostCSS gate forbidding unlayered declarations (Codex). Premature until the app layer exists; it would fail on everything.
  • Visual regression before the structural parity test (Fable's ordering). Screenshots would not have said the marquee attribute was on the wrong element.
  • Counting six systems as the diagnosis. Codex and Opus both made this point and I agree: the number is not the problem, the missing owners and contracts are.

Recommended sequence

Structural parity test, then the ADR that names the two modes, then the app layer, then the CSS ratchet. The first is a product fix and takes a day. The other three reuse enforcement the repo already trusts.

Findings

1. [structural] The migration is a fiction, and the fiction is the problem

Components: editor/src/styles.css (policy comment), editor/src/styles/*.css (24 partials, 7,398 lines), docs/CSS_AUDIT.md (deleted), editor/src/routes/AuthRoute.tsx + LoginRoute.css Finding: The repo's only written styling strategy is the four-line comment in styles.css ("Migration target: replace these with Tailwind utilities + shadcn primitives. Delete a partial as it empties out."). Every measurable signal says the organization has decided otherwise: since the 2026-06-20 split, 107 commits landed in the partials against 16 in the primitives folder (verified via git log); the partials grew from ~6.5k to 7,398 lines; the per-partial roadmap (docs/CSS_AUDIT.md) was added and deleted the same day (6da6ed65 → 16b847c6); and the newest large feature, the auth flow (AuthRoute.tsx, created 2026-08-27, #606), was written as 640 lines of new BEM in LoginRoute.css — a file named after a component that no longer exists. The structural cost of a zombie migration is that it blocks both alternatives: because the legacy layer is nominally condemned, nobody invests in making it sound (no @layer, no stylelint, no namespace rules, no dark-mode audit — "it's going away"); because it is not actually going away, all new feature styling compounds inside the ungoverned layer. Evidence: The migration's only two completed deletions (the 03/15 numbering gaps) came from the buttons wave of 2026-07-27 — primitive consolidation, not utility conversion. Nothing shaped like "convert a partial to utilities" has ever succeeded here. The deleted audit itself blessed colocated CSS as "✅ keep" and flagged the DM Sans/Geist doc drift on day one; three months later that drift is still live in DESIGN.md. Impact: Every new feature makes the declared end-state more expensive while the declared end-state prevents spending on the actual one. The 10:1 flow means the design system loses ground every month the fiction stands.

2. [structural] One override mechanism carries two opposite intents

Components: editor/src/index.css (Tailwind layers), editor/src/components/ui/button-surface.css (deliberately unlayered), everything in editor/src/styles/ and all colocated .css (unlayered by default) Finding: button-surface.css is unlayered on purpose, and the purpose is coherent: it encodes "call sites may not restyle buttons" in the cascade itself, so container rules beat cva utility classes without !important, with data-button-surface="none" as the documented escape hatch. But the other ~10,700 hand-written lines are unlayered by default — plain CSS imported outside any layer — and therefore also beat every Tailwind utility. The same mechanism means "this is a contract" in one file and "nobody chose this" in forty-three others, and nothing distinguishes them. The mental model every Tailwind developer brings (utilities win) is inverted repo-wide, silently: sidebar.tsx:135 sets bg-[#f6f4ef] on the same element AppShell.tsx:16 gives .editor-shell-frame, whose unlayered gradient (01-app-shell.css:11-14) always wins — the utility is dead code sitting in the primitive, and cn()/twMerge cannot flag semantic-vs-utility conflicts. Evidence: index.css:4-6 documents unlayering as a local trick for one file. The convention that keeps the mix workable ("geometry stays with the consumer; semantic classes own paint") lives only in comments (chrome.css:8) with no enforcement. Only ~15 !important across all editor CSS shows the convention mostly holds — by hand. Impact: A class of silent no-op edits (utility written, never renders) that no tool can detect, plus an unfixable ambiguity during review: is this unlayered rule a contract or an accident? The fix is syntactically cheap (@import "./styles/…" layer(legacy) plus an explicit @layer order putting legacy below utilities) but flips the winner at every currently-mixed call site, and the repo has zero visual regression coverage to make that flip safe — see finding 8. Note the fix keeps button-surface.css unlayered: "unlayered = deliberately final" becomes a meaningful convention only once it is rare.

3. [structural] The design system's tooling is aimed at a graph that excludes two-thirds of the CSS, and no design check gates anything

Components: editor/components.json, eslint.config.mjs:111-126 (uncommitted @shadcn/lint block), scripts/hooks/lint-on-edit.mjs, package.json (lint = eslint . --quiet), scripts/check-loc-ratchet.sh Finding: Four independent mechanisms each neutralize the design lint, and they compound: every rule is 'warn'; --quiet drops warnings from pnpm lint; the edit hook returns on exit code 0 (ESLint's exit for warnings-only, verified at lint-on-edit.mjs: if (result.status === 0) return;); and the hook's LINTED regexes admit only .ts/.tsx, so no automated path in the repo ever reads a .css file — editing the 1,906-line 13-journey-index.css (which carries an unactioned FIXME to split it) triggers nothing anywhere. Worse, the lint's dominant rule is structurally blind: components.json points at src/index.css, whose import graph never reaches styles.css or any colocated sheet, so ~955 of 1,027 no-unknown-classes findings are real classes with real CSS the tool cannot see, and its prescribed fix ("declare with @utility") matches nothing this codebase does. Meanwhile the primitives folder is exempt from the lint — which is exactly where the design system's own raw hexes hide (tabs.tsx:64 after:bg-[#2563eb], sidebar.tsx:135,315 off-theme #f6f4ef cream). Evidence: git show HEAD:eslint.config.mjs | grep -c shadcn → 0; the whole block is dirty working-tree state. Contrast with the component-reuse ratchet ten lines above it: error-level, shrink-only baseline in eslint-suppressions.json, demonstrably moved 97 → 75 suppressions in five days. Impact: The enforcement map is inverted relative to risk: the strongest checks in the repo (ADR 0007 postcss tests, the backdrop-filter build gate) protect the published page, while the surface where 10:1 of the styling change lands has zero checks. If the staged lint ships as-is it adds 1,563 messages of noise and no gate — worse than not shipping it, because it trains everyone that design findings are ignorable.

4. [structural] One stylesheet, two markup producers, no structural contract

Components: packages/journey-page-domain/src/journey-page-styles.ts (shared CSS keyed on data-journey-*/data-module-kind), workers/frontend-router/src/public-page-delivery/render-blocks.ts (SSR switch), editor/src/components/editor/LivePreview.tsx + per-kind editors (preview switch), packages/journey-page-domain/src/blocks.ts (BlockDefinition), docs/adr/0006-* Finding: ADR 0006 explicitly rejected a shared renderer — reasonably, since the preview is an interactive click-to-edit surface — but its chosen mitigation was "public-HTML renderer and interactive React preview renderer co-located per kind" in the block registry "with per-kind parity tests." Neither half exists: BlockDefinition (blocks.ts:208-216) has createDefaultFields/normalizeFields/generation and no renderer field of either kind; the two renderers are independent switches four directories apart. The contract between them is implicit — "whatever elements and attributes the shared CSS happens to select on" — and the parity tests (4 of 9 kinds) assert only that both HTML strings contain a handful of data-* substrings (faq-rendering-parity.test.ts), which cannot detect a different element type or a missing wrapper. Evidence: Three verified divergences, all in the class the substring tests cannot see: (a) SSR renders a standalone logos block as a <div> band deliberately so [data-module-kind]:nth-of-type(even) striping is undisturbed (comment at render-blocks.ts:569-571), while the editor renders <section data-module-kind="logos"> (LogosSection.tsx:52-58), shifting stripes for every following section in the preview only; (b) the rolling-logos marquee can never render in the editor — SSR puts data-logos-variant on .client-logo-row with a .client-logo-track child (render-blocks.ts:556-557), the editor puts the attribute on the section root and never emits the track, so both marquee rules (journey-page-styles.ts:500-516) are unmatchable; (c) the video play button differs because the editor omits data-journey-video-preview-trigger and falls through to 14-library.css. Impact: This is the one finding that is a live product defect, not developer debt: the WYSIWYG promise — the product's core claim — fails silently. An author configures a marquee, sees static rows, and the prospect sees something the author never saw. Every new block kind or markup tweak re-rolls these dice. Crucially, the fix is cheap: the FAQ parity test already renders LivePreview via renderToStaticMarkup in the same vitest process as the SSR renderer, so a structural comparator (parse both, strip editor-only wrappers, compare element type + styling-relevant attribute sets per kind, all 9 kinds) is a day of work on an existing seam. 6. [concern] A flat global class namespace with duplicate definitions and order-dependent winners

7. [concern] The Button's interactive states must be implemented twice, in two languages

Components: editor/src/components/ui/button.tsx (cva), button-surface.css Finding: The price of the unlayered surface language is paid inside the design system itself: the cva's colour classes for default/outline are dead paint everywhere except under data-button-surface="none", and every interactive state expressed as a utility (aria-expanded:, data-popup-open:, hover) must be restated in the unlayered dialect or it silently fails to apply to the glassed variants. Impact: Two files in two languages must be read to know what a Button looks like, and every new state or context is a two-place edit where missing one produces a subtle, variant-specific regression. The architecture holds today because the comments are excellent; it is a per-state tax with no tooling backstop, forever.

Evidence: grep -rn "toHaveScreenshot\|toMatchSnapshot" across editor, workers, e2e → nothing. Impact: The cheapest entry point is the published page: pure SSR HTML+CSS, no auth, no live data, six presets — deterministic screenshots with near-zero flake, which would also close finding 4's verification half. The SPA can come later or never; starting visual regression with the worker-rendered surface is the high-value, low-flake move.

9. [concern] Docs and evals instruct what the build forbids, in a repo where agents follow instructions literally

Evidence: DESIGN.md:67 vs the plugin's error message telling you to delete exactly what the doc says to add. Impact: A standing trap for every UI task. Cheap fix, high leverage: make DESIGN.md point at code for anything code already expresses (as its glass-tokens section already does), and regenerate the eval criteria from the same sources.

10. [observation] Dark mode is automatic for every user but opt-in per rule in the legacy layer

Components: editor/src/lib/theme.ts ("follows the OS color scheme — there is no in-app preference"), editor/index.html no-flash script, 24 partials Finding: Because theming follows the OS, dark mode is not a feature users enable — every OS-dark user is in it on every SPA route (decided 2026-06-12, per the comment). Yet only 5 of 24 partials contain any .dark rule (verified), and the partials hold 77 raw hex literals; legacy surfaces adapt only where they happen to route through a token. The --success/--warning/--info extensions exist fully wired with dark values and are barely used while raw palette utilities (text-emerald-600, bg-red-50) recur; --chart-1..5 are declared, never referenced anywhere (verified), still hold stock zinc greys, and poison the lint's "nearest token" suggestions. 1. [structural] ADR 0006 specified the mechanism that makes two renderers safe, and only the unsafe half shipped

3. [structural] Unlayering everything replaces an ordered cascade with a bundler-order cascade

Components: editor/src/index.css:4-7, editor/src/components/ui/button-surface.css, editor/src/styles.css + 24 partials, 16 colocated sheets, editor/vite.config.ts.

Finding: I want to defend the decision and attack the mechanism separately, because the explanation runs them together.

The decision is right. index.css:4-6:

"Unlayered on purpose: Tailwind utilities sit in @layer utilities, so these rules win over the CVA's colour classes without !important."

That is a genuinely good call. It lets button-surface.css own appearance while button.tsx stays unforked upstream base-nova, which keeps shadcn add viable. I would keep it.

The mechanism is too coarse. "Unlayered" is a single global privilege level with no interior structure, so once every hand-written file is unlayered, the question "which of two rules wins" falls back to specificity and source order across separately-emitted CSS chunks. Verified against editor/dist/assets/: index-*.css is the only asset with @layer (5 occurrences); ProtectedEditorLayout-*.css (114.7 KB), EditorRoute-*.css, LoginRoute-*.css, MediaPickerDialog-*.css and the rest contain zero. Those are separate <link> elements whose relative order in <head> — not any declaration in the repo — decides the winner between, say, MediaPickerDialog.css's nine deliberately re-skinned class names and the 13-journey-index.css/14-library.css rules they override.

Tailwind v4 already ships the precise tool for "beat utilities, but in a declared order":

@layer theme, base, components, utilities, app;

Move all 40 hand-written files into app in their current emission order and the rendered result is byte-for-byte identical to today — app sits after utilities, so every rule that beats a utility today still does, and within-layer order is source order, which is unchanged. What you gain is that the order becomes a fact declared in one file instead of an emergent property of Vite's module graph and <head> insertion sequence, and it stops depending on chunk order entirely (layers are document-global; <link> order is not). You can then split app into ordered sublayers (app.base, app.feature, app.surface) and move individual files below utilities one at a time, each move being a small reviewable behavior change instead of a 10,966-line flip.

Mechanically: the 24 partials take layer(app) on their @import lines in styles.css; the 16 sheets imported from TSX need their contents wrapped, which is a codemod, not a rewrite.

Impact today: 63 class names are defined in more than one editor stylesheet and 20 of those straddle the ordered aggregator and the unordered colocated files, so their winner is not derivable from any source file. cn() cannot help — twMerge only understands Tailwind's own grammar, so a semantic-vs-utility conflict passes through silently. The author has already met this mechanic once and documented it in a different context (button-surface.css:248-250: "custom properties resolve where they are declared: the :root definition already baked in root's --btn-ink and cannot see this one"). It is never generalized into a rule.

3. [Observation] Several bounded styling domains are justified

Components: Editor application, public journey pages, worker-only documents and email

Finding: This is not one styling system, but it is also misleading to count every CSS location as a separate system. There are three legitimate domains:

  1. Clarity’s application chrome.
  2. Customer-branded journey documents.
  3. Worker-specific documents, including email.

Within the application domain, Tailwind, primitives, partials, chrome CSS, and route CSS are competing implementation idioms rather than independent products.

Evidence: The application core in index.css:1, button.tsx:1, and utils.ts:1 follows the current shadcn model of semantic CSS variables, @theme inline, variants, and primitive composition—consistent with shadcn’s theming guidance. Journey styling must also execute in worker HTML through render-shell.ts:62. Email’s table and inline styles in base.ts:21 reflect email-client constraints.

Impact: Forcing all three domains through Tailwind would introduce application build assumptions into edge HTML and email without removing meaningful complexity. The goal should be explicit boundaries and shared tokens/contracts—not one rendering technology everywhere.

6. [Concern] CI protects incidents, not the architectural boundaries

Finding: Existing gates are individually good but do not constrain the failure modes above. CSS ownership, layering, selector growth, and cross-renderer parity can regress without failing CI.

Evidence: CI runs lint, tests, and build in ci.yml:68, but the lint script uses --quiet in package.json:8. Recommended direction

First replace the blanket migration slogan with an executable styling contract. Declare the three domains, put application base and semantic CSS into named layers, reserve one narrowly allowlisted final-override layer, and ratchet new work away from globally owned partials. This makes the existing CSS safe immediately, preserves semantic CSS where it earns its keep, and creates a stable foundation for incremental shadcn adoption and journey-renderer parity work.
