Appendix A: Opus critique of plan v1

Repository read: /Users/williamlarsten/Development/clarity-css-home @ 31ccd5fa (branch refactor/home-library-design-system). All file references below are from that worktree.

Summary of the position: the recipe proven in waves 1–3 is good and should be kept almost verbatim. The sequencing is wrong in four places, the slice grouping cuts across three stylesheets that are actually three families each, the .jp-theme prerequisite is both unnecessary in the form proposed and much more expensive than the plan implies, and the plan is missing the single highest-leverage move available: fixing the cascade inversion once, mechanically, instead of paying for it in every slice. It also assumes a lint plugin that does not exist on main.

Changes to the plan

1. Add a prerequisite PR that moves the legacy layer into @layer components, and stop paying the cascade tax nine more times

What: Before any slice, land a PR whose only job is to put every remaining legacy stylesheet into Tailwind's components layer, so utilities win by default.

Why. The plan treats the cascade inversion as background weather. It is the dominant per-slice cost. Wave 1 shipped 3 ! overrides plus an invented custom-property seam (--media-card-preview-bg) purely to route around it; wave 1's report states the reason plainly: "for !important declarations the layer order reverses, so a layered important utility beats an unlayered important rule" (/tmp/css-home/wave1-report.md:70). Wave 2 shipped 31 ! (wave2-report.md:154-165). Wave 3 spent a whole commit removing 19 of them and still ships 12 (wave3-report.md:227-238). That is three waves of bookkeeping on one stylesheet out of forty-two. There are 19 !-suffixed utility sites left in editor/src today across 10 files.

The fix is mechanical and does not need a new layer name. Tailwind already emits @layer components; as an empty declaration before @layer utilities{ — verified in the built entry chunk, which contains exactly @layer properties{, @layer theme{, @layer base{, @layer components;, @layer utilities{ and nothing else. Legacy CSS placed in components therefore sorts above base and below every utility, in every chunk, regardless of file order, because the layer name is established by the eager entry chunk (index-*.css) that always loads before the lazy ProtectedEditorLayout-*.css chunk. Implementation, in order of preference:

  1. @import "./styles/01-app-shell.css" layer(components); in editor/src/styles.css, and import sites for colocated sheets rewritten the same way. Needs a one-command spike to confirm Vite's CSS resolver preserves layer().
  2. Guaranteed fallback if it does not: a codemod that wraps each file's contents in @layer components { … }. Two lines per file, 40 files, idempotent, self-checking — the same shape as scripts/codemods/snap-arbitrary-values.mjs.

button-surface.css and chrome.css stay unlayered until their own slice; their whole design is "unlayered so we beat the CVA's colour utilities without !important" (editor/src/components/ui/button-surface.css:10-12), and that is still true and still wanted until the surface language becomes a primitive.

Sizing it honestly. Flipping the layer makes every utility that is dead today come alive. The audit already names one (sidebar.tsx:135's bg-[#f6f4ef] losing to .editor-shell-frame). Nobody knows how many there are. That is exactly what wave 2's computed-style probe measures, and it costs one run: capture before, flip, capture after, run summarize-probe.mjs. Decision rule to write into the plan: if the grouped diff is under ~50 property: before -> after rows, do the flip once in the prerequisite PR; if it is larger, move only the current slice's stylesheets into components as step 1 of each slice. Either way the tax is paid once per file instead of once per consumer.

7. Replace the --jp-* rename prerequisite with a 15-line --app-* mirror

What: Drop the namespace rename from the critical path. Add the mirror to P0b.

Why. Two findings.

First, the rename is larger than one line of plan. packages/journey-page-domain/src/journey-page-styles.ts reads the shadcn names ~50 times (var(--primary) ×17, var(--foreground) ×8, var(--border) ×6, var(--muted-foreground) ×6, plus --background, --card-foreground, --muted, --primary-foreground, --radius*). All six presets in theme-presets.ts declare --background, --foreground, --card, --card-foreground, --muted, --muted-foreground, --border, --input. theme.ts:71-89 emits them. editor/tests/journey-page-theme.test.ts — the repo's most rigorous styling gate, enforcing ADR 0007's rule that "a --foreground remap must also remap --muted/--card" — asserts on those names and would have to be rewritten. And the surface is live customer pages with zero visual regression coverage.

Second, the shadowing is narrower than the plan assumes. Custom properties resolve where they are declared, which button-surface.css itself documents: "custom properties resolve where they are declared: the :root definition already baked in root's --btn-ink." So --cg-ink: var(--foreground) declared at :root in chrome.css:22 keeps the app's foreground even inside .jp-theme. Shadowing bites in exactly one case: a utility on an element inside .jp-theme, because bg-card emits background-color: var(--color-card) on that element.

The cheap fix is therefore a mirror, not a rename:

/* index.css, in :root and .dark */
--app-background: var(--background);
--app-foreground: var(--foreground);
--app-card: var(--card);
--app-primary: var(--primary);
--app-border: var(--border);
--app-muted: var(--muted);
--app-muted-foreground: var(--muted-foreground);

/* Editor chrome rendered inside the journey preview: .jp-theme rebinds the
   shadcn names to the customer's page colours; restore the app palette. */
[data-editor-chrome] {
  --background: var(--app-background);
  --foreground: var(--app-foreground);
  /* … */
}

Fifteen lines, no published-page code touched, reversible, and verifiable with a computed-style probe on a canvas editor mounted inside the preview. Schedule the --jp-* rename separately as journey-package hygiene with its own SSR-HTML + screenshot gate; it is not on this plan's critical path.

1. Is the order right? Should shell/topbar precede base rules, or should 0 and 1 merge? Neither. 4. Is folding button-surface.css into cva variants actually right, or should the container-owned appearance idea survive as a data-surface variant on a Surface primitive? The container-owned idea must survive, and cva alone cannot express it. button-surface.css:36-46 states the contract: "appearance is decided by the CONTAINER, never per call site… New surface? Pick an existing context or add ONE here — never restyle buttons at the call site." A cva variant is a call-site prop; moving the three contexts (.cg-bar, [data-surface="panel"], hero) into cva rows means 4 variants × 3 contexts = 12 combinations that every call site can now get wrong. Concretely:

  • Button's variant fills (default gradient, outline glass, the aria-expanded/data-popup-open restatements) go into button.tsx's cva. They are the button's own appearance.
  • The three contexts stay container-owned, on a Surface primitive keyed by data-surface="hero|panel|bar|media", expressed as arbitrary descendant-variant bundles in the primitive's own class string — [&_[data-button-variant]]:h-8 [&_[data-button-variant]]:border-0 …. This mechanism is proven: wave 2 reproduced four legacy selectors and their relative specificities this way for MediaCardActions, and explicitly rejected group variants because "group-data-[upload-active]/card: resolves to (0,2,0) and would lose to the hover rule it must beat" (wave2-report.md:172).
  • --btn-*, --cg-*, and the [data-record-action] / .dark [data-record-action] re-pointing stay as token declarations in index.css. They are tokens, which the plan already sanctions, and the re-pointing depends on the where-declared resolution rule that a utility cannot reproduce.
  • The glass surface itself becomes @utility glass / @utility glass-media in index.css, not a utility stack. Two reasons. It has a multi-layer background plus two degradation blocks (@media (prefers-reduced-transparency: reduce) and @supports not (backdrop-filter…)) that no utility stack expresses compactly. And Tailwind's composite backdrop-* utilities emit a fixed function order — blur, brightness, contrast, …, saturate — while chrome.css:40 needs blur(30px) saturate(1.5) contrast(0.4) brightness(1.14). Filter functions do not commute; reordering changes the rendered glass. button-surface.css's blur(12px) saturate(1.4) happens to survive; chrome.css's four-function stack does not.

Net: button-surface.css (286) + chrome.css (162) → about 40 lines of @utility and tokens in index.css, the rest in button.tsx and a new surface.tsx.

Risks the plan misses

  • The prerequisite is an external styling-contract change. Generated styleAttr names may be consumed by embeds or custom code even if stored documents do not contain them. Audit production HTML/customization before removing generic aliases.

  • Global font loading is currently inconsistent. Moving Geist into the eager bundle deliberately repaints auth/legal routes and changes bundle weight; leaving it where it is means font-sans lies on public routes.

  • CSS chunk availability can regress. chrome.css currently reaches public VideoPlayer through a direct import. The replacement must remain available on public routes after styles.css disappears.

  • Portal context can sever container-owned styling. Dialogs, menus, tooltips, and popovers mounted under body will not inherit a data-surface ancestor outside the portal. Put the surface marker on portal content and test it there.

  • Exact breakpoint semantics are already known to drift. Named Tailwind max-* variants exclude the nominal boundary while legacy max-width includes it. Recorder/edit also combines 640, 760, 768, 780, and a 60rem container query.

  • Tailwind source discovery is route/package sensitive. Classes moved into a shared package or dynamically assembled string may generate no CSS because scanning is rooted in editor; add an explicit @source or keep literal styling contracts inside the editor.

  • Current screenshots hide too much and use mutable data. Masking all images/video and relying on a live account can conceal scrims, overlays, wrapping, and empty-state changes. Fixtures must control asset dimensions and content.

  • Browser-owned controls need cross-browser evidence. Range thumbs, backdrop filters, autofill, media permissions, fullscreen, pointer-coarse behavior, and reduced transparency are not honestly covered by the Chromium-only resting-state suite.

  • Large normalization diffs can hide accessibility regressions. Wave 3 had all 16 screenshots fail intentionally, yet a real defect remained elsewhere. Focus rings, hit targets, contrast, reduced motion, keyboard order, and accessible names need independent assertions.

  • Partial migration preserves source-order hazards. There are selectors defined across ordered partials and colocated CSS. During intermediate slices, a utility may still lose to an unrelated unlayered rule; every slice needs a residual-selector/import scan.

  • Near-zero source CSS does not guarantee a smaller or simpler output. Large arbitrary utility strings can increase generated CSS and duplicate contracts across call sites. Track compiled CSS size and repeated class sequences.

  • Semantic legal cleanup can alter regulated content. Preserve exact visible text, links, dates, and heading/list semantics with tests; do not review it only as a styling diff.

  • Parallel PRs can invalidate visual proof. Any merge changing shared primitives or index.css changes another PR’s base. Reports must name the exact base, parity, and normalized SHAs and be regenerated after rebasing.

Ratchets (land with slice 0)

  • @shadcn/lint rules other than no-unknown-classes at error with a shrink-only per-file baseline like eslint-suppressions.json; no-unknown-classes stays off until the last partial goes, then on at error.
  • Per-file CSS line-count ratchet: a script with a committed baseline that fails when any .css under editor/src grows; check-ci-invariants.sh runs it in CI.
  • lint-on-edit.mjs hook extended to .css so editing a stylesheet triggers the ratchet locally.

PR strategy

Stacked PRs: slice N branches from slice N−1's branch and targets it; when a PR merges, retarget the next to main. Each PR carries its own harness spec (new cases for its surfaces), its own three-way report, and its own before/after metrics. Main pushes deploy to production, so every merge is a visible change; William reviews the report before merging.

Risks

  • .jp-theme token shadowing: canvas components styled with theme-token utilities pick up the customer's page colours. Mitigation: --jp-* namespace before slice 7; until then, canvas slices avoid theme-token colour utilities.
  • Surfaces without a deterministic capture (recorder with live camera, drag-and-drop, transitions). Mitigation: fake media streams in Playwright, computed-style probes, manual before/after PNG pairs archived per wave.
  • font: inherit deletion changes every form control size app-wide. Mitigation: its own slice with a route-wide screenshot sweep.
  • Review load: canvas diffs are large. Mitigation: canvas last; cropped-region diff tooling from wave 3 (diff-regions.mjs, crop-pair.mjs) promoted into scripts/.
  • Drift while slices are open: someone adds to a partial. Mitigation: the line-count ratchet from slice 0.
