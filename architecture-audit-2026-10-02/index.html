Bottom line

The platform is not the problem, and this time I tried hard to prove otherwise. The Worker answers in 13 to 22 ms, share page HTML arrives in 54 ms, and customer playback fails 2.4% of the time once mail scanners are removed. Mux's average is 4.9%. A framework migration, a sync engine, Hono and tRPC each lose on this repo's evidence (see "From scratch").

The problem is that the system watches itself and not the customer. From 7 September to 1 October every lead form and every page password answered 403 in every browser. Production logged zero exceptions, because a refusal is not an exception. No prospect lead has been recorded since 31 August, apart from test probes on 1 October. In the same way, 2,689 reps have "notify me when someone watches 60%" switched on, and nothing in this codebase has ever sent that alert. The settings came over from the old app; the sending did not.

So the order is this. First, prove the prospect's form, password and playback in production on a schedule, and alarm when leads stop. That takes hours. Second, tell reps when a prospect acts, starting with lead submissions, which already name the person. That takes a day or two. Third, finish the video lifecycle work (WIL-3494) through to deleting the old JSON copy. That is the one architectural move worth its weeks, because video is where the fixes keep landing. The route table (WIL-3401) is worth doing, scoped to policy, after the video work leaves the shared files.

The target

Same vendors: Workers, D1, R2, Mux, WorkOS, Stripe, Cloudflare email. On that platform, six properties today's code lacks.

  1. Production proves the customer's outcomes. A scheduled check opens a public page, submits a lead, unlocks a password page and starts playback, and an alarm fires when leads or plays stop. Today the deploy smoke checks three URLs and one redirect.
  2. Every fact has one owner. A video's server facts live in the videos row only. The node's JSON holds what the rep chose, nothing Mux decides. Page liveness lives on the page, and a database trigger keeps routes from outliving it.
  3. The rep hears about the prospect. Lead submissions and watch thresholds become notifications, sent by the existing one-minute cron from a watermark, once per viewer and threshold.
  4. Policy is declared once. One route table states who may call each route, whether the trial wall applies, origin rules and rate limits. Dispatch reads the row. Env is parsed once into named capabilities, so a missing secret fails the deploy, not a customer's request.
  5. Each wait has a visible end. Every spinner and poll ends in a state the screen renders: saved, refused, still preparing, unavailable.
  6. The repo holds only its own instructions. Vendored skills are installed from the lockfile, not committed. One deploy builds once.

Fable estimated the same features at about 70,000 to 75,000 lines against 97,000 today. The difference is transitional video code, two layers of Library caching, a legacy redirect module, a duplicate screen and deploy policy written four ways. That is a list of deletions, not a rewrite.

The highest-leverage moves, in order

0. This week, in hours: watch the prospect's flows in production

The 24-day outage came from a security header change (7 Sept) that made browsers send Origin: null on form posts, which the new origin guard refused. The fix landed on 1 October with a test, but that test only runs on previews and manual staging runs. The production gate never submits a form. Add a scheduled production check for lead submit, password unlock and first play on an internal page, plus an alarm when submissions stay at zero for a set period. A route table would not have caught this bug. A canary would have caught it the same morning.

1. Rep notifications, starting with leads

Five switches in Settings write five columns nothing reads. The mailer has five templates, none about a prospect. Lead submissions already live in the main database and name the person, so "Anna from Acme filled in your form on Proposal X" can ship in a day or two as a cron job reading new submissions from a watermark. Watch thresholds come next, with care: page views live in the stats database, and mail scanners generate views, so "someone watched 60%" must count real playback per session and skip known scanner traffic. Naming the viewer on a shared link is a later product decision, not a prerequisite.

2. Finish the video lifecycle through deletion (WIL-3494)

This is the architectural move. Video has 70 fix commits since 1 September and holds six of the most-fixed live files. Today every write to the videos row also rewrites the old JSON, and a row the parser rejects silently falls back to that JSON, so the two copies can disagree without anyone noticing. Keep #936 and #962 moving. In PR 7's migration, add the checks the parser needs and the table lacks: an upload id while uploading, an asset time while processing or ready, a ready time when ready, an error when stalled or failed, and both clip ends when a clip exists. When videos-verify has read zero differences for a week, delete the projection, the fallback, the tombstone joins and the placeholder ports. Multi-track recording should be built on PR 6's take session, not on today's recorder route.

3. The route table, scoped to policy, after #936 merges

Worth doing, but smaller than the first draft claimed. About eight fixes since September were route policy, against 70 for video. It also shares files with the in-flight video PRs, so it goes after them, not beside them. Do the Env parsing as its own first PR. Leave typed responses out of it. Exporting response types from a table whose handlers return raw responses would move the cast, not remove it, and a lint would then bless it.

Performance and customer experience

What stunning looks like for the rep. Stop recording and the link is on the clipboard in about a second; that already works (1.1 s), so keep it. The status beside the link says Uploading, Processing, Ready to share, or Needs attention, never a silent failure. Within a minute of a prospect acting, the rep gets a message naming who and what, with a link straight to it. The Library card shows the latest activity without opening a modal.

What stunning looks like for the prospect. The page paints in under a second on a phone, and the tap plays at once; with the warm-up it now does, at 62 to 105 ms. A form keeps them on the page and reveals the next step. A processing video never dead-ends.

Keep, and copy

  • The jobs table: fenced leases, state checks, one running job per subject, dedupe keys. The best schema in the repo, and the right home for notifications.
  • The Stripe event inbox: stored by event id before the 200, retried by cron, abandoned after a bounded number of tries.
  • Generated D1 row types with the lint behind them. Extend the lint to untyped .first() and to .json() as.
  • The editor's document store from #916, and the render-parity harness that proved 6,887 publications byte-identical.
  • The page cache's first rule: read the page from the database before any cache lookup, so unpublish and password changes act at once.
  • Early link creation in the recorder, which runs the claim beside the upload. The gap is in what the screen says, not in the order.

Corrections and disagreements

The first draft ranked the route table first. All three critics disagreed, with evidence. Its cited "54 router fixes" were mostly billing, admin and cron. Route policy took about eight. And it shares files with the in-flight video PRs. I agree with them.

Typed responses from the route table, refused. Two critics refused it outright. Exporting response types from a table whose handlers return raw responses moves the cast instead of removing it.

Notifications "in the same batch as the view", impossible as written. Views and jobs live in different databases. Lead alerts avoid the problem entirely.

Foreign keys for dangling routes, replaced by triggers. Pages are soft-deleted, and a foreign key to a deleted-but-present row still passes.

The 60-second cache cap is a constant. I first attributed it to short media signatures. They last 24 hours.

The overnight report's #929 and #919 were overstated. The cache works and is nearly inert. Image resizing works at 720 and fails at high pixel density.

Astra put the video lifecycle first; Opus and Fable put the canary first. I put the canary first because it takes hours and guards revenue. I rank video as the one architectural move because the critics' fix counts back it.
